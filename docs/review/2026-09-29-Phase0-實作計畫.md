## 2. 範圍

### 2.1 做

1. **三個型態分頁**：超商｜外食｜自煮（`<button role="tab" aria-selected>`），取代 radio。
2. **預設分頁**：`resolveDefaultMealType({ planned, pref, lastPicked })`〔1-5〕：`planned`（Phase 0 固定 null）→ `pref`（有效型態值）→ `lastPicked`（有效型態值）→ `"convenience"`（PRD 第 4 節）。`cook_quick`／`cook_full` 對應自煮分頁＋子切換。`settings` 讀取失敗當空物件、不擋 modal〔1-5〕。註解寫明：這跟推薦的 `getSourcePref`（不合法值退回 `DEFAULT_MEAL_PREFS`）刻意不同〔Q8〕。
3. **商品分頁**（超商、外食）：
   - 超商分頁＝`convenience_items` 裡 `channel: convenience` 且不是飲料。
   - 外食分頁＝`taiwan_items` 非飲料在前，`convenience_items` 裡 `channel: delivery` 在後（沿用現在 item-picker.js L17–29 的來源順序）〔N8〕。
   - **整份餐盒、便當都列出**（刪 `excludeWholeMeals`／`WHOLE_MEAL_CATEGORIES`）。
   - **依 PRD 6.3 分區**〔2-1〕：內建品項先依角色分區（主餐 → 配菜 → 點心），區內再依 `category` 分組，組的順序與組內順序都照資料原始順序，不按熱量排（PRD 6.1）。
   - **「我的品項」是例外**〔N8〕：依 `channel` 放進對應分頁，**永遠整組放在分頁最後、不進角色分區**，**預設收合**〔1-5〕，下方「＋新增到我的超商/外食品項」。`archived: true` 的不列出（Phase 0 沒有封存入口，先把規則放好）。
   - 被擋的品項排在**組內最後**、灰階、寫原因；分頁頂端一行中性文字「灰色的 N 項因你的過敏原／飲食／不吃設定不能選」；整組都被擋時收成一行「沙拉（4 項因設定不能選）」，可展開〔Q4〕。
   - 空狀態：分頁沒有任何可選品項時顯示中性文字（例：下午茶的超商分頁只有 1 項）〔Q9〕。
4. **飲料步驟**（三分頁共用）：分頁內容下方、摘要上方，「加飲料（選填）」，第一個選項「不加」，單選；被擋的灰階寫原因〔1-5〕；切換分頁不清掉；只顯示熱量，不做糖量警告、不預設無糖（PRD 6.1）。內建飲料在前，`role: drink` 的我的品項（不分 `channel`）在後。飲料**維持不看時段**（現行 `fitsSlot`：一杯飲料在哪個時段喝都合理；推薦仍照 `valid_slots`）——明確保留，不是默默沿用〔Q9〕。
5. **自煮分頁**：
   - 子切換「快煮（簡單料理）｜開伙」，值就是這餐的 `meal_type`（decisions #34），不從食材反推。
   - **選項灰階一律問 engine 的 `composeOptionProblem`**〔N3〕（第 3 節）：免開火、快煮難度、已達 `COMPOSE_MAX`；過敏原／飲食／不吃照舊走 `passesHardFilters`。ui 只顯示回傳的原因。已選的選項即使後來變成不合法（例：切到快煮）也保持可取消，送出時由 `composeProblem` 擋下並提示。
   - 蛋白質最多 2、蔬菜最多 3（`COMPOSE_MAX`），達上限時未選的選項灰階並寫「最多選 N 個」。主食、醬料、烹調法單選。
   - 縮放：主要槽位＝有主食槽就是主食，否則蛋白質；蛋白質是主要槽位時，**只有選 1 個蛋白質才有滑桿**（目前資料沒有「無主食槽＋可選 2 個蛋白質」的骨架，這條防未來，用 check-engine 假骨架測〔Q5〕）；蔬菜不縮放。多個蔬菜時用油仍是「有蔬菜就＋5g」，刻意不按蔬菜數量加〔3-7〕。
   - **用油選項照章程 B5.6 原文**〔1-3〕：只在烹調法是煎、炒時出現，選項＝「預設（N g，依用油習慣）／約 1 茶匙（5g）／約 2 茶匙（10g）」，相同克數只列一次。**不加「不用油」**（跟「不加調味」同一批送 C3，登記日後討論）〔Q6〕。
   - 調味選項（骨架 `seasoned: true` 時）：「清淡／一般」，未覆寫時依 decisions #28 決定預設。
   - 狀態存 `implicitOverride = { oil_g?, seasoning? }`，實際值＝覆寫值 ?? 預設值；換成不能選用油的烹調法時清掉用油覆寫〔3-3〕。
   - 步驟編號只數目前看得到的步驟（截圖發現「1.」後跳「4.」）。
   - **自煮分頁要餐型完整才能送出**；只記飲料請到超商／外食分頁，提示文字寫出這一點〔3-5〕。
6. **外食分頁最上方「找不到？直接估算」**：名稱（選填，預設「外食估算」）＋S/M/L（`ESTIMATE_SIZE_KCAL`）→ `estimate` 元件，只存在這一餐。蛋白質等未知是 null（C4.5）。估算是使用者自己宣告吃了什麼，**不過硬性過濾**〔2-6〕。可以跟外食商品、飲料同一餐送出〔Q7〕。文案延續 PRD 第 9 節「有聚餐？先記下來，其他餐會自動調整」。
7. **「我的品項」快速新增**（超商/外食分頁）〔1-1、1-2、Q9〕：
   - 必填：名稱、熱量、角色晶片（早午晚預設主餐、下午茶/宵夜預設點心；可選飲料）。
   - 過敏原：未確認〔預設〕／確認不含／含：勾選。
   - 飲食宣告「這個品項是：全素／蛋奶素／都不是（預設）」：使用者有設飲食限制時放在必填區下方；沒設時放進「更多」〔N11〕。這樣之後才改成素食的人，也有機會在建立當下就填好。
   - 「更多（選填）」：蛋白質、碳水、脂肪、纖維、飽和脂肪、鈉（PRD 10.3；沒填是 null）＋上面的飲食宣告（沒設飲食限制時）。
   - `channel` 取目前分頁；`valid_slots` 依角色預設（主餐：早午晚宵夜；配菜：全部；點心：下午茶、宵夜；飲料：全部），**一定包含目前時段**。
   - **資料路徑**〔N1〕：表單 → 記錄（PRD 10.1 格式）→ `validateCustomFood`（B8）→ `addCustomFood` → `fromCustomFood`（改成讀記錄裡的 `role`、`channel`、`valid_slots`，飲食標記用現有的 `dietTags(f)`）→ `partitionByMealType` → `passesHardFilters`。**送出前預告也走同一條**：ui 把草稿組成記錄、用 `fromCustomFood` 轉成品項形狀，再交給 engine 的 `quickAddProblem(item, profile)`；engine 不 import data（C1），也不另寫一份轉換。
   - **送出前預告**：以使用者目前的過敏原／飲食設定，這筆照現在填的會被擋時，表單上用中性文字寫出是哪個設定擋住，例如「你設了過敏原『蛋』，過敏原未確認的品項不能選」。**不寫「改成確認不含就能選」這類引導**（C4.1：沒確認就保守排除）〔N10〕。
   - **宣告矛盾提示**〔N13〕：宣告全素卻勾「含：蛋／乳製品／魚／甲殼類／軟體動物」，或蛋奶素卻含魚／甲殼類／軟體動物時，`quickAddProblem` 回中性提示，不擋存檔。章程 B1 規定我的品項只受 B8 驗證，B6.8 不適用；計畫明寫這一點。**「全素但過敏原未確認」刻意不提示**〔S8〕：未確認是預設值，加了之後幾乎每次都會跳出來，變成噪音；有設過敏原的人另有「送出前預告」。
   - 存完：能選且同角色還有名額 → 直接選中（飲料就選進飲料步驟）；被擋或名額已滿 → 不選中，提示原因。
   - PRD 10.1 其他欄位（`archived: false`、`copied_from: null`、`created_at`、`updated_at`）由 `addCustomFood` 寫預設值；管理畫面在 B-1。
   - PRD 10.3、0.1 第 9 點同步寫進「飲食宣告欄」與「更多」。
8. **`picker_last_meal_type`**：`addDailyLog` 成功後才寫 `settings`，寫失敗只記 console；每時段一個值直接覆蓋；推薦、統計、hero 不讀（check-arch C4.15）。`engine/picker.js` 只收 `lastPicked` 參數，連註解都不出現這個字串〔2-5〕。
9. **送出**：
   - 規則沿用 `manualSelectionProblem`（decisions #20：只限各角色數量，不要求主餐；round2「早午晚要 main」寫在 #20 之前，以 #20 為準，不另開紀錄〔Q1〕）。**估算不佔角色名額，但算「有選東西」**〔3-4〕。
   - **手動主餐上限依時段**（第 6 節使用者決定）：常數在 `core/config.js`，`manualSelectionProblem`／`canAddManualItem` 收 `slot` 參數，超量訊息依常數產生（例：「午餐的主餐最多 2 個」），不再寫死「每種角色最多選 1 個。」。

## 3. 程式結構

- **core/config.js**：
  - `COMPOSE_MAX = { protein: 2, vegetable: 3 }`。
  - `QUICK_MAX_TIER_RANK = 1` 與 `isQuickTier(rank)`：recommend.js 兩處（`maxRankForSource`、`filterBySource`）與 meal-content.js `cookMealType` 改用它〔2-4、N12〕。
  - 手動角色上限依時段：`MANUAL_ROLE_MAX` 保留為預設，加 `MANUAL_MAIN_MAX_BY_SLOT`（值見第 6 節）與 `manualRoleMax(role, slot)`。
- **engine/meal-content.js**（共用判斷，pool 與選擇器都用）：
  - `maxTierRank(method, items)`〔N12〕：烹調法（可為 null）與食材的最高難度。pool.js L84、`contentFromCompose`、`composeOptionProblem` 共用。
  - `deriveCookMealType(rank)`（現在的 `cookMealType` 改名匯出）：推薦的 `contentFromRec`（偏好是 auto 或退回時）與 commit 2 的舊畫面使用〔N2〕。
  - `noCookViolation(method, items)`〔N4、2-3〕：免開火且**任一食材（蛋白質、主食、蔬菜、醬料）**需要加熱就回 true。pool.js L68 在迴圈裡直接呼叫它，不組草稿。
  - `composeOptionProblem(item, axis, draft, { tier })`〔N3〕：回傳原因或 null，只判斷「這個選項加進目前草稿行不行」：免開火（文字沿用「這個食材需要加熱」）、快煮難度（`tier === "cook_quick"` 且 `!isQuickTier(...)`）、已達 `COMPOSE_MAX`（只對還沒選的選項）。硬性過濾不在這裡，照舊 `passesHardFilters`。
  - `composeProblem(draft, { tier })`〔2-3、N2〕：判斷順序固定，前兩段的文字跟 `composeMissingReason` 逐字相同：
    1. 餐型不完整：「請先選餐型」「請選蛋白質」這類，照 manual-picker.js L210–213 原文；
    2. 免開火：「免開火不能搭配需要加熱的食材，請換烹調法或換食材。」（食安優先顯示）；
    3. 不在骨架 `allow`；
    4. 超過 `COMPOSE_MAX`；
    5. 快煮下有元件難度超過門檻。
  - **草稿 → MealContent → 合計的單一路徑**〔3-1、N6〕：
    - `buildDraftContent(draft, catalog) → MealContent`：商品＋估算＋飲料，或自煮＋飲料＋`implicit`；`meal_type` 由呼叫端傳入分頁值／子切換值〔N9〕。
    - `contentTotals(content, catalog)`：
