# 家庭共餐（自煮）— 設計草案 v0（待獨立審核）

> 依據：使用者 2026-10-04 的決定（本檔 §1）；既有：decisions #148、#151、家常菜估算已上線（`data/home_dishes.json` 17 道、`estimate` 元件的 `est`）、PRD 第 3 節（MealContent）、12.5（我的料理 `dish` 元件）、第 5 節採買清單（decisions #62、#96）。
> 目的：把「家庭共食」從外食分頁的估算，改成**自煮裡的「共餐」**，選的是**真的家常菜 1–4 樣**，採買清單可以由選的菜反推要買什麼。自助餐不動。

## 1. 使用者決定（逐字摘要）
1. 家庭共餐屬於**自煮**（家裡煮的）：午餐／晚餐 →「自己選」→ 自煮 → **共餐** → 選家常菜 1–4 樣。
2. **自助餐維持自助餐**，留在外食分頁（現有的類別平均估算不變；分頁名稱 2026-10-04 剛改成「外食/共餐」，要改回「外食」）。
3. **採買用 B**：選的是**具體的家常菜**（不是素菜／菜肉／純肉類別），採買清單由所選的菜的配方**反推購買需求**。
4. 其餘照我建議：共餐只在**開伙**（快煮不顯示）、只開放午餐與晚餐、不進推薦（章程 C4.17）、主食、湯、份量的選法沿用現有。

## 2. 現況（要動的地方）
- 家庭共食目前是 `estimate` 元件（外食型態）：`est: { n, cats[], staple, staple_size, dish, soup }`，數字用**類別平均**（`data/home_dishes.json` 的 classes）算，不知道是哪幾道菜；`size` 是 null，快照七欄有數字。PRD 第 3 節把 `estimate` 定義在外食型態。
- 家常菜資料：17 道（菜 14、湯 3），每道有每 100g 七欄、`cooked_g`（成品重）、配方（`data/reference/home_dish_recipes.json`：生重 g、role veg／protein／other、用油 g）。配方的 `ref` 是內建食材 id、`fx_` 分層品項 id、衛福部編號、調料選樣表 `hs_`。
- 採買清單（PRD 5.3，**還沒做**，Phase 4）：只彙總 `ingredient` 元件；「我的料理不進 MVP」（decisions #62）；`purchase_key`、`purchase_unit`、`g_per_unit` 欄位還沒補。
- `dish` 元件（PRD 12.5，切片 9 我的料理，**還沒做**）：快照是一份的營養、`qty` 是份量倍數 0.5／1／1.5／2、只出現在自煮型態、這一餐不含 `ingredient`、紀錄的 `implicit` 是 `{ oil_g: 0, seasoning: null }`、推薦不產生；`validateDailyLog` 等已預留 kind 但 `COMPONENT_KINDS` 現在沒有 `dish`。
- 單品 `food` 元件（已做）：代換表品項或我的食材，`qty` 份或 `amount` 克，快照是 1 份的量與營養；可用在自煮只有單品的一餐（`archetype_id`、`method_id` 為 null、implicit 0）。

## 3. 提案（請審核者質疑）

### 3.1 資料形狀：共餐用什麼元件表達
**方案 Y（我的傾向）：重用 `dish` ＋ `food` 元件**
- 每道菜一個 `dish` 元件：`{ kind: "dish", ref: "hd_xxx", amount: <吃的克數>, snapshot: { name, amount, unit: "g", 七欄, partial? } }`（沿用 `food` 的 amount 記法：快照是「1 份的量與營養」，合計＝快照 × amount ÷ snapshot.amount；`ref` 以 `hd_` 開頭＝內建家常菜，將來 `cdish_` 是我的料理）。
- 主食一個 `food` 元件（`fx_cooked_rice`、`brown_rice_cooked`、`mixed_grain_rice_cooked`、`fx_cooked_noodles`，用 `amount` 克）；湯一個 `dish` 元件（湯 `hd_` ，amount 毫升當克）。
- 餐的型態 `cook_full`、`archetype_id`／`method_id` null、`implicit` `{ oil_g: 0, seasoning: null }`（用油與調味已在每道菜的營養裡）。沿用 PRD 12.5 的規則（不含 `ingredient`）。
- 好處：與切片 9 的「我的料理」同一種元件，將來不用兩套；採買只要讀 `dish` 的 `ref` 與 `amount` 去查配方；預約格式沿用（計畫只存 `ref` 與 `amount`，不存快照，重新解析）；不再需要 `est`。
- 代價：要實作 `dish` 元件的 db 驗證、`toSavedContent`／`toPlanContent`／`resolveSavedMeal` 解析、`contentTotals`、備份驗證、check-arch C4.17③ 的 `"dish"` 字面量規則（推薦檔案不得出現）；PRD 12.5 的「`dish` 的 `qty`」與這裡的 `amount` 要統一（建議 `dish` 也用 `qty` 或 `amount` 擇一，同 `food`）。
**方案 X：沿用 `estimate`，把 `est` 改成 `{ staple, staple_size, dishes: ["hd_a", …], dish, soup: "hd_s"|null }`**，仍是外食型態以外的 estimate。好處：改動小。壞處：自煮型態就要放行 `estimate`（現在自煮只收 ingredient／food／product 的規則要鬆綁），採買要另外讀 `est`，跟切片 9 的 `dish` 平行兩套。

### 3.2 份量
- 沿用現在的分法：**菜的全分量**小／中／大＝120／160／200g，分給選的 N 樣（每樣 1/N），因此 4 樣不比 1 樣多；主食小中大＝2／4／6 份（飯 80／160／240g、麵 120／240／360g）；湯 250ml 可選一道湯。
- 與現在不同：每樣是**具體的菜**（用該道自己的每 100g），不是類別平均。熱量與營養＝該道每 100g × 克數。
- 預設份量沿用 2026-10-04 的規則：菜量依蛋白質目標（每餐 <30g 小、30–50g 中、>50g 大），主食量選整餐熱量最接近這個時段配額的一格。
- 每樣可否各自調克數？先不做（沿用均分），日後再說。

### 3.3 畫面
- 自煮分頁（開伙）：餐型列表之外，多一個「共餐」區塊（午餐、晚餐才有；快煮、早餐、下午茶、宵夜沒有）：主食（含不吃）→ 主食量 → 從家常菜清單（14 道）點選 1–4 樣（依類別分組顯示素菜／菜肉／純肉，只當分組標題）→ 菜量 → 湯（3 道或不加）→ 預覽（熱量、蛋白質、鈉、各項克數）→ 加入這一餐。
- 外食分頁：標題改回「外食」；原「家庭共食／自助餐」卡改名「自助餐」，維持類別平均估算（`est` 現有形狀，使用者決定「自助餐維持自助餐」）。
- 家常菜被擋規則：共餐的菜是**複合料理**，過敏原一律「未確認」（章程 B6.3）、素食不標。使用者有設過敏原或不吃清單時要怎麼擋？提案：有設任何過敏原／素食限制時，共餐區塊整個**不擋但顯示「過敏原未確認」**？（待審核者意見：硬性過濾會讓有過敏原的人用不了共餐；但不擋違背「過敏原不得混進推薦」的精神——共餐不是推薦、是使用者手動記錄，同現有外食估算的處理：估算不過硬性過濾。）

### 3.4 採買反推（B）
- 一樣菜的採買量＝配方每項生重 g × (這一餐吃的克數 × 人數 ÷ 該道 `cooked_g`)。人數＝`household_size`（PRD 5.2，預設 1）。例：蒜炒高麗菜 吃 53g、人數 4 → 高麗菜 400g × (53×4 ÷ 282) ≈ 301g。
- 配方項目的 `ref` 要對到採買品項：食材 id／`fx_` 直接用；衛福部編號（如 E2100101 大蒜）、調料選樣表（醬油、糖、鹽、水）要處理：水與鹽可略過、調料列「調味料」不進清單或另列、衛福部編號需有名稱。採買清單的 `purchase_key` 合併規則（PRD 5.3）也要容納 `hd_` 來源。**採買清單本身還沒做**；本次只要求共餐的元件資料能被日後讀出配方，不實作採買 UI。
- 要不要先做一個純函式 `dishPurchaseLines(dishRef, amount, people, catalog)` 加 check-engine 斷言（不接畫面），讓 B 的反推邏輯有人驗證？

### 3.5 其他
- 型態：`cook_full`；`picker_last_meal_type` 記自煮；推薦不產生、不讀（C4.17③ 的 `homeDishes`／`"dish"` 規則；check-arch 要允許選擇器讀 `catalog.homeDishes`）。
- 已上線的家庭共食估算（外食分頁的類別平均那版）：因為使用者還沒有舊資料需要遷移（沒有網友使用），**直接改成自助餐**（卡名、名稱、`est` 形狀不動，名稱預設「自助餐：…」可選）。
- 預約、補記、昨天的餐：共餐三種模式都要能用；預約只存 `ref`＋`amount`。
- 備份：`COMPONENT_KINDS` 加 `dish` 屬資料格式放寬，備份格式不升版（沒有新 store／settings key），但要補來回斷言。

## 4. 給審核者的問題
1. 方案 Y（重用 `dish`＋`food`）與方案 X，哪個對？Y 會不會把切片 9 的設計綁死（PRD 12.5 `dish` 的 `qty` 倍數 vs 這裡的 `amount` 克）？`hd_` 內建家常菜與使用者的 `cdish_` 同一元件會有什麼衝突（db 驗證、快照 name、備份、`remapSavedRefs`）？
2. 每道菜快照存「1 份的量與營養」（`amount` 記法）夠嗎？預約只存 ref＋amount、日後家常菜資料改了怎麼辦（食材重算）——跟 food 元件的作法一致嗎？
3. 過敏原與素食怎麼處理（§3.3 最後一點）：複合料理一律未確認；有設過敏原的使用者要不要擋？建議值是什麼？
4. 採買反推（§3.4）的算法與資料缺口：配方 ref 中衛福部編號、調料、水、鹽怎麼進採買？`cooked_g` 當分母合理嗎（滷汁、湯的水量假設）？人數要不要由使用者在共餐表單選（而不是全域 household_size）？
5. 這一輪的切法與順序（文件先行 → db／engine 斷言 → 選擇器畫面 → 採買純函式）是否能每個 commit 通過 pre-commit？現有 `est` 的家庭共食要改成自助餐，哪些程式／文件／快照／walkthrough 會被牽動？
6. 還有沒有要問使用者的產品決定（共餐只午晚餐？每道菜各自調份量？共餐的菜要不要有「常吃」？）。
