# 今日建議的日期切換與預約 設計草案（第一版，2026-10-02，待 Opus 審核；第 7 節使用者已回答）

## 0. 背景與已定

- 使用者決定：#118（七個圓點、每一餐可先自選）、#119（不做週格子）、#120（補記過去 7 天）、#129（推薦只在今天；採買清單之後再做）、**#140（2026-10-02，本草案的依據）**。
- #140 摘要：①未來六天每天五個時段都用同一個三分頁選擇器「自己選」，存成預約、不寫 `daily_log`；②未來不跑推薦，只顯示已選合計熱量、不顯示目標（PRD 6.2）；③今天：已選（含沒記錄的預約）優先，其他時段推薦用每日目標扣掉已選的熱量與營養素；④預約與推薦都不自動當吃過，不加「餐時」；⑤隔天「昨天的餐」卡片一次確認；⑥「沒吃」＝0 大卡紀錄；⑦七天滾動。
- PRD 早就規劃了計畫層：第 1 節 L2 `meal_plan`（key＝`date|slot`）與解析規則、第 3 節計畫與紀錄的欄位差異與預算規則、第 5.1 節「週規劃＝泛化的大餐預約」、第 6.1／6.2 節防呆、第 9 節美饗日曆的職責去向（「確認」＝照計畫記下、過期失效不提醒）。本草案沿用，只改跟 #140 衝突的地方（第 6 節列出）。
- 現況（2026-10-02 查過程式）：
  - `engine/today.js` `planToday`：`recalcTodayBudget(目標, todayLogs)` → 已記錄或關閉的時段跳過 → 推薦。今天按「自己選」本來就直接寫 `daily_log`，所以「今天自己選優先、扣預算」已經成立；**新的只有「之前排好、今天還沒記的預約」**。
  - `engine/budget.js`：`recalcTodayBudget`、`slotNutrientShare`、`isCompleteLogDay`（每個開啟中的時段都有紀錄才算完整；tdee 第 9 步、近 7 天平均、本週總覽都用它）。
  - `engine/tdee.js` 第 9 步：下修目標前要 ≥14 個完整日且平均攝取 ≤ 目標 × 1.10（防棘輪）。#140 不自動當吃過就是為了不讓這道檢查失效。
  - App **沒有餐時**（`core/slots.js` 只有時段名稱、權重、開關；`ui/clock.js` 只給日期）。PRD 9 寫的「時段結束時間檢查沿用」是 v1 的東西，v2 沒有。
  - 選擇器 `openMealPicker(slot, { onLogged, savedEdit, onSaved })` 已有「編輯組合」模式（不寫紀錄、改呼叫 `onSaved`），`todayStr()`、`todayLogs`、`slotNutrientShare` 寫死今天。
  - 推薦顯示紀錄 `markRecipesShown` 只記「哪個組合哪天顯示過」，**沒記哪個時段最後顯示了什麼**。

## 1. 畫面

### 1.1 日期列
- 今日建議最上方（彙總卡之上）一條線、七個圓點：今天＋未來 6 天，標「今天」「週六 10/4」這類短字。點了切換到那一天，選中的圓點實心。
- 有預約的日子圓點下方一個小點（中性，不是「完成度」）。
- 切到別的分頁再回來 → 回到今天。

### 1.2 今天
- 彙總卡照舊（今天的剩餘預算）。
- 每個時段卡片，依序：
  1. 已有紀錄 → 照舊（已記錄＋撤銷＋存成組合）。
  2. 有預約、沒紀錄 → 顯示預約內容與熱量，按鈕「記下」「改」「取消預約」。不催、不提示。
  3. 都沒有 → 推薦（照舊），配額已經扣掉其他時段的預約；多一個「這餐不吃」（U1，寫 2.4 的沒吃紀錄，可撤銷）。
  - 預約了「這餐不吃」（U3）→ 顯示「這餐不吃（預約）」＋「記下」「取消預約」，配額照這餐不吃分。
- 「記下」寫一筆 `source: "from_plan"` 的紀錄（PRD 3 早就保留這個值），寫完計畫留著（紀錄優先顯示，PRD 6.1「計畫條目默默被取代」）。

### 1.3 未來六天
- 同樣的五張時段卡片（含基本資料關掉的下午茶、宵夜——#140「五個時段都可以」，見第 7 節 U2）。
- 每張：有預約 → 內容＋熱量＋「改」「取消預約」；沒有 → 「還沒排」＋「自己選」。
- **不跑推薦、不顯示配額、不顯示目標**（6.2）。頂端一行「已排 3 餐，約 1450 kcal」，只有數字。
- 選擇器以「預約模式」打開：標題寫日期與時段，確認鍵寫「排進 10/4 午餐」；不顯示這個時段的建議份額與缺口（`slotNutrientShare` 是今天的數字，未來不能顯示）；「存成組合」照樣可以勾。
- 文案延續 PRD 9 的精神：「有聚餐？先排進來，當天其他餐會自動調整」。

### 1.4 昨天的餐（隔天確認）
- 今天打開今日建議時，**昨天**開啟中的時段裡還沒有紀錄的，在日期列下方一張卡片「昨天的餐」，每個時段一列：
  - 有預約：預約內容｜**吃了**｜**改**｜**沒吃**
  - 沒預約、昨天有顯示推薦：昨天最後顯示的推薦｜**吃了**｜**S**｜**M**｜**L**｜**沒吃**
  - 沒預約、昨天也沒顯示推薦（沒打開 App）：**S**｜**M**｜**L**｜**沒吃**
- 「吃了」寫進昨天的 `daily_log`（`from_plan` 或 `rec_accepted`）；S／M／L 寫一筆 `estimate` 元件（外食型態，名稱「估算（中）」）；「改」以補記模式打開選擇器（日期＝昨天、預載預約內容）；「沒吃」見 2.4。
- 每列按完就收起來；整張卡「先不用」收起（只收今天，明天不會再列前天——前天以前走補記）。
- 用字中性（6.1）：標題「昨天的餐」，不寫漏掉、未完成，不用紅色。
- 全部時段都有紀錄、或昨天的資料都處理完，就不出現。

### 1.5 補記過去的一餐（#120，同一批）
- 本週總覽「補記過去的一餐」：系統日期選擇器（過去 7 天，不含今天）→ 時段 → 選擇器補記模式 → 寫那一天的 `daily_log`（`source: "backfill"`）。1.4 的「改」就是這個模式，所以一起做。

## 2. 資料

### 2.1 `meal_plan` store（DB_VERSION 4、備份 v6）
```js
{ key: "2026-10-04|lunch", date, slot, content, name, created_at, updated_at }
```
- 一個時段一筆（預約不像紀錄可以同一時段多筆；改＝覆蓋，取消＝刪除）。
- `content` 用**組合的儲存格式**（`toSavedContent`：只存 `ref`、`qty`／`amount`，`product` 不存快照，`food` 只存 ref），多允許 `estimate`（自帶快照）與 `implicit`（使用者選的用油調味，沒選是 null）。到顯示時用 `resolveSavedMeal(plan, catalog, ctx)`（`ctx.slot`＝那個時段）→ `savedMealDraft` → `contentTotals`，被擋、下架、已封存照組合的規則寫中性原因。**這跟 PRD 第 3 節「建立計畫時就存快照」不同，見第 6 節 T1。**
- `name`：建立時的顯示名稱（列表用；顯示內容仍以重新解析為準）。
- 只存今天以後的日期，過了昨天的計畫在開啟 App 時清掉（保留昨天給 1.4 用）。
- 不得有欄位引用運動（6.2，check-arch C4.12 已涵蓋新 store 嗎？要補）。

### 2.2 預約不吃這餐
- 第 7 節 U3（要做）：`content: { meal_type: null, components: [], skip: true }`，未來卡片顯示「這餐不吃」，當天那個時段不推薦、配額分給其他時段，隔天卡片列「沒吃（照預約）」一鍵確認。

### 2.3 昨天最後顯示的推薦
- 新 settings key `last_shown_recs`（dedicatedOnly）：`{ date, slots: { lunch: { name, content, totals } } }`。`buildRecommendation` 渲染推薦卡片時覆寫當天那幾個時段（同一天重畫會更新成最後顯示的那一份）。日期不是今天時第一次寫入就整個換掉，所以最多只留「昨天」或「今天」一天。
- 備份要不要帶？建議不帶（隔天就沒用）→ 但 `SETTING_KEYS` 與備份驗證要能接受或排除它，見 T3。

### 2.4 「沒吃」紀錄
```js
{ log_date, slot, meal_type: null, source: "skipped", name: "沒吃", content: { meal_type: null, archetype_id: null, method_id: null, components: [], implicit: null }, totals: 全部 0（sodium、sat_fat 也 0，partial false） }
```
- `isCompleteLogDay` 照舊（有紀錄就算），那天變完整，攝取少一餐 → 校正與近 7 天平均都更準。
- 今日卡片顯示「沒吃」＋撤銷；不提供「存成組合」（`canSaveLog` 已經擋空元件）。
- 驗證：`source: "skipped"` 時 `components` 必須是空陣列、`totals` 全 0、`meal_type` null；其他 source 照舊至少 1 個元件。

## 3. 引擎

### 3.1 解析規則（PRD 第 1 節改寫）
```
某天某時段的顯示內容 =
   已有 daily_log 紀錄 → 已記錄
   meal_plan 有這一筆  → 預約內容（重新解析、重跑硬性過濾；被擋寫中性原因，不默默刪）
   今天             → 推薦
   未來             → 還沒排
```
- 「有效型態」那一條拿掉：#140 未來的預約一定有內容（不做「只預約型態」），所以 `profile.meal_prefs` 照舊是唯一的型態來源。
- 被擋的預約：今天那張卡片顯示原因＋「改」「取消預約」，不推薦也不佔預算？見 T5。

### 3.2 今天的預算
- `planToday` 多收 `todayPlans`（只收今天、沒有紀錄的時段的預約，解析成功的那些），把它們當**暫時紀錄**：
  - `recalcTodayBudget`：預約的熱量扣掉、那個時段當已處理。
  - `checkHardConstraints` 的全天蛋白質缺口：預約的蛋白質算進去。
  - 推薦 `skipSlots`：有預約的時段跳過；`loggedContents` 加上預約內容（跨時段不重複）。
  - 選擇器的 `slotNutrientShare`（今天的自己選）同樣把預約算進去。
- 週纖維平均：只看紀錄，不看預約（預約不是吃過的）。
- 自煮預約（有 `ingredient` 元件）的熱量：**照選的份量**（U4；選擇器存下的主食倍數原樣用，不依當天配額縮放）。這修正 PRD 第 3 節「ingredient 不預先佔用、當天才縮放」。
- 預約在基本資料關掉的時段：照樣扣熱量（使用者明確排了要吃），那個時段本來就不推薦。
- 沒有任何預約時，`planToday` 的輸出要跟現在逐字相同（推薦快照不變）。

### 3.3 未來日子
- 不呼叫推薦、不算配額；只算每筆預約的 `contentTotals` 加總熱量給頂端那一行。
- 自煮預約的顯示熱量：用名目份量（scale 1）。

## 6. 給審核的技術問題

- **T1 計畫內容存法**：PRD 3 寫「建立時存快照、品項之後改了計畫不變」；本草案改成組合的儲存格式、顯示時重新解析（我的組合同一套，`food` 本來就沒快照）。理由：一份程式、改了我的品項或標不吃會照實反映、被擋有原因。代價：預約的熱量可能在你排完以後變動（例如改了我的品項）。哪一個對？
- **T2** 一個時段一筆預約（不像紀錄可多筆）夠不夠？
- **T3** `last_shown_recs` 放 settings 還是新 store？要不要進備份？
- **T4「沒吃」紀錄**：`source: "skipped"`、空元件、totals 全 0 對 `isCompleteLogDay`、tdee 第 9 步、近 7 天平均、本週總覽、`summarizeWeek` 的蛋白質纖維平均（0 會拉低平均——真的沒吃就該拉低？）有沒有副作用？跟「基本資料關掉時段」語意是否重疊？
- **T5** 今天的預約被擋（例如之後標了不吃）：還要不要扣預算？建議不扣、那個時段改推薦，卡片上方寫原因。
- **T6** 預約當暫時紀錄餵進 `recalcTodayBudget`、`checkHardConstraints`、`slotNutrientShare`、`loggedContents` 的做法對嗎？要不要另寫一個 `effectiveTodayLogs(todayLogs, todayPlans)` 統一產生？
- **T7** S／M／L（400／700／1200）用在下午茶、宵夜偏高：點心時段另一組（例如 150／300／500）？常數放 `core/config.js`。
- **T8** 過期計畫清理放開 App 時（ui 層）還是 db 讀取時過濾？日期滾動（午夜跨日、時區）怎麼測？
- **T9** 快照：沒有預約時 recs、picker、ui 逐字不變；新增 `plan/*` 斷言與 diff-recs 段落的範圍。
- **T10** 預約模式、補記模式要不要更新 `picker_last_meal_type`？建議只在今天記錄時更新。
- **T11** 備份 v6 的遷移：v5 沒有 `meal_plan` → 當空；fixture 凍結。
- **T12** 彙總卡（`today-hero.js`）要不要把今天的預約另外列出（例如「已排 1 餐 約 700 kcal」）？還是只反映在剩餘預算？

## 7. 使用者的產品決定（2026-10-02 全部照建議，decisions #141）

- **U1** 今天的卡片要不要也有「這餐不吃」（記 0 大卡，其他餐的配額自動變多）？建議**要**：跟昨天卡片的「沒吃」同一件事，今天就知道不吃的人不用等到明天。
- **U2** 基本資料關掉的時段（下午茶、宵夜預設關）在未來六天也能排？建議**能**（你說五餐都要），排了的到那天照顯示、熱量照扣；沒排的照舊不推薦。
- **U3** 未來可以預約「這餐不吃」嗎（例如明天早上要空腹抽血）？建議**可以**：當天那時段不推薦、配額分給其他餐，隔天卡片一鍵確認。
- **U4** 自煮的預約到當天，份量照你選的（建議），還是像推薦一樣依當天配額自動放大縮小主食？建議照選的：你排的是要煮的量，之後採買清單也用這個量；配額不夠時其他餐會自己調整。
- **U5** 「昨天的餐」只列昨天、前天以前走補記？建議**只列昨天**，卡片不累積。
