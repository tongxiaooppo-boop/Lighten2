## 1. 位置與搜尋

- 新主分頁「我的食物」，在「今日建議」旁邊，共 6 個分頁；**寬度在切片 2 用 mobile-walkthrough 截圖定案**。
- 分頁頂端一個搜尋：名稱、別名（代換表原列文字、衛福部俗名、合併重複列保留的名稱）；範圍是四個子分頁、我的品項、我的食材、我的料理、我的組合；結果標出子分頁與大類、子類。**不含衛福部全表**（U11）。
- 職責搬家（章程 A1.3）：

| 原位置 | 職責 | 新位置 |
|---|---|---|
| 基本資料「我的品項」區塊（`js/ui/profile/custom-foods.js`） | 清單、搜尋、新增、編輯、補填、封存／還原 | 「我的食物」各子分頁的「我的品項」組；補填照 PRD 10.4 只給未確認類 |
| 同上「已隱藏的內建品項」 | 取消隱藏；封存複製品時提示可取消隱藏原品項 | 「我的食物」的「已隱藏」組（U1）；封存時的提示照舊 |
| 基本資料的不吃清單（`tab-profile.js`） | 列出全部（含推薦卡片「順便不要」加的、已下架殘留的）、移除 | 「不吃的全部清單」：查得到的顯示名稱，查不到的列「已不提供」可移除（B9） |
| PRD 12.2 查詢頁（未實作） | 搜尋、明細 | 「我的食物」的搜尋與明細；衛福部全表日後處理（U11） |

- 「基本資料」只留身體數據、目標、飲食限制與過敏原、低碳、用油習慣、資料備份。

## 2. 四個子分頁

| 子分頁 | 內容 |
|---|---|
| 超商 | 內建超商品項（不含飲料）＋我的超商品項；照選擇器的角色分區、`category` 分組 |
| 外食 | 內建外食與宅配餐盒（不含飲料）＋我的外食品項；同上 |
| 自煮 | 代換表分層（水果、飲品除外，第 3 節）＋對不到代換表的內建食材＋我的食材＋我的料理（B-4 之後） |
| 飲品・水果 | 現成飲料、家裡的飲品、沖泡、水果（第 6 節） |

- 共同動作：**常吃**、**不吃**、**明細**。我的品項、我的食材、我的料理只有「封存」，沒有「不吃」。
- 常吃與不吃**互斥**：標不吃時自動移出常吃，反之亦然；還原的備份兩邊都有同一項時以不吃為準。
- 超商、外食內建品項有「複製成我的版本」；**被擋的也可以複製**（U13），按鈕在明細裡、不在被擋原因旁邊；複製表單照 PRD 10.3 顯示中性預告，過敏原照原品項帶入（章程 C4.1）。
- 明細的數字一律由 engine 函式提供（章程 C4.11）。

## 3. 自煮：代換表分層

### 3.1 層級與 id

| 層 | 來源 |
|---|---|
| 大類 | 代換表六大類（水果類在「飲品・水果」子分頁；乳品類的液體同時列在「飲品・水果」，見 6.1） |
| 子類 | 代換表的分組欄。附-3-3 分組欄空白的 9 列（麵筋泡、秋刀魚、牛肉條、豬肉酥、雞心、素雞、素魚、素雞塊、百頁豆腐）人工指定並寫理由；**乳品類 11 列不分子類，直接平列**（它只有全脂／低脂／脫脂分級，分級不當一層）；蔬菜見 3.4 |
| 品項 | 代換表一列拆成的品名，重複列合併（3.5） |

- **id 規則（切片 −1 就寫進 PRD，切片 2 之前定案）**：
  - 對得到 `data/ingredients.json` 內建食材的分層品項，**id 就是內建食材 id**（例：`chicken_breast`、`soy_milk`、`egg`）。所以在「我的食物」標雞胸不吃或常吃，跟推薦卡片「順便不要」是同一個 key，今日建議會跟著變。
  - 其餘分層品項用新前綴 `fx_`，凍結（比照 `ingredient_ids_frozen.json`）。
  - check-data 斷言：內建食材 id、catalog uid（含 `tw_`、`conv_` 等）、分層 id 三者不重複；分層 id 不用 `custom_`、`cdish_`、`cing_`、`saved_` 前綴（decisions #40「只比 key」的前提）。
- **對不到代換表任何一列的內建食材**也要出現在自煮子分頁（才能標不吃與常吃）：放進所屬大類與子類，標「內建食材（代換表沒有這一列）」，只顯示「今日建議的一餐：Xg」，不顯示「1 份（代換表）」。第二輪列出的候選：糙米飯、雜糧飯、藜麥、花椰菜米、希臘優格、鯛魚片、甜豆、紅甜椒、泡菜、照燒醬；青花菜↔花椰菜、A 菜↔萵苣逐項確認。烹調法與隱含成分（用油、調味）不列出。
- 不做衛福部第 4 層細項（U7）、不做「其他」大類。脂肪分級不顯示（章程 B3）。
- 麵腸、麵丸、烤麩、麵筋泡明細寫「原料：小麥麩質」。高蛋白質乾豆類照代換表歸全穀雜糧，靠搜尋與別名找。組內依名稱排序。

### 3.2 一個品項的資料

- **份量**寫成「1 份（代換表）」並附家用單位（「1/4 碗」「小 1 個」），不附手測量。
- **營養一律用可食部分計算**：附-3 用可食部分生重（熟重只顯示「煮熟約 30g」）；附-6、附-7 用可食量（購買量只顯示「連皮約 170g」；山竹用購買量會多算 5 倍）；附-4 用可食重量。
- 液體（乳品、無糖豆漿、優酪乳）的量是毫升；營養計算時用代換表附-1「1 杯＝240 公克(C.C.)」換成公克，出處 `derived`。
- **每一個品項的「1 份（代換表）」營養由 tools 預先算好寫進資料檔**（章程 C2：前端不換算）。出處 `derived`，公式「整合編號 × 克數」；引用內建食材的，check-data 驗證它等於內建食材 `per_100g` × 代換表克數（內建食材數值仍只由 `tools/build-ingredients.js` 產生，章程 B1）。
- 代換表營養欄不顯示、不計算（章程 B2）。明細不顯示六大類份數換算（decisions #36）。
- **畫面名稱由參考資料定**：去掉代換表的符號與附註（◎、◎◎、＊、＊＊、△、#、「（+5公克碳水化合物）」「(3個/斤)」「6x8x1.5公分」）；會誤導的加說明（「雞排肉（生）」「牛肉條（生）」）；原名留作別名。
- **過敏原與素食**：用 `collab/transcripts/exchange_tags.json` 的已審標註，加上第 8 節的修正，照章程 B6 轉入。依 D9，未確認的照現行規則擋。

### 3.3 對應規則（代換表 → 衛福部）

1. 一律人工逐項指定並寫理由；同名、俗名只當候選。
2. **狀態由代換表決定**（生、熟、乾、濕、含糖／無糖），找狀態相同的衛福部樣品；check-data 比對樣品狀態描述。例：代換表「油麵 45g」（濕）對 R2001101 衛生油麵，不對乾的 R2000201。果乾：代換表註明「果乾類含添加糖」，衛福部是無加糖樣品的，狀態不符，不收。
3. 有平均值樣品時用平均值；有內建食材的跟內建食材用同一筆。
4. 泛稱列（「一般魚類」）不當品項。
5. **對不到狀態相符的樣品時**：如果代換表本身有同一種食物的生熟等值列，熟的那列用 `derived` 推算（例：麵條(熟) 60g＝麵條(乾) 20g 的衛福部樣品值；粥(稠) 125g＝米 20g），出處寫「整合編號 × 比例，附-4 某列＝某列」，跟 decisions #35 的熟糙米飯同一做法。連代換表都沒有等值列的才不收（例：鍋燒麵(熟) 沒有乾的同名列；米粉(濕) 可食重量是 30~50 範圍值）。不收的列清單與理由寫在參考資料。
6. 對應結果存在 `data/reference/`，tools 產生前端資料檔。

### 3.4 蔬菜

- 每日飲食指南七類：葉菜類、花菜類、根菜類、果菜類、豆菜類、菇類、海菜類；附-5 沒有海菜，這組先不出現。
- 「筍與莖菜」（本 App 自己加的分組，標明）：竹筍、麻竹筍、綠蘆筍、茭白筍、玉米筍、半天筍、球莖甘藍、芋莖、鵝菜心。

- 標籤「高鈣深色蔬菜」，照指南名單逐項精確比對。組內依名稱排序。

## 4. 代換表品項直接記錄：`food` 元件（C3，另做專項審核）

### 4.1 選擇器

- 「自己選」三分頁共用兩步（U9），都不影響分頁的 `meal_type`（decisions #47）：
  - **「飲品・水果」**：現成飲料（內建 `role: drink` 品項，照角色上限 1 杯，C4.8）、家裡的飲品與水果（`food`，照單品上限）、沖泡建立的我的食材（`food`）。取代現在的飲料步驟。
  - **「加點單品」**：其餘代換表品項、對得到代換表的內建食材以外的分層品項、我的食材，依大類 > 子類展開，可搜尋。
- 每一步：常吃的在最上面；不吃的在最下方（分隔線、灰階、**預設收合，組名帶筆數**，例「你標了不吃（3）」，可直接取消）；被過敏原或飲食限制擋的灰在各組最後並寫原因，不進不吃組（章程 C4.1）。
- 份量：步進器，0.5 份一格，0.5–8（U10）；旁邊寫 engine 算好的換算（「4 份＝1 碗，160g」）。常數 `FOOD_QTY_MAX`；**不動 `QTY_OPTIONS`**（`product`、`dish` 照舊 0.5–2）。
- 單品上限：一餐最多 4 項，**不佔**主餐、配菜、點心、飲料的角色名額（章程 C4.8 修改）。
- 單品不套 `valid_slots`，任何時段都能選（比照飲料，decisions #44）。
- 一行中性操作說明：「單品不含烹調用油；有用油可以加油脂類」。
- 只有單品可以成為一餐（U8）；跟餐型、料理重複的照算、不擋、不提示（章程 C4.13）。

### 4.2 MealContent 與寫入驗證

- 元件：`{ kind: "food", ref, qty, snapshot: { name, amount, unit: "g"|"ml", kcal, protein_g, carb_g, fat_g, fiber_g, sat_fat_g, sodium_mg, partial } }`；快照是 1 份的營養與量，`qty` 照乘。
- `ref` 命名空間：分層品項 id（內建食材 id 或 `fx_`）或我的食材 `cing_`；解析規則分別查分層資料與 `custom_ingredients`。
- `data/db.js` `contentProblems` 加 `food` 分支：`ref` 非空；`qty` 是 0.5 的倍數且 0.5 ≤ qty ≤ `FOOD_QTY_MAX`；紀錄與計畫必有 `snapshot.name`、`snapshot.kcal`、`snapshot.amount`、`snapshot.unit`；允許 `partial`；`saved_meals` 的 `food` 不帶快照（11.1）。
- **只有單品的自煮一餐**：`implicit` 記 `{ oil_g: 0, seasoning: null }`（check-engine 斷言）；送出條件改成「餐型完整，或至少 1 道料理，或至少 1 項單品」；選了半套餐型又加了單品時照 `composeProblem` 擋下，不默默丟掉半套餐型。`manualSelectionProblem` 把單品算進「有選東西」。超商、外食分頁的 `implicit` 照舊是 null。
- 記錄名稱（`draftLogName`）寫量，不寫份數：「鮮奶 480ml」「飯 160g」，不寫「飯（半份）」。
- 合計一律 `buildDraftContent` → `contentTotals`（C4.11）。斷言：`food` 不參與主要槽位縮放（C4.6）；自煮加單品時隱含用油只算一次；null 照 C4.5 傳染、帶 `partial`。
- 硬性過濾：分層品項的 `vegan`／`lacto_ovo` 由 `data/catalog.js` 正規化成 `diet_tags`；`passesHardFilters` 多回一個原因代碼 `code: "allergen" | "diet" | "disliked"`，ui 依代碼決定放最下方還是灰在原位，不比對文字；斷言「又不吃又過敏」的品項留在原位（過敏原原因）。
- 分層資料掛在 catalog 物件上（`catalog.foodTree`），`resolveSavedMeal` 等不多加參數。
- **PRD 6.3 的豁免**（比照 `dish`）：第 1 點（骨架 `allow`、軸上限）與第 2 點（免開火，章程 C4.3）不適用於 `food`——只用於手動記錄、推薦不產生、營養用快照不縮放、單品不宣告烹調方式；第 3 點（顯示時重新過濾）照常。
