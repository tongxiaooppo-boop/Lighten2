# Lighten2 架構 review（v1 程式碼 → 2.0 起點）

日期：2026-09-28　審查者：Opus（Lighten2 主導開發）
範圍：`js/` 全部 14 個模組（約 4800 行）、`index.html`、`tools/check-engine.js`、`data/*.json` 的結構面（數值正確性另見資料 review）。
前提（使用者 2026-09-28 拍板）：**沒有任何使用者資料需要遷移**；以 v1 程式碼逐步改寫，不從零重寫。

---

## 0. 結論

1. **演算法層是健全的，保留**：目標熱量公式（`nutrition.js`）、體重趨勢校正（`tdee.js`，EWMA 暖機偏差已改 OLS）、每日預算分配（`budget.js`）、蛋白質/纖維缺口（`matcher.js`）、推薦引擎的硬性過濾＋餐型骨架＋統一成分模型（`recommend.js`）。`node tools/check-engine.js` 目前 31442 項全過。這些是多輪審核的成果，2.0 只搬家、不改邏輯。
2. **v1「修修補補」的根源不在演算法，在三個結構問題**：
   - **同一份食物資料被 4 個地方各自載入、各自正規化**，而且正規化規則不一致（有一處把「缺過敏原資料」當安全）。
   - **「一餐的營養怎麼算」寫了 4 份**（推薦組合、自己煮、自己選多品項、大餐），每修一個 bug 要改 4 處，漏改就是新 bug（大餐目前就漏了碳水/脂肪）。
   - **沒有模組系統**，全部掛在 `window` 上、靠 `<script>` 順序，工具函式（日期、escape、四捨五入）在 6–8 個檔案各抄一份。
3. **2.0 的改法**：保留演算法，重建三個「地基」模組——食物資料目錄（catalog）、一餐內容（MealContent）、資料庫（新 schema）——並改用瀏覽器原生 ES modules（不需要建置工具，GitHub Pages 照樣能跑）。PRD 2.0 的新功能全部蓋在這三個地基上。
4. **沒有使用者要遷移，PRD 2.0 可以砍掉的相容設計**見第 5 節。

## 2. 找到的具體問題

### 2.1 安全面：選擇器把「缺過敏原資料」當安全（潛在）

- `item-picker.js` 的 `normalizeTaiwan`／`normalizeConvenience`：`allergen_tags` 缺欄時給 `[]`（確認不含）。
- `recommend.js` 的 `fromTaiwan`／`fromConvenience` 同一種情況給 `["未確認"]`（保守排除）。
- 同一個品項在推薦卡片會被擋、在「自己選」卻能選。目前資料每筆都有 `allergen_tags` 欄位，所以還沒真的出事，但這正是 PRD 5.7「未確認就保守排除」要防的那種漏洞，而且是兩份正規化並存造成的。
- **2.0 處理**：正規化只在 catalog 做一次，缺欄一律 `null`＝未確認，過濾規則只寫在 `filters.js`。

### 2.2 正確性：大餐紀錄漏掉碳水/脂肪

- `feast.js` 的 `resolveFeastItem` 對台式品項只取 `protein_g`/`fiber_g`，`carbG`/`fatG` 永遠是 null，但 `taiwan_items.json` 早已補上碳水/脂肪。
- 結果：從美饗日曆記錄的大餐，碳水/脂肪會被 hero 的「資料涵蓋率警語」算成缺資料。
- 根源就是「一餐營養怎麼算」寫了 4 份（見 2.4）。

### 2.3 正確性：`daysSince` 的時區錯位

- `recommend.js` 的 `daysSince(dateStr)` 用 `new Date("YYYY-MM-DD")`，這會被解析成 **UTC 午夜**（台灣時間早上 8 點）。
- 台灣時間 00:00–08:00 之間，今天被顯示過的組合算出來是 `-1` 天，降權變成 `(3-(-1))×20 = 80` 分，比設計的 60 分重。
- 影響小（只在半夜到早上 8 點），但日期工具抄了 8 份就是這種 bug 的溫床。**2.0 處理**：`core/dates.js` 一份，全部用本地日期字串運算。

### 2.4 結構：一餐營養的算法有 4 份

| 位置 | 算什麼 | 缺值處理 |
|---|---|---|
| `recommend.js` `achievableNutrition`＋組合加總 | 推薦組合（含主要槽位縮放） | `sumOrNull` |
| `tab-today.js` `composeTotals` | 自己煮 | 食材當 0、飲料 null 傳染 |
| `item-picker.js` `sumSelected` | 自己選多品項 | `sumOrNull` |
| `feast.js` `resolveFeastItem` | 大餐 | 碳水/脂肪直接 null（2.2 的 bug） |

**2.0 處理**：`engine/meal-content.js` 一份，就是 PRD 2.0 的 MealContent：`buildContent → validateContent（骨架 allow／上限／免開火食安）→ contentTotals（含縮放）→ snapshot`。推薦、自己選、餐點日曆、採買清單全部呼叫它。

### 2.5 結構：同一份食物資料載入 4 次、正規化 3 次

- `recommend.js` `loadAxes`（7 個 JSON）
- `item-picker.js` `loadComposeAxes`（5 個 JSON）＋ `getConvenienceItems`
- `database.js` `getTaiwanItems`（把靜態種子資料放在「資料庫層」本身就是錯層）
- `tab-ledger.js` 還有一份 `TAIWAN_ITEM_IMAGE`，跟 `item-picker.js` 重複

**2.0 處理**：`data/catalog.js` 是唯一入口。啟動時載入全部種子資料＋使用者的「我的品項」，驗證格式、正規化成統一品項形狀（見資料章程），其他模組只查 catalog。

### 2.6 結構：沒有模組系統

- 14 個檔案用 IIFE 包起來，再把函式掛上 `window`。依賴關係只寫在註解裡，靠 `index.html` 的 `<script>` 順序維持。
- 重複的工具函式：`fmt`/`localDateStr` 在 6 個檔案、`dateAddDays` 在 7 個、`escapeHtml` 在 6 個、`round1` 在 8 個；時段中文標籤定義在 3 處（`tab-today.js` 的 fallback 版本還少了下午茶）。
- **2.0 處理**：改用 `<script type="module">`。
  - 不需要打包工具，GitHub Pages 直接跑，所有現代瀏覽器都支援。
  - 依賴變成顯式 `import`，漏載入會直接報錯，不會變成 `window.xxx is not a function` 的執行期錯誤。
  - `tools/check-engine.js` 改成 Node 直接 `import` 同一批檔案（Node 原生支援 ES modules），不再需要 `vm` 模擬 `window`。

### 2.7 資料庫層

- **死碼**：`recipe_templates`、`raw_ingredients`、`taiwan_items` 三個 store 從沒寫入過；`applyFilter` 只服務 `recipe_templates`。
- **`daily_log` 的 `source_type` 語意混亂**：推薦的自組食譜記成 `recipe_template`（根本沒有 template），多品項組合記成 `custom`，大餐可能是 `taiwan_item` 或 `custom`；`component_ids` 把餐型 id、食材 id、烹調法 id、飲料 uid 混在同一個陣列，無法反推是什麼。
- **清單型 store 整包讀改寫**：`addDailyLog` 讀整個陣列 → push → 寫回。兩個寫入同時發生（例如連點）會掉一筆。單人使用機率低，但 2.0 有 meal_plan 批次寫入（複製上週），要處理。
- **2.0 處理**：
  - DB 名稱改 `lighten2`（跟 v1 線上版同網域，名稱相同會共用同一份 IndexedDB）。
  - store：`user_profile`、`weight_log`、`daily_log`、`meal_plan`、`custom_foods`、`exercise_log`、`recipe_feedback`、`settings`。刪 `feast_reservation`（Phase 3 前保留）、`recipe_templates`、`raw_ingredients`、`taiwan_items`。
  - `daily_log` 一筆＝一餐：`{ id, log_date, slot, meal_type, source, content: MealContent（含營養快照）, totals: {kcal, protein_g, carb_g, fat_g, fiber_g}, created_at }`。`source` 只剩 `rec_accepted`／`manual`／`from_plan`／`backfill`。`is_feast`、`feast_reservation_id`、`component_ids`、`item_id`、`item_name` 全部由 `content` 取代。
  - 所有寫入走一個序列化佇列（同一個 store 的寫入排隊執行），批次寫入提供單一函式一次寫完。

### 2.8 UI 層

- innerHTML 字串拼接＋手動 escape、模組層級變數存狀態、每次整張重繪——以這個規模（6 個分頁、單人使用）**不需要引入框架**，維持原做法。
- 要改的是切檔：`tab-today.js` 964 行混了三件事；Phase 0 的三分頁選擇器會被「自己選」和「餐點日曆」共用，必須是獨立元件（`ui/meal-picker/`），不能長在 tab-today 裡。

## 3. 2.0 目標結構

### 3.1 目錄

```
js/
  core/        dates.js  slots.js（時段清單/標籤/權重/結束時間/預設值，唯一來源）  html.js  config.js
  data/        db.js（IndexedDB 存取＋寫入佇列）  catalog.js（食物資料目錄）
  engine/      nutrition.js  tdee.js  budget.js  matcher.js
               filters.js（硬性過濾）  meal-content.js（一餐內容）  pool.js  recommend.js
               plan.js（Phase 2：解析規則）  shopping.js（Phase 4）
  ui/          app.js  tab-*.js  meal-picker/（三分頁選擇器，Phase 0）
tools/         check-engine.js  check-data.js
```

### 3.2 依賴方向（只能往下依賴）

```
ui  →  engine  →  data  →  core
```
- engine 不碰 DOM；data 不碰 engine；core 不依賴任何東西。
- 「推薦引擎、統計、hero 不得讀 `picker_last_meal_type`」這類規則，改成用 import 關係就能檢查（grep engine/ 底下有沒有 import 那個 key 的存取函式）。

### 3.3 單一真相來源

| 概念 | 唯一位置 |
|---|---|
| 時段清單、中文標籤、預設權重、預設開關、時段結束時間 | `core/slots.js` |
| 型態列舉 `convenience｜delivery｜cook_quick｜cook_full` | `core/config.js` |
| 食物資料（內建＋我的品項）與正規化 | `data/catalog.js` |
| 過敏原/飲食限制/不吃清單的判斷 | `engine/filters.js` |
| 一餐營養計算、骨架驗證、快照 | `engine/meal-content.js` |

## 4. 改寫順序（取代 PRD 2.0 第 7 節的 Phase 0 前半）

Phase 0 之前多一個 **Phase −1：地基**，不加任何新功能，完成後 App 行為跟 v1 一致：

1. `core/*` 抽出，全部改 ES modules，`check-engine.js` 改 import，**31442 項照樣全過**。
2. `data/catalog.js`：資料依資料章程重整後接上，`recommend`／`item-picker` 改吃 catalog。
3. `engine/filters.js`、`engine/meal-content.js`：4 份營養計算收斂成 1 份（順便修掉 2.1、2.2）。
4. `data/db.js`：新 DB 名稱、新 store、寫入佇列、`daily_log` 新格式。

然後才是 Phase 0（三分頁選擇器）。Phase 0 的規格（round 2 第 2 節）大部分沿用，但「純函式區、Phase 1 再搬到 meal-content.js」這種過渡安排不需要了，直接寫進 `meal-content.js`。

## 6. 保留不動、但要寫進章程的既有規則

這些是 v1 多輪審核定下的，2.0 改寫時最容易被「順手簡化」掉：

- 硬性過濾「未確認就保守排除」（過敏原缺資料、飲食標籤缺資料都算未確認）。
- 飲食限制逐成分判斷（不是聯集），全素自動滿足蛋奶素。
- 餐型骨架：不對稱槽位、每個食材自己的 `serving_g`、主要槽位 0.5–2.0 縮放、免開火食安檢查。
- 現成品項統一成分模型：一餐恰好 1 main＋≤1 side＋≤1 drink＋≤1 snack、≤3 件；下午茶不需 main。
- 缺資料寫 `null` 不寫 0，加總時 null 傳染。
- 近 7 天平均/纖維缺口只算「完整記錄日」且不含今天。
- 運動跟飲食脫鉤：engine 層任何模組不得 import 運動紀錄。
