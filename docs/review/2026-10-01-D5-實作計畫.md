## 3. 要審核決定的技術問題

| # | 問題 | 建議 | 理由 |
|---|---|---|---|
| Q1 | 章程寫 `getFavoriteRefs`／`setFavoriteRefs`，計畫用 `getFavoriteRefs`／`addFavoriteRef`／`removeFavoriteRef`，不做整批 `set` | 照計畫，改章程文字 | 互斥要在同一個 transaction 讀改寫兩個 store；整批 set 會讓呼叫端拿舊清單覆蓋（我的食物和選擇器各有一份 state）。跟不吃、隱藏清單同一種單筆寫法 |
| Q2 | 常吃組的順序：資料原順序，還是標記先後 | 資料原順序：現成 → 分層 → 我的品項，各自照目前清單的原順序（不另外排序；審核 S5） | PRD 6.1「照資料原順序」；標記先後要另外記時間，清單只是 id 陣列 |
| Q3 | 常吃但被過敏原或飲食擋：留在常吃組灰在組尾，還是回原組灰著 | 留在常吃組組尾 | 使用者找得到自己標過的東西並看到原因；原組再出現一次會違反 U2「不重複」 |
| Q4 | `addDislikedIngredient` 的回傳值要不要改成 `{ disliked, favorites }` | 不改，呼叫端自己用 `removeFavoriteFrom` | 三個呼叫端與 fake-db 不用動回傳處理；`tab-today.js` 本切片沒有常吃 state，直接忽略即可 |
| Q5 | 自煮各軸：常吃排前面時，被擋的要不要也移到最後 | 本切片不動被擋的位置 | PRD 13.6 寫「被擋的仍最後」，但現況被擋的是原位灰掉，不是最後；一起改會讓自煮分頁的既有畫面也變。若審核認為要照 PRD 字面，另開一條改 |
| Q6 | 切片 5 的明細作用文字 | 一律「常吃只影響自己選的排列。」，切片 6 再依品項能不能進推薦分兩種 | 切片 5 推薦確實不受影響；先寫「今日建議會優先」會是不實文字 |
| Q7 | 標常吃後的回饋：選擇器要不要像不吃一樣有提示列＋復原 | 不要；按鈕文字直接變「取消常吃」。我的食物照不吃的做法捲到那一列並寫一行訊息 | 常吃不會讓東西消失，不需要復原；選擇器已有我的組合帶入提示與不吃提示，再多一列會擠 |

## 6. 自查（寫計畫前從要改的函式往外查過的依賴）

- `addDislikedIngredient` 的呼叫端：`tab-foods.js`、`meal-picker/index.js`、`tab-today.js`、`fake-db.mjs`、check-engine 斷言——回傳值不變（Q4），都不用改處理；transaction 多開 `settings`，`withStores` 支援多 store（`copyBuiltinToCustom` 已這樣用）。

- `splitDisliked` 的其他呼叫端：`list.js`、`tree.js`、選擇器 `splitOf`——都只加一步，不改它。
- `groupForTab` 收到的 items 變少（常吃搬走），被擋筆數「灰色的 N 項」的計算在 `productTabHtml` 裡只看傳入的組：常吃組被擋的要另外算進去，否則提示筆數會少（實作時兩個加起來）。
- `food-step.js` 的 `countShown` 決定大類組名的筆數與「0 筆不畫」：改成排除常吃後，一個子類全被搬走時那一組不畫（預期）。
- `cookTabHtml` 的呼叫端只有 `renderPanel`；`archetypeOptions` 另外只有 `index.js` `onCookClick` 用（依 id 找，不受順序影響），所以只改 `axisHtml`（審核 S10 更正）。
- `#meal-picker-panel`／`#meal-picker-drinks` 的 DOM 行不在 ui 快照（diff-recs 第 482 行），但 `flow/*` 與 `saved/*` 情境的其他容器不受影響；常吃清單在既有情境都是空的。
