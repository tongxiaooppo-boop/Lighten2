## 參考 repo（2026-09-28，來源：[collab/repo-analysis/](../collab/repo-analysis/README.md)，已對照原始碼查證）

### 平行工作線 B-3：資料匯出/匯入

參考 zaofang-local-recipes 的 `app/lib/backup.ts`：
- 備份檔帶 manifest：格式名稱、版本、App 版本、建立時間、各 store 的筆數。
- 匯入流程：先解析並驗證（格式、版本、筆數跟資料一致），給使用者看預覽（各有幾筆），確認後才在一個 transaction 裡寫入（PRD 11.6 已要求 `saved_meals`、`custom_foods`、`hidden_catalog_uids` 同一個 transaction）。
- 不學它的 ZIP：它打包 ZIP 是為了放圖片，我們品項不配圖（decisions #8），一個 JSON 檔就夠，也不必引入外部函式庫（章程 C3）。

### Phase 4：採買清單

參考 BasketMate 的 `backend/app/services/shopping_service.py` `compute_pending_items()`：
- 聚合時順便記下「這個食材來自哪幾餐」，清單上可以顯示「糙米 3 份：週一晚、週三晚…」，讓使用者看懂數量怎麼來的。
- 它沒有排除已經吃掉的餐、沒有單位與生熟重換算、沒有人數縮放；這些 PRD 5.3 都已經規定，不要照它簡化。

### 未來若要做雲端同步

參考 fatloss-plan-demo 的 `script.js` `mergeByKey`／`queueCloudSync`：本機先寫、雲端排隊、登入時以 `updatedAt` 做 last-write-wins 全量合併。
- 它刪除時不留墓碑，多裝置會靜默遺失；我們「我的品項」「我的組合」用封存（`archived`）代替刪除，比較適合這種合併方式，但 daily_log 的撤銷是硬刪除，要做同步時得重新設計。

### 已確認不採用

- fatloss-plan-demo 的「常用餐食」：同名覆蓋、一鍵直接記錄凍結的營養數字、不重新檢查過敏原——正好是「我的組合」審核時決定避開的做法（PRD 第 11 節、decisions #32），當對照用即可。
- foodwake 的營養資料：沒有交代資料授權，營養數值一律用 TFDA（章程 B2）。
- online-nutritionist、ai-diet-agent：AI 輸出沒有 schema、沒有硬性過濾；目前沒有規劃 AI 功能。
