## 0. 這次要解決什麼問題

起點是一件小事：「自己選」手動組餐 modal 裡「現成品項模式」跟「自己煮模式」該不該共存。往下挖才發現：**這個雙模式切換，本質上是「自己選」modal 自己發明了一套跟 profile 既有的 `meal_prefs`（超商/外食/自煮快煮/自煮正常煮）不一致的分類**，導致「現成品項模式」的內容（超商/台式單品多選湊一餐）看起來又跟「美饗日曆」重複。

往下再挖，變成使用者想要的東西其實更大：**每一餐都該有一個型態（超商/外食/快煮/開伙），這個型態可以是引擎自動建議帶入的，也可以是使用者自己指定的；使用者還想要能「規劃一整週」要開伙/快煮吃什麼，並依人口數產生採買清單。**

這已經不是修一個 UI 元件的量級，而是要在三個既有的資料/UI 表面（profile 的 `meal_prefs`、今日建議的自己選 modal、美饗日曆）之外，補上一層「餐點計畫」的概念。這份文件就是在定這一層該怎麼設計。

**Opus 審核後的整體判斷（也是這份文件的立場）**：不要整個程式翻新。既有的推薦引擎、硬性過濾、每日動態預算、體重趨勢校正、餐型骨架自組邏輯都是健全的、經過多輪審核定案的，2.0 只需要**加一層**，不是**換一層**。

## 1. 核心概念一：三層資料模型

| 層 | 資料位置 | 內容 | 現況 |
|---|---|---|---|
| **L1 長期預設** | `profile.meal_prefs[slot]` | 每個時段一個型態，沒有日期概念 | 已存在 |
| **L2 餐點計畫** | 新 store `meal_plan`，keyPath `id`＝`date\|slot` | 某天某時段的預約內容（一定有內容，或「這餐不吃」） | 新增（日期切換，decisions #140–#142） |
| **L3 實際紀錄** | `daily_log` | 真的吃了什麼 | Phase −1 改成新格式：一筆一餐，`meal_type`＋MealContent 快照 |

**解析規則**（整份設計最核心的一條）：

```
某天某時段的顯示內容 =
   已有 daily_log 紀錄 → 已記錄
   meal_plan 有這一筆  → 預約內容（重新解析、重跑硬性過濾；被擋寫中性原因，不默默刪）
   今天             → 推薦
   未來             → 還沒排
```

預約一定有內容（或「這餐不吃」），不做「只預約型態」，所以 `profile.meal_prefs` 照舊是唯一的型態來源。今日建議的即時運算引擎**完全不改演算法**，只多一個輸入：今天沒有紀錄的預約，當暫時紀錄（第 3 節預算規則）。

**明確不做的事**：`profile.meal_prefs` 不加平日/週末兩組設定。長期預設維持單一值，需要跟平常不一樣時，靠日期切換逐日預約。「複製上週」不做（decisions #120）。這是刻意的取捨（少一份要維護的資料結構），不是遺漏。

## 2. 核心概念二：型態不是「食材 vs 成品」的開關

使用者原始想法是「超商/外食/快煮/開伙，每種都要能選食材或成品」。逐一檢查後發現這個二分法不該讓使用者自己選：

- **超商、外食**：所謂「自組」，本質是「多個現成商品湊一餐」（沙拉+茶葉蛋+豆漿），營養值固定、不能縮放。這其實是「單品 vs 多品」，不是「食材 vs 成品」。引擎本來就有 `generateItemCombos` 在做這件事。
- **快煮、開伙**：這才是真正的食材自組（餐型骨架＋食材軸，`serving_g` 可縮放）。自煮沒有「成品」這個概念——冷凍水餃、微波調理包在資料上就是超商品項，不該在自煮型態裡重複出現。
- **快煮 vs 開伙**：不是兩個互斥的型態，是同一個型態（自煮）的不同 tier 上限（開伙 = tier 不限，快煮 = tier ≤🟡，「開伙」本身就包含「快煮」做得到的所有東西）。

**結論**：使用者看到的只有「型態」（超商｜外食｜自煮），型態決定 UI 要開哪一種選擇器（商品多選 vs 餐型骨架食材軸），不會有一個額外的「食材/成品」切換鈕讓使用者困惑——這個切換鈕正是今天模式選擇造成混亂的根源。

## 3. 核心概念三：統一的「一餐內容」格式（MealContent）

**Phase −1 一次定案**（0.1 第 4 點），實作在 `engine/meal-content.js`，推薦、自己選、今日建議的日期切換、採買清單共用（章程 C2）。

```js
MealContent = {
  meal_type: "convenience" | "delivery" | "cook_quick" | "cook_full",
  archetype_id: "protein_stir_fry" | null,        // 只有自煮才有
  method_id:    "method_stir_fry" | null,
  components: [
    { kind: "ingredient", axis: "protein",   ref: "beef_shank" },
    { kind: "ingredient", axis: "staple",    ref: "brown_rice_cooked", is_primary: true },
    { kind: "ingredient", axis: "vegetable", ref: "cabbage" },
    { kind: "product",    role: "drink",     ref: "conv_dr01", qty: 1,
      snapshot: { name, kcal, protein_g, carb_g, fat_g, fiber_g, sat_fat_g, sodium_mg } },
    { kind: "estimate",   name: "喜宴", size: "L" | null,                // 「主食＋家常菜」估算：size 是 null、份量記在 est（見下方 estimate 說明，decisions #151）
      snapshot: { kcal, protein_g, carb_g, fat_g, fiber_g, sat_fat_g, sodium_mg },
      est?: { n: 1 | 2 | 3 | 4, cats: ["veg" | "mixed" | "meat", …共 n 個], staple: "white" | "brown" | "mixed" | "noodle" | "none",
              staple_size: "S" | "M" | "L" | null, dish: "S" | "M" | "L", soup: boolean } },
    { kind: "dish",     ref: "cdish_xxx", qty: 1,                    // 我的料理（第 12.5 節）；一餐不跟 ingredient 混用
      snapshot: { name, kcal, protein_g, carb_g, fat_g, fiber_g, sat_fat_g, sodium_mg, partial } },   // 一份的營養，含用油與調味
    { kind: "food",     ref: "chicken_breast" | "fx_xxx" | "cing_xxx", qty: 2.5,   // 單品（第 13.4 節）：代換表品項或我的食材；qty 或 amount（整數 g／ml）擇一（decisions #136）
      snapshot: { name, amount, unit: "g" | "ml", kcal, protein_g, carb_g, fat_g, fiber_g, sat_fat_g, sodium_mg } },  // 1 份的量與營養（單一樣品，缺值直接是 null）
  ],
  implicit: { oil_g: 10, seasoning: "normal" | "light" | null },   // 只有自煮才有
}
```

**計畫與紀錄用同一個格式，差別只在這幾個欄位什麼時候有值**（日期切換的計畫格式，decisions #140–#142）：

計畫一筆是 `{ id, date, slot, name, content, created_at, updated_at }`，`id`＝`date|slot`，一個時段一筆。`content` 用組合的儲存格式（`toSavedContent`：`ref` 與 `qty`／`amount`，`product` 不存快照），**重新解析**後才顯示與計算；差別只有下表：

| 欄位 | 計畫（`meal_plan.content`） | 紀錄（`daily_log.content`） |
|---|---|---|
| `ingredient` 的份量 | 主要槽位保留使用者選的 `scale`；沒選是 1 倍；不存依預算縮放的倍數 | 主要槽位的元件存 `scale`（實際吃的倍數，不取整；只有主要槽位會縮放） |
| `estimate` 的 `snapshot` | 存 `{ kind, name, size, snapshot }`（有 `est` 時一併存），快照照存、不重算 | 存 |
| `product` / `dish` / `food` | `dish` 在計畫格式先預留；`product`、`food` 只存 `ref` 與 `qty`／`amount`，不存快照，之後品項被改被刪，計畫跟著重新解析（被擋或已不提供寫中性原因） | 存 `snapshot` |
| `implicit` | 存使用者選的用油/調味（沒選則存 null） | 存實際採用的克數與程度 |
| `skip` | `skip: true`＋`components: []`＝預約「這餐不吃」，解析前分流 | 沒有；「這餐沒吃」是 `source: "skipped"` 的紀錄 |
| 整餐營養合計 | 不存（顯示時由 `contentTotals` 算） | 存 `totals`（快照，食材資料之後修正也不回溯改紀錄） |

- `product` 存 `qty`；推薦生成沿用角色上限（1 主餐＋1 配菜＋1 飲料＋1 點心、最多 3 件）；手動記錄只限制角色數量上限，不要求主餐（0.1 第 6 點）；主餐上限依時段：早餐、午餐、晚餐 2，下午茶、宵夜 1，其他角色各 1（常數在 `core/config.js`，decisions #41）。
- 允許混合（自煮配一瓶超商豆漿），統一格式後不是特例。
- **隱含成分**：自煮的一餐一律帶用油（`cooking_oil`，煎 5g、炒 5g＋有蔬菜 5g、蒸與滷／燉 0；基本資料「用油習慣」設少油時減半，這就是推薦、計畫、自己選共用的預設用油；「自己選」另可選 1 或 2 茶匙）與調味程度（清淡約 300 mg／一般約 700 mg 鈉；已選醬料時預設清淡）。兩者都**不跟主要槽位縮放**。調味程度是「鹽等值的鈉估計」，不代表醬油、不帶過敏原；溫沙拉的調味只代表煎肉調味，不含沙拉醬（decisions #38）；推薦卡片與自煮合計註明「未含沙拉醬」；滷燉定食同理註明「未含滷汁拌飯」（骨架 `not_included`，章程 B7.5；滷汁的鈉高，只用這一句與烹調法的提示說明，不顯示警告，decisions #150）。細節見章程 B5.6–B5.7。
- **鈉與飽和脂肪**只用於顯示：合計時有資料的部分照加，另外註明「部分品項無資料」，不因一項缺資料就整欄變空（章程 C4.5）。其餘營養素維持 null 傳染。
- `estimate` 元件：查不到品項時的匿名估算（喜宴、朋友家、共食、自助餐），只存在這一餐裡，不存成品項。兩種：①一般外食 S／M／L（`size` 有值、沒有 `est`，熱量取常數 `ESTIMATE_SIZE_KCAL`，其餘六欄是 null＝未知，章程 C4.5）；②**主食＋家常菜**（decisions #151）：`size` 是 null，份量與組成記在 `est`（`n` 道菜各自的類別 `cats`、主食種類與大小、菜量、有沒有湯），七個營養欄位由 `data/home_dishes.json` 的類別平均與主食每 100g 算出，**快照七欄都要有數字**（不得是 null）。**估算快照在草稿、預約、暫時紀錄、「記下」全程照存、不重算**（之後常數或資料檔改了，已存的預約與紀錄不變）；沒有 `est` 的舊估算（一般外食 S／M／L）行為不變。估算一律標「估計」，過敏原與素食維持「未確認」，不能存成組合或常吃（第 11.2 節）。
- `dish` 元件（第 12.5 節）：使用者的我的料理，快照是一份的營養（含料理自己的用油與調味），`qty` 是份量倍數。只出現在自煮型態的一餐，而且這一餐不含 `ingredient` 元件；這時紀錄的 `implicit` 記 `{ oil_g: 0, seasoning: null }`（用油與調味已在快照裡，章程 C4.11；計畫與組合也可以是 null，見 12.5）。推薦引擎不產生這種元件（章程 C4.17）。
- `food` 元件（第 13.4 節）：代換表品項（`ref` 是內建食材 id 或 `fx_` 開頭）或我的食材（`cing_`）直接記錄，快照是「1 份」的量與營養（沒設一份的我的食材是 100g 或 100ml），`qty` 是份數；**或**用 `amount`（實際吃的克數或毫升，整數 1–3000），兩者恰好一個（decisions #136、#138）：合計＝快照 × `qty` 或 × `amount ÷ snapshot.amount`。三個分頁都能用，不影響 `meal_type`；不佔角色名額（另有單品上限）；不縮放、不帶隱含用油；推薦引擎不產生（章程 C4.17）。自煮的一餐沒有 `ingredient` 元件時（例如只有單品），紀錄的 `archetype_id`、`method_id` 是 null，`implicit` 記 `{ oil_g: 0, seasoning: null }`（decisions #123）。
- `qty`：`product` 與 `dish` 只能是 0.5、1、1.5、2（第 12.3 節）；`food` 是 0.5 的倍數、0.5–12（`FOOD_QTY_MAX`，decisions #122）；角色上限算元件數，不算 `qty`。

**daily_log 一筆的欄位**（Phase −1a 實作定案，decisions #33）：`{ id, log_date, slot, meal_type, source, name, content, totals, created_at }`

- `name`：記錄當下的顯示名稱，跟 `totals` 一樣是快照（品項之後改名或下架，紀錄照樣顯示當時的名稱）。
- `meal_type` 怎麼決定（原則：有明確的型態來源就用它，沒有才推導）：
  - 推薦的自組食譜：時段偏好是 `cook_quick`／`cook_full` 而且沒有退回一般推薦時，就是那個偏好；偏好是 auto 或退回時，才依食材與烹調法難度推導（都 ≤🟡 是 `cook_quick`，否則 `cook_full`）。
  - 推薦的現成品項組合：依來源（超商 `convenience`、外食與宅配餐盒 `delivery`；推薦組合不跨來源）。
  - 自己選（Phase 0 起）：**一律等於分頁的值**——超商分頁 `convenience`、外食分頁（含估算、含我的品項）`delivery`、自煮分頁是快煮/開伙子切換的值；飲料步驟不影響（decisions #47）。第 13 節起的「飲品・水果」「加點單品」兩個共用步驟也不影響；只有單品的一餐照樣是分頁的值，紀錄上不顯示型態圖示（decisions #83）。
  - 預約「記下」用預約內容裡的型態（`content.meal_type`）。
  - 型態一旦寫進紀錄就不再推導（第 11.2 節從紀錄存成組合時沿用紀錄的型態）。
- `source`：`rec_accepted`（記錄推薦，含昨天的餐裡推薦那一列的「吃了」）、`manual`（自己選）、`from_plan`（預約「記下」，或昨天的餐裡預約那一列的「吃了」）、`backfill`（補記與昨天的餐 S／M／L／「改」，日期切換使用）、`skipped`（這餐沒吃）。`skipped` 紀錄：`meal_type` null、`content` 是 `{ meal_type: null, archetype_id: null, method_id: null, components: [], implicit: null }`、`totals` 七欄全 0、`partial` 空陣列、`name` 是「這餐沒吃」；`validateDailyLog` 對它分流，其他 source 照舊至少 1 個元件。
- `implicit`：−1b 起，自煮（`cook_quick`／`cook_full`）的紀錄一定是 `{ oil_g: 非負數, seasoning: "light" | "normal" | null }`（實際採用的用油與調味，章程 C4.11）；其他型態是 `null`。自煮的一餐**沒有 `ingredient` 元件**時（只有單品、只有料理或兩者都有），`archetype_id`、`method_id` 是 null，`implicit` **恰好**是 `{ oil_g: 0, seasoning: null }`（decisions #123）；`contentTotals` 也只在有 `ingredient` 元件時才加隱含成分。
- `data/db.js` 寫入前驗證以上欄位與 `content` 的結構（元件種類含 `food`、各種元件的必填欄位、`implicit` 依型態（自煮必有用油與調味、其他是 `null`）；`totals` 的營養欄位缺值要寫 `null`，不能省略欄位）。

**預算規則**（沿用 v1 大餐預約的精神，泛化到所有計畫）：
- 今天沒有紀錄的預約，當**暫時紀錄**扣當天預算（含自煮，照使用者自己選的份量，沒選是 1 倍，不依當天配額縮放，decisions #141）；那個時段不推薦。失效的預約（任何元件被擋或已不提供）不扣，該時段改推薦，卡片寫中性原因。預約「這餐不吃」不扣熱量，配額分給其他時段。
- 暫時紀錄只影響剩餘預算、推薦與硬性過濾的全天缺口；週纖維平均、近 7 天平均、校正只看 `daily_log`（預約不是吃過的）。
- `dish`、`food` 不參與主要槽位縮放（章程 C4.6 不適用）；`dish` 在計畫格式先預留，日期切換第一版不用。
- 計畫層不存依預算縮放的倍數或熱量——未來某天的預算，存計畫的當下根本不知道；使用者自己選的主食倍數照存。

## 4. 「記住上次選過的型態」（picker_last_meal_type）

`profile.meal_prefs[slot] = "auto"`（無偏好）時，「自己選」modal 要停在哪一個型態分頁，使用者要的是「記住我上次在這個時段選了什麼」，不是固定停在某個型態。

這是一個**容易不小心長成第三層隱性偏好**的功能，設計上要守住三條硬規則：

1. **只有送出成功才寫入**，點分頁、取消、看一眼都不算。
2. **推薦引擎、統計、首頁 hero 永遠不讀它**——它只決定 modal 打開時停在哪一頁，不影響任何建議或數字。
3. **每個時段只存一個值，直接覆蓋**，不記時間、不記次數、不留歷史。

存放位置：`settings` store 的一個 key（`picker_last_meal_type: { breakfast: "convenience", ... }`），不放進 `profile`（放 profile 就等於升格成 L1 了）。

完整解析規則：
```
modal 預設型態 =
    plan[date|slot].content.meal_type  （預約內容裡的型態；沒有預約時 null）
 ?? meal_prefs[slot]（如果是有效型態值）
 ?? lastPicked[slot]（如果是有效型態值）
 ?? "convenience"                      （fallback：auto 時段多半是下午茶/宵夜，自煮選項很少，停在自煮畫面太空）
```

程式介面是 `engine/picker.js` 的 `resolveDefaultMealType({ planned, pref, lastPicked })`：engine 只收 `lastPicked` 值，不知道這個 setting key；`settings` 讀取失敗當成空物件，不擋 modal。這裡「不合法的偏好就往下找 lastPicked」跟推薦引擎「不合法的偏好退回預設偏好」刻意不同，不要合併成同一個函式。

**刻意接受的副作用**：使用者在 auto 時段每次都選超商，modal 會一直停在超商，但今日建議首頁卡片還是照樣可能推自煮——因為推薦引擎不讀這個狀態。不會因此跳出「要不要把這個時段設成超商？」之類的提示，那等於在分析使用者行為後推銷偏好，違反不評判原則。

## 5. 週規劃、人口數、採買清單

### 5.1 定位：週規劃＝泛化的大餐預約

v1 的大餐預約是「預先登記未來某天某時段要吃什麼、預扣當天預算、確認後才寫入 `daily_log`」。週菜單規劃要的是同一件事，只是也用在自煮上。**不另開一個平行的「週規劃」模組**，而是由 `meal_plan`（keyPath `id`＝`date|slot`，見第 1、3 節）承擔，入口是今日建議的日期切換——今天＋未來 6 天，每一天跟今日建議同一個風格（decisions #118、#119；原本的「餐點日曆」週格子不做）。聚餐、喜宴這類「大餐」就是一筆含 `estimate` 或外食 `product` 的計畫，沒有另外的大餐旗標。

### 5.2 情境：一人一盤，份量按人數放大

確認過使用者要的情境是「每人一盤同樣的菜，份量依人數放大」，不是「三菜一湯大家夾」的台式共食模型（後者的營養估算方式完全不同，明確排除在 2.0 之外）。家裡共食與自助餐改用外食分頁的「主食＋家常菜」估算記一個人吃的那一份（第 3 節、decisions #151）。

- `profile` 新增 `household_size`（預設 1，全域預設值）。
- `meal_plan` 條目可以逐筆覆蓋 `servings`（早餐通常只有自己吃、晚餐才是全家，不能只有一個全域值）。
- **`daily_log` 只記使用者自己那一份**，家人吃的不算進使用者的營養/熱量計算。

### 5.3 採買清單 —— 唯讀彙總視圖，不是獨立資料

採買清單本身**不存資料**，是一個純函式 `buildShoppingList(meal_plan 條目[], 日期範圍) → 清單列[]`，計畫一改就重新算。唯一需要存的狀態是「哪些品項已經打勾買了」。

**聚合邏輯**（MVP 範圍）：
```
只彙總日期範圍內、今天以後（含今天尚未記錄的時段）、meal_type 為 cook_quick 或 cook_full、已指定 content 的計畫條目
（meal_plan 沒有狀態欄位；已被 daily_log 取代的時段不算）
對每個 ingredient 元件：
  數量 = 該食材 serving_g（名目份量，不管當天縮放）× servings
  依「採買身分」（purchase_key）彙總，不是依食材資料庫的 id
用油（cooking_oil）與調味不列入（屬常備品）
```

**已知的隱藏複雜度**（MVP 都要處理，否則清單第一眼就會誤導人）。欄位名稱以章程 B4 為準，Phase 4 再補採買專用欄位：
- **熟重換生重**：米飯類主食（糙米飯、雜糧飯）是「熟重」基準，直接寫「糙米飯 1050g」會誤導使用者去買多一倍的生米。用食材的 `cooked_to_raw`（章程 B4，Phase −1b 就補上）換算。其他主食（地瓜、南瓜、毛豆仁用生重，燕麥、藜麥用乾重）本來就是買的狀態，不需要換算（decisions #35）。
- **可數食材用單位**：蛋要顯示「顆」不是克，Phase 4 補 `purchase_unit` / `g_per_unit`（來源優先用食物代換表），而且要對**總數**取整，不是逐餐取整再加總。
- **烹調法不是可以買的東西**：用 `axis` 判斷，`method` 與 `implicit` 不進清單。
- **常備品**：燕麥、醬油、鹽、油這類一次用量很少、家裡通常有的，標 `pantry: true`，清單分「要買」「家裡常備」兩區，不算進「要買」的總量。

**明確不做**（MVP 範圍之外）：超商/外食品項不進採買清單、包裝規格換算（「米一包 1.5kg」）、賣場分區排序、庫存追蹤、削皮去骨損耗、價格、自動排一週菜單、匯出分享。清單全面標示「估算」。

### 5.4 「複製上週」的兩個陷阱

1. **不能連大餐/一次性計畫一起複製**：預算會被預先佔用，複製後等於讓一次性大餐每週自動重複扣預算。規則：預設不複製含 `estimate` 元件的計畫（估算的一餐本來就是一次性事件，見第 9 節）；目的日期已經有計畫的時段預設跳過、不覆蓋；只複製到今天以後的日期。
2. **不能從「實際吃了什麼」（L3）複製**：這會讓紀錄反過來變成偏好來源，跟第 4 節「不能讓 lastPicked 變成隱性偏好」是同一類問題。只從 L2 計畫複製；上週沒排計畫就顯示「上週沒有排計畫」，並提供「用目前的長期預設（L1）預填」的選項。

## 6. PRD 核心原則風險與防呆規則

這份設計新增了兩個容易跟既有核心原則衝突的東西，明訂防呆規則：

### 6.1 不評判「超吃」/ 不製造全有全無心態

「計畫」這個概念天生帶有評判性（「有沒有照計畫吃」），這是節食心態的已知陷阱，必須從設計上堵住：

- **禁止**在任何 UI 顯示：遵循率、「偏離計畫」、「未完成」、紅色未打勾標記、連續照計畫天數、計畫 vs 實際的熱量差比較。
- 實際紀錄（L3）跟計畫（L2）不一樣時，計畫條目**默默**被取代，畫面只顯示實際吃的東西，不提示「跟計畫不同」。
- 過去日期裡沒被記錄的計畫條目，直接不顯示或灰掉，不顯示「漏掉」。
- 隔天的「昨天的餐」卡片用字中性：標題「昨天的餐」，不寫漏記、忘了記、沒記到、還沒記、未完成，不用紅色、不統計連續天數；預設收合成一行「昨天的餐（N 餐）」，只列昨天（前天以前走補記）；每列的「這餐沒吃」與「吃了」分開、不同色，每列另有「不確定」（不寫紀錄，只收起）；整張卡「先不用」收起。
- `daily_log.meal_type` 是新增的高風險欄位——有了它就能統計「這週外食 5 次」。**任何 UI 不得依 meal_type 做頻率統計並搭配評價性文字或顏色**，不得出現「外食比較多喔」「多自己煮吧」。只能用在解析規則、採買清單、中性顯示（例如一個圖示）。
- 商品挑選清單**禁止**依熱量高低排序或用顏色區分熱量高低，維持資料原始順序。
- 加飲料步驟不做糖量警告，不預設選「無糖」。

### 6.2 運動與飲食脫鉤

- 計畫層與採買清單**永遠不計算、不顯示未來日期的熱量預算**；未來日子只顯示已排的合計熱量、不顯示目標。不依預算推算份量：自煮照使用者選的份量，沒選是 1 倍（不去推算「那天可能有運動」而調整份量）。
- `meal_plan`、`picker_last_meal_type` 等新資料結構**不得有任何欄位引用 `exercise_log` 或運動計畫**，也不做「今天有運動，預設停在高蛋白自煮」之類的聯動。

### 6.3 既有自組食譜原則（三輪審核定案，不可退化）

- 計畫內容（`MealContent`）裡的 `ingredient` 元件，必須落在對應餐型骨架該軸的 `allow` 清單內，數量符合軸上限（`COMPOSE_MAX`）——計畫層不能變成繞過骨架、自由湊食材的後門。（例外：使用者自己定義的「我的料理」是另一種元件 `dish`，豁免本節第 1、2 點，第 3 點照樣適用；不進推薦，見第 12.5 節。單品 `food` 同樣豁免第 1、2 點：只用於手動記錄、推薦不產生、營養用快照不縮放、單品不宣告烹調方式；第 3 點照樣適用，見第 13.4 節。）
- 免開火（`sm_no_cook`）的食安檢查，在計畫「存檔當下」跟「顯示當下」都要各跑一次（只檢查骨架的 `ingredient` 元件，`food` 不宣告烹調方式，不套用）。
- 計畫條目在**顯示時**要重新跑 `passesHardFilters`（過敏原/飲食限制/不吃清單），因為規劃完之後使用者可能更新了設定，導致原本合法的計畫變成不合法——被擋下要顯示中性提示，不能默默刪掉。
- 超商/外食的「多品組合」繼續套用既有的品項角色上限，並依角色分區/排序顯示（主餐、配菜在前，飲料獨立一步），避免重現「前十幾張卡片全是飲料」的笛卡爾積式混亂。Phase 0 的具體做法：內建品項先依角色分區（主餐 → 配菜 → 點心），區內依 `category` 分組，組與組內都照資料原順序（不按熱量排）；「我的品項」例外，整組放在分頁最後、不進角色分區；被過敏原或飲食限制擋的品項排在組內最後、灰階並寫原因。**使用者標「不吃」的品項**（第 13 節起）移到分頁或步驟的最下方一組，上面分隔線、灰階、預設收合、組名帶筆數，可以直接取消不吃；又不吃又被過敏原擋的留在原位（decisions #80）。

## 8. 已知限制與明確排除

- **不支援台式共食（三菜一湯大家夾）**的份量/營養模型，只支援「一人一盤，份量按人數等比放大」。家裡的共食與自助餐**用外食的「直接估算」記錄**：一般 S／M／L，或「主食＋N 道家常菜」（N＝1–4，每道選素菜／菜肉／純肉，湯另開關，decisions #151）。後者的數字來自 `data/home_dishes.json`（只供估算算出七個營養欄位，不供逐道選擇、不進推薦，章程 C4.17 ③）；#148「不建菜色資料」那半句由 #151 取代。
- **採買清單是估算**，主食份量用名目份量、不預測當天縮放倍數；不處理包裝規格、庫存、損耗、保存期限、價格。
- **`profile.meal_prefs` 不分平日/週末**，需要規律性差異時靠週規劃逐日設定＋複製上週。
- **`picker_last_meal_type` 刻意不影響推薦引擎**，modal 記得的型態跟首頁建議可能不同步，這是刻意的設計，不是 bug。
- **不做內建品項的修補/覆蓋層**：不想要一個內建超商/外食品項就標「不吃」（第 13 節起取代「隱藏」按鈕），想「改」就複製成自己的版本，不會出現「內建資料 + 使用者差異」的合併邏輯。
- **不加第五種型態**：外食型態的定義擴大成「不是自己煮、也不是超商——別人做的」，涵蓋喜宴/朋友家等查不到品項時的匿名估算，不會為了這些情境另開型態。
- **圖片政策**：品項卡片全面不配圖（含使用者自建品項），只有今日建議推薦卡片保留 5 張既有的時段插畫（早/午/下午茶/晚/宵夜）當背景墊底，不是逐品項配圖。

## 9. 美饗日曆的收斂（第三輪定案）

美饗日曆不維持獨立的品項策展身分，它的功能被「超商」「外食」型態分頁取代，**在 Phase −1a 直接移除**（decisions #16；沒有使用者資料要遷移，也沒有人在日常使用，不需要過渡期）。它原有的 4 項職責去向：

| 美饗日曆原有功能 | 新歸屬 | 什麼時候有 |
|---|---|---|
| S/M/L 匿名估算（喜宴、吃到飽、朋友家） | `estimate` 元件，外食分頁最上方「找不到？直接估算」卡片，只存在這一餐裡；S/M/L 熱量常數（400／700／1200 kcal）已在 −1a 放進 `core/config.js` 的 `ESTIMATE_SIZE_KCAL`；另加「主食＋家常菜」類型（共食、自助餐，七個營養欄位都有數字，decisions #151） | Phase 0；家常菜類型 2026-10 |
| 建立具名的自訂食物（v1 唯一的新增入口，靠有沒有填名稱猜意圖） | 拆成兩個明確動作：「只估這一次」（estimate）和「存成我的品項」（快速新增，含過敏原欄位）；猜意圖的做法廢除 | Phase 0 |
| 預約未來／直接記錄過去兩種模式（v1 另有「時段已過不能預約」檢查，v2 沒有餐時，不沿用） | 預約未來：今日建議的日期切換（寫 `meal_plan`；v2 沒有餐時，不做時段結束時間檢查）；回填過去：「本週總覽」的「補記過去的一餐」（日期選擇器，過去 7 天，decisions #120） | 日期切換；補記 |
| 預約狀態 reserved→confirmed→cancelled | `meal_plan` 不設狀態欄位。「確認」＝今天按「記下」，或隔天在「昨天的餐」確認，寫一筆 `daily_log`（`from_plan`）；「取消」＝刪掉計畫；過期沒記錄的預約直接失效，不提醒、不標「未完成」 | Phase 2 |
| 撤銷一餐（`undoDailyLog` 寫在 feast.js，今日建議的撤銷按鈕呼叫它） | 搬進 `data/db.js` | Phase −1a |
| 今日建議把「今天的預約」當暫時紀錄算預算 | 刪除；Phase 2 起由 `meal_plan` 的固定熱量計畫取代 | Phase −1a 刪、Phase 2 取代 |

接受的空窗（沒有人在日常使用）：
- Phase −1a 到 Phase 0：不能新增自訂食物、不能記錄查不到的一餐。
- Phase −1a 到今日建議的日期切換：沒有「預約未來」的入口；到「補記過去的一餐」之前沒有「回填過去日期」的入口（decisions #120）。

（「複製上週」不做，decisions #120：有我的組合與日期切換的預選就夠了。以下是原本的規則，留作紀錄：）「複製上週」**跳過含有 `estimate` 元件的計畫**——估算的一餐本來就是一次性事件（喜宴、聚餐），不需要另外的大餐或「一次性」欄位。

**對核心原則的提醒**：美饗日曆原本讓「先把大餐排進去」變成一件光明正大、被系統鼓勵的事，這對「不評判超吃」是有正面作用的使用入口。身分收斂之後，這層意義不能跟著消失——日期切換裡還沒預選的餐、外食分頁的估算卡片，文案要延續這個精神（例如「有聚餐？先排進來，其他餐會自動幫你調整」）。

## 10. 使用者自建品項（「我的品項」，第三輪新增）

使用者要能自己新增/編輯/刪除超商或外食品項（例如超商出的新品、剛發現的健康餐廳），不用等開發端更新 `convenience_items.json`/`taiwan_items.json`。

### 10.1 資料模型：擴充 `custom_foods`，不開新 store

沿用 `custom_foods` 這個 store（一筆一個 key），程式碼裡概念稱「我的品項」。沒有舊資料，所有欄位一開始就照下面的格式（decisions #9）。

```js
{
  id: "custom_xxx",
  name,                                         // 必填
  channel: "convenience" | "delivery",          // 必填（從目前分頁自動帶入）
  role: "main" | "side" | "snack" | "drink",    // 必填，預設依時段（早午晚＝main，下午茶/宵夜＝snack）
  valid_slots: [...],                           // 必填，依 role 推預設，且一定包含新增當下的時段
  kcal,                                         // 必填，正數（飲料可以是 0：無糖茶、氣泡水）
  protein_g, carb_g, fat_g, fiber_g, sat_fat_g, sodium_mg,   // 選填，未填為 null
  vendor, category, note,                       // 選填
  allergen_tags: null | [],                     // 必有此欄；null=未確認（預設）／[]=確認不含／[..]=含這些
  vegan: false, lacto_ovo: false,
  copied_from: null | "<內建品項 uid>",           // catalog 的 uid（台式外食帶 tw_ 前綴），跟 hidden_catalog_uids 同一個命名空間；只能由「複製成我的版本」寫入
  archived: false,                              // 軟刪除，只提供這個，不做硬刪除
  created_at, updated_at,
}
```
不存圖片欄位。`data/db.js` 提供 `updateCustomFood(id, patch)`。寫入驗證見章程 B8。

### 10.2 內建品項的「增減」：隱藏＋複製，不做修補層

- **隱藏**：`settings.hidden_catalog_uids`，選擇器和推薦引擎都要濾掉。這是使用者主動操作，推薦引擎可以讀它（跟 `picker_last_meal_type` 不同，那是被動累積、引擎不可讀）。~~跟「不吃食材」的語意不同……不要合併成同一個機制。~~ **2026-09-30 修正（decisions #76，推翻本條「不要合併」）**：畫面上只剩「不吃」；隱藏退為「複製成我的版本」時自動寫入的內部機制（避免同一樣東西兩筆）。前提改變：使用者要的是「一個地方管自己吃不吃」，而 B-1a 上線後兩個按鈕在推薦端效果相同、在畫面上讓人分不清。既有的隱藏資料不轉換，在「我的食物」的「已隱藏」組列出、可以取消、不能新增（第 13.5 節）。
- **B-1a 的入口**（[B-1a 實作計畫](review/2026-09-29-B1a-實作計畫.md)）：「自己選」超商／外食分頁的「已選」段（品項清單上方）與飲料步驟裡，已選的內建品項有「隱藏」「複製成我的版本」。隱藏後提示列有「復原」；基本資料的「我的品項」區塊列出已隱藏的內建品項，可以取消隱藏（有從它複製的我的品項時中性提示）。被擋或名額已滿、選不到的內建品項，B-1a 不能隱藏或複製（等 B-1b 的食物資料頁；也避免在灰色卡片旁暗示「複製後改答案就能選」，章程 C4.1）。推薦引擎在 `planToday` 裡濾掉含隱藏品項的現成組合。**第 13 節修正**：選擇器的「隱藏」按鈕拿掉，改成「不吃」；被擋的內建品項可以在「我的食物」的明細裡複製（按鈕不在被擋原因旁邊，decisions #84）。
- **複製成我的版本**：以內建品項為底建立一筆自建品項（`copied_from: seedUid`），同時自動隱藏原本的品項（一個 transaction，全有全無）。之後開發端更新內建資料，使用者複製過的版本不會跟著動——刻意接受的落差，UI 用小字標示「從內建品項複製」，開發端補正內建營養資料時要知道這件事對已複製的使用者沒有效果。

### 10.3 填寫負擔：延續 `custom_foods` 現有的容錯精神

快速新增（在選擇器裡）只要**名稱＋熱量＋角色晶片**（角色有預設值：早午晚餐預設主餐，下午茶/宵夜預設點心；`channel` 從目前分頁自動帶入），其餘欄位收在「更多（選填）」。`valid_slots` 快速新增時務必包含目前這個時段，否則新增完在這個時段看不到它。

Phase 0 的表單欄位（decisions #48）：
- 必填區：名稱、熱量、角色晶片（主餐／配菜／點心／飲料）、過敏原（未確認〔預設〕／確認不含／含：勾選）。
- 飲食宣告「這個品項是：全素／蛋奶素／都不是（預設）」：使用者有設飲食限制時放在必填區，沒設時放在「更多」。
- 「更多（選填）」：蛋白質、碳水、脂肪、纖維、飽和脂肪、鈉（沒填是 null），以及上面的飲食宣告。
- `valid_slots` 依角色預設：主餐＝早午晚宵夜、配菜＝全部、點心＝下午茶與宵夜、飲料＝全部，再加上目前時段。
- **送出前預告**：以使用者目前的過敏原／飲食設定，這筆照現在填的會被擋時，用中性文字寫出是哪個設定擋住（例：「你設了過敏原『蛋』，過敏原未確認的品項不能選」），**不寫「改成確認不含就能選」這類引導**（章程 C4.1）。
- 宣告全素卻勾了含蛋、乳製品、魚、甲殼類、軟體動物（或蛋奶素卻含魚、甲殼類、軟體動物）時，中性提示矛盾，不擋存檔；我的品項只受章程 B8 驗證，B6.8 不適用（章程 B1）。「全素但過敏原未確認」不提示（未確認是預設值）。

### 10.4 一併修掉的既有漏洞：自訂食物完全不做過敏原檢查

v1 的 `passesHardFilters` 對自訂食物完全跳過過敏原檢查（`!item.is_custom` 例外），跟「未確認就保守排除」相反。**Phase −1b** 拿掉例外並在 `db.js` 加寫入驗證（`allergen_tags` 欄位必有，預設 null）；**Phase 0** 的快速新增表單帶過敏原欄位（未確認／確認不含／含…，預設未確認）（decisions #17、#27）。Phase 0 起有新增入口但還沒有編輯畫面：建立時就被擋的情況由「送出前預告」處理；**建立之後才設過敏原（或之後才改成素食、當初沒宣告）的人，舊品項會變灰且到 B-1a 之前無處可改，只能重建一筆**——刻意接受，灰階照常寫原因（decisions #49）。`allergen_tags === null` 一律當未確認；只有使用者設過敏原/飲食限制時才會擋。B-1a 起，被擋的我的品項旁有「補填」按鈕（選擇器與基本資料的我的品項區塊都有），點進去就是編輯畫面，存完在選擇器裡重新判斷能不能選。**「補填」只給「成分未確認」「飲食限制未確認」**；「含過敏原」「不吃」只寫原因，不放補填（不引導改答案，章程 C4.1）。

### 10.5 要不要進今日建議候選池：分兩階段

- **B-1a（先做）**：只能在「自己選」（含今日建議的日期切換的預選）手動選。
- **B-2（之後）**：資料填得夠完整（`kcal`/`protein_g` 都有，過敏原已確認過）就依 `channel` 自動併入推薦候選池，不設每筆的「允許推薦」開關（不想被推薦已經有「不吃」清單可用）。管理畫面用中性語氣顯示每筆狀態（例如「補上蛋白質就會出現在建議裡」），不催促。

### 10.6 UI 位置

- **選擇器裡快速新增**：超商/外食分頁最後一組「我的品項」（預設收合）下方放「＋新增到我的超商/外食品項」。新增完：能選且同角色還有名額就直接選中（飲料選進飲料步驟）；被擋或名額已滿就不選中，提示原因。
- **管理畫面**（**第 13 節起搬到「我的食物」主分頁**，各子分頁的「我的品項」組；以下內容照舊）：~~放在「基本資料」分頁的一個區塊，不新開頂層分頁，~~內容含列表（可搜尋，新到舊）、新增、編輯、補填、封存/還原、已隱藏的內建品項清單（可取消隱藏）。每一筆用中性文字標狀態：「從內建複製」「以你目前的設定不能選：<原因>」「已封存」；複製來的在編輯時唯讀並列「內建目前的數值」（decisions #61）。從這裡新增時沒有「目前時段」，`valid_slots` 預設用角色推的時段。封存複製品時，若原品項仍隱藏，中性提示可以取消隱藏。這個畫面擴大成第 12.2 節的「食物資料」查詢，查詢與管理是同一個畫面。

## 11. 我的組合（2026-09-28 新增，依獨立審核修訂）

使用者常吃的幾套固定組合（例如「平日早餐：飯糰＋茶葉蛋＋豆漿」、「雞胸肉糙米快炒」），存起來之後可以直接引用，不必每次從頭選（decisions #31、#32；審核紀錄 [2026-09-28-my-combos](../collab/opus-review-log/2026-09-28-my-combos.md)）。

**命名**：畫面上叫「我的組合」；程式與資料一律叫 `saved_meals`／`SavedMeal`，避免跟推薦引擎既有的「多品組合」（`generateItemCombos`）混淆。

**定位**：組合是**單餐的範本**，不是週模板（不推翻 decisions #4）；不進 L1/L2 解析規則，也不會自動填進任何計畫或紀錄。

### 11.1 資料模型：新 store `saved_meals`

```js
{
  id: "saved_xxx",
  name: "平日早餐",                  // 必填；建立時自動帶「品項名稱以＋連接」，使用者可改；可重複（以 id 區分）
  content: MealContent,             // 見下表
  archived: false,                  // 刪除＝封存，不做硬刪除
  created_at, updated_at,
}
```

`content` 是 MealContent（第 3 節）的「範本形式」：

| 欄位 | 組合 | 跟計畫的差別 |
|---|---|---|
| `meal_type` | 存來源那一餐的型態（建立時就知道，不另外推算） | 相同 |
| `archetype_id`、`method_id` | 照 MealContent 保留（引用時依目前骨架重新驗證，11.3 規則 4）；自煮沒有 `ingredient` 元件時兩個都是 null | 相同 |
| `ingredient` | 只存 `axis`、`ref`、`is_primary`；份量不存，帶入選擇器時主要槽位從 1 倍開始，使用者自己拉滑桿（decisions #124） | 相同 |
| `product` | 只存 `ref`、`qty`，**不存 `role`、不存 `snapshot`**；角色與營養每次即時從 catalog（含我的品項）讀 | 計畫存快照；組合是長期範本，內建資料修正後應該跟著更新 |
| `estimate` | **不允許** | 估算的一餐是一次性事件（第 9 節） |
| `dish` | 只存 `ref`、`qty`，不存 `snapshot`；營養每次即時從我的料理算 | 同 `product` 的理由（第 12.6 節） |
| `food` | 只存 `ref` 與 `qty` 或 `amount`（擇一，原樣保存，不補預設），不存 `snapshot`；營養每次即時從分層資料或我的食材讀 | 同 `product` 的理由（第 13.4 節）；引用時分層品項下架、衛福部來源的我的食材被移除（不吃）或自填的已刪除，歸「已不提供」（衛福部來源再加回就恢復，id 固定）；`qty` 記法但那項我的食材沒有設一份 → 擋下「沒有設一份，請改用克數」；一份幾克改了，組合的「N 份」跟著變（數值引用當下讀） |
| `implicit` | 入口 1（「自己選」送出）：使用者在選擇器裡主動改過用油／調味才存值，否則 `null`；入口 2（從紀錄存）：一律 `null`。`null`＝引用時套用當下的預設用油與調味 | 相同 |
| 營養合計 | 不存 | 相同 |

- **轉換只有兩個函式，都在 `engine/meal-content.js`**（章程 C2），兩個建立入口依序呼叫：
  1. `toSavedContent(mealContent, { keepImplicit })`：純結構轉換，去掉快照、`role`、縮放倍數與合計。`keepImplicit` 為 true 時保留 `implicit`，否則設 `null`。入口 1 傳入「使用者是否在選擇器裡改過用油／調味」；入口 2 一律傳 false（紀錄裡分不出當時是預設還是使用者指定）。
  2. `remapSavedRefs(savedContent, catalog, ctx)`（`ctx = { hidden, customs, slot, profile }`，`customs` 是轉好的我的品項、含已封存的；切片 8、9 再往 `ctx` 加 `customIngredients`、`customDishes`、`tfdaLookup`，要分得出「衛福部查詢檔載入失敗」與「查不到」，decisions #125）：套用 11.3 解析規則 1–2（隱藏且有複製版本 → 換成複製版本；查不到或隱藏且無複製版本 → 移除），回傳 `{ content, dropped }`。`dropped` 非空時，存檔前用中性文字列出「以下品項已不提供，不會存進組合」。`resolveSavedMeal` 的規則 1–2 也呼叫同一個函式。
- 單品 `food` 的解析讀 `catalog.foodTree`（分層資料掛在 catalog 物件上，decisions #92）與我的食材，**不為它另加參數**。
- **驗證分兩層**（章程 C1）：
  - `data/db.js` 寫入時只做結構驗證：名稱非空、至少 1 個元件、沒有 `estimate`、`product` 有 `ref` 與 `qty` 且沒有 `snapshot`／`role`、`dish` 有 `ref` 與 `qty`、`food` 有 `ref` 與 `qty` 或 `amount`（恰好一個），兩者都沒有 `snapshot`。
  - 語意驗證（角色數量上限、骨架 `allow` 與軸上限、免開火食安）由 ui 在寫入前呼叫 engine 完成；用手動記錄規則（章程 C4.8），**不檢查時段**。
- 真正記錄時，照第 3 節寫進 `daily_log`，那一刻才存商品快照與 `totals`。

### 11.2 建立

兩個入口，都是使用者明確操作：
1. 「自己選」送出時可勾「存成組合」，名稱欄預先填好自動名稱。這一餐有估算時不能勾（「估算的一餐不能存成組合」）；勾了送出時紀錄與組合在同一個 transaction 寫入，全有全無（decisions #124、#125）。
   - 自動名稱：品名以「＋」串接、不寫量（自煮＝餐型名＋食材名；商品、單品＝品名），使用者可改（decisions #124）。
2. 已記錄的一餐可以「存成組合」：在今日建議**今天**已記錄的卡片，「撤銷」旁邊（過去日期的紀錄等補記過去的一餐時再想，decisions #124）。**含 `estimate` 元件的那一餐不提供這個選項**。已下架或已隱藏的品項依 11.1 的 `remapSavedRefs` 處理（有複製版本就換成它，沒有才不存）。之後語意驗證若不通過（例如骨架已經改過），用中性文字列出原因、不存檔。

入口 2 是從 L3（實際紀錄）建立範本。第 5.4 節禁止「從 L3 複製成計畫」，理由是不能讓紀錄被動變成偏好來源；這裡是使用者對單一一餐的明確操作，不是系統依紀錄推導，所以不衝突。比照第 4 節的精神：**不得依紀錄頻率提示「你常吃這個，要存成組合嗎？」**，也不記使用次數。

### 11.3 引用

**解析只有一個函式**：`engine/meal-content.js` 的 `resolveSavedMeal(saved, catalog, ctx)`（`ctx` 同 11.1；料理、我的食材的欄位到切片 8、9 再加），回傳「可用元件」「被擋元件與原因」「已不提供的元件」。所有引用都經過它（章程 C4.16）。規則是**元件級**：

1. `ref` 查不到（已下架，或我的品項、我的料理已封存；`food` 引用的分層品項下架或我的食材已封存）→ 歸「已不提供」；料理的食材查不到時整道歸「已不提供」，衛福部查詢檔載入失敗不算查不到（12.2、12.5）。
2. `ref` 在 `hidden_catalog_uids` 裡：若有未封存的我的品項 `copied_from === ref`，改用那一筆（使用者「複製成我的版本」後組合自動跟上）；否則歸「已不提供」。隱藏的語意是「已不存在或買不到」（10.2），比照下架處理，不是灰階阻擋。規則 1–2 由 `remapSavedRefs` 實作（11.1），建立與引用共用。
3. 硬性過濾（過敏原/飲食限制/不吃清單）沒過 → 歸「被擋」，附原因。
4. 自煮部分依**目前的**骨架重新驗證（骨架或食材資料可能改過）：`archetype_id` 已不存在 → 所有自煮元件歸「被擋」（原因「這個餐型已不提供」）；食材不在該軸 `allow` → 該元件歸「被擋」（「這個餐型目前不提供這個食材」）；超過軸上限 → 依 `components` 順序，後面超出的歸「被擋」；違反免開火食安（章程 C4.3，引用等同顯示，要再檢查一次）→ 需要加熱的食材歸「被擋」（「免開火不能搭配需要加熱的食材」）。烹調法不是元件：不在目前骨架的 `methods` 裡時，帶入不預選烹調法並寫「烹調法「X」目前不在這個餐型，請重選」；快煮的難度限制不在解析時擋，帶入後由選擇器的送出規則擋（decisions #125）。只有 `ingredient` 元件才跑規則 4，沒有食材的自煮組合不看 `archetype_id`。
5. 角色一律用 catalog 當下的 `role`；超過角色數量上限時，依 `components` 順序，後面超出的元件歸「被擋」。主餐上限：選擇器帶入用當下的時段（解析與送出一致）；管理區塊、存檔前驗證、編輯模式沒有時段，主餐上限 2（decisions #63、#125）。單品 `food` 沒有角色，改比單品上限（`FOOD_MAX_PER_MEAL`），超出的依順序歸「被擋」；規則 4 的骨架重新驗證只檢查 `ingredient` 元件，`food` 略過。
6. `valid_slots` 是瀏覽用的過濾，**不是安全規則**：組合帶入的元件不受時段限制；骨架驗證也不檢查時段。

畫面：
- 「自己選」三分頁上方一列「我的組合」，**列出全部未封存的組合**（不分型態），每張顯示名稱、型態文字（超商／外食／快煮／開伙）、名稱下小字列內容與熱量（＝帶入後選擇器摘要的熱量，自煮主要槽位 1 倍）（decisions #124）。有元件不能用時，卡片加一行中性文字「有 N 項目前不能用：原因」。
- 只要還有可用元件，卡片就可以點；「可用元件」是 0 個時整張灰階、**不能點**，卡片上的中性文字說明原因。點選後切到組合的型態分頁（自煮含快煮/開伙子切換），把可用元件帶入選擇器（取代那個分頁原本的選取、飲料與單品；其他分頁的選取保留）；被擋與已不提供的元件不預選。帶入的品項不在這個分頁目前的清單裡（時段、管道改過）時插進清單並標示；帶入的餐型不在這個時段也照樣列出可以取消。已帶入的元件在選擇器裡一律顯示（即使不在這個時段的 `valid_slots`），可以取消。確認後才記錄，不做一鍵直接記錄。
- 今日建議的日期切換（未來日期的預選；跟日期切換一起做，decisions #124）：引用組合一律**帶入三分頁編輯器**，不直接填入計畫。未來日期的組合卡片**不做預算縮放**：只顯示商品的固定熱量，自煮部分照 1 倍（帶入後主要槽位從 1 倍開始，使用者可自己改，改了的倍數存進計畫；第 6.2 節：不計算未來日期的預算）。填進計畫時用計畫格式（第 3 節）：只存 `ref` 與 `qty`／`amount`，`estimate` 存快照，不補商品快照。
- 組合的排列：使用者建立的順序，不依熱量排序、不上色（第 6.1 節）。

### 11.4 推薦

**推薦引擎、統計、hero 都不讀 `saved_meals`**，組合只供手動引用（章程 C4.16）。之後若要讓組合進推薦候選，屬 C3 需審核的變更，且只能放符合推薦生成規則（章程 C4.7、低碳）的組合。

### 11.5 管理

「我的食物」主分頁最上方（搜尋框下、子分頁上）收合一行「我的組合（N）」（第 13 節起；原定「基本資料」分頁，decisions #124）：列表、改名、**編輯內容**（用同一個選擇器直接編輯、存回同一筆，見第 12.6 節）、刪除（封存，不跳確認，有「復原」）/還原（區塊最下方「已刪除（N）」）；封存的組合不出現在選擇器。改名、編輯或刪除不影響已記錄的餐（紀錄有自己的快照）與已排的計畫（計畫有自己的內容）。

### 11.6 匯出匯入（平行工作線 B-3）

組合引用我的品項的 id。匯入時 `saved_meals`、`custom_foods`、`hidden_catalog_uids` 在同一個 IndexedDB transaction 寫入；若匯入會重新產生我的品項 id，要同步改寫組合裡的 `ref`。第 12 節新增的 `custom_ingredients`、`custom_dishes` 也在同一個 transaction，id 改寫要連動（我的料理引用我的食材、組合引用我的料理）。（以上是**合併匯入**的規則，分享包上線時才適用。）

**B-3 做的是完整備份與還原（取代）**（decisions #71；實作計畫 [B-3](review/2026-09-29-B3-實作計畫.md)）：

- **位置**：基本資料分頁最下面的「資料備份」區塊。說明一句「資料只存在這台裝置的瀏覽器裡，換手機或清除瀏覽器資料前請先匯出」。
- **匯出**：下載 `lighten2-backup-YYYY-MM-DD.json`，內容是所有 store 的全部資料（不含內建資料）。匯出當下對「JSON 來回一次」的結果跑還原時同一套驗證；有還原不了的紀錄（例：驗證器變嚴之前寫入的舊格式）就在下載的同時用中性文字列出類別與日期。
- **還原＝取代，不是合併，也不是同步**：一個 IndexedDB transaction 清空全部 store 後寫入檔案內容（全有全無），id 原樣保留，所以不需要上面的 id 改寫。完成後通知其他開著的 App 分頁重新載入，自己也重新載入。
  - 預覽：匯出時間；每一類檔案與目前的筆數、最後一筆日期；還原後變成 0 筆的類別；目前有 `created_at` 晚於檔案匯出時間的紀錄時寫「目前有 M 月 D 日之後新增的紀錄，還原後不會保留」。
  - 目前資料不是空的（有基本資料，或飲食、體重、運動紀錄、我的品項、我的組合任一類有資料）時，要先按過「先匯出目前的資料」或勾「目前的資料不需要保留」，「還原」才能按（使用者 2026-09-29 決定）。
  - 驗證失敗（格式不對、版本較新、任一筆不合法、基本資料讓目標計算丟錯）時不寫入任何東西，列出前 5 個問題。
- **檔案格式**：

```js
{
  format: "lighten2-backup",
  schema_version: 1,                 // db.js 的 BACKUP_SCHEMA_VERSION；新增 store、settings key 或改變區塊結構就 +1（跟 DB_VERSION 分開計）；新增 MealContent 元件種類（如 `food`）不升版（decisions #123，比照 #88）
  exported_at, app_version,          // 只供人看；缺也放行
  manifest: { <store>: 筆數, ... },   // 必須跟 sections 的實際筆數一致
  sections: {
    system: { user_profile: {...} | null, settings: [{ id, value }], recipe_feedback: [{ id, value }] },
    logs: { daily_log: [...], weight_log: [...], exercise_log: [...] },
    custom_foods: [...],
    saved_meals: [...],              // v3（工作線 C）起
  },
}
```

  - 檔案只描述含哪些區塊，不描述匯入語意；日後的分享包是同一種檔案、只含食物類區塊，由匯入端提供合併（見 `docs/日後討論.md`）。每筆紀錄都帶自己的 `id`，合併時存成 `origin_id` 去重與追溯。
  - 版本：檔案版本較新 → 拒絕；較舊 → 逐版升級，舊檔沒有的區塊當成空的；同版本出現不認得的區塊或 settings key → 拒絕。`tools/fixtures/backup-v<N>.json` 每一版凍結一份，之後的版本都要讀得了。
  - store 與 settings key 的清單由 db.js 的 `STORE`、`BACKUP_SECTIONS`、`SETTING_KEYS` 決定，check-engine 斷言每個 store 都在某個區塊裡；之後新增 store 或 key 的工作線要一起補匯出（第 7 節各列）。

**`user_profile` 欄位**（由基本資料表單寫入；還原時由 `validateProfile` 驗型別）：

| 欄位 | 型別 | 還原時 |
|---|---|---|
| `age`、`height_cm`、`weight_kg` | 有限正數 | 必填 |
| `body_fat_pct` | 有限正數或 null | 可缺 |
| `gender`、`activity_mode`、`goal_mode`、`diet_restriction`、`oil_habit` | 字串 | 可缺；選項值不在 db.js 另列，由 engine 的實際行為決定：性別認不得 `calculateTargets` 會丟錯 → 擋下；目標、活動量認不得會退回維持、久坐；飲食限制認不得會往保守方向（推薦變空）——後兩種只會出現在手改過的檔案，不擋 |
| `low_carb` | 布林 | 可缺 |
| `allergens` | 字串或字串陣列（舊資料是自由文字） | 可缺 |
| `disliked_ingredients` | 陣列，每項 `key` 是字串（`type` 不檢查，decisions #40） | 可缺 |
| `meal_prefs`、`enabled_slots` | 物件（值可以是 `"off"`） | 可缺 |
| `activity_value`、`protein_g_per_kg`、`fat_pct`、`fiber_target_g` | 數字（表單沒有，engine 會讀） | 可缺 |

平常按「計算」存基本資料時還沒有寫入驗證，另排（`docs/日後討論.md`）。

- **衛福部全表的查詢檔**：由 `tools/build-tfda-lookup.js` 從 `data/reference/tfda-2025-update1.json`、`tfda_tags.json`（過敏原與素食標註）、`tfda_groups.json`（放在哪一組）產生 `data/tfda_lookup.json`（2213 筆全收；每筆整合編號、樣品名稱、俗名、衛福部分類、內容物描述、組（代換表大類或 other）、是否液體、狀態、每 100g 七個營養欄位、過敏原、素食、`composite`、`listed`；代換表分層已用的樣品 `listed: false`，搜尋不列；約 980 KB，壓縮後約 100 KB；decisions #134、#135）。進位用 `tools/lib/ingredient-values.js` 同一份算法；生熟狀態（12.4 的 `state`）也由 tools 從「內容物描述」推好寫進查詢檔；check-data 逐筆比對 2213 筆必須跟參考資料算出來的值完全相等。前端照讀，不做任何換算或解析（章程 C2）。
  - **載入時機**：跟其他種子資料一樣帶版本字串（`catalog.js` 的 `?v=`，章程 C1.6），**不跟 catalog 一起載入**，在用到衛福部食材之前才載入：食物資料頁、料理編輯器、打開選擇器（要列出料理熱量）、解析組合、建立計畫快照、寫入我的食材或料理前的驗證。
  - **載入失敗是錯誤狀態，不是「查不到」**：跟料理有關的動作（記錄含料理的一餐、存或編輯含料理的組合、編輯料理）暫停，並用中性文字說明「衛福部資料載入失敗，請稍後再試」；不能把料理歸成「已不提供」，也不能在組合編輯時把它當成 `dropped` 拿掉。
  - **改版**：衛福部出新版時，查詢檔保留舊版有、新版消失的編號並標「衛福部已下架」（數值照舊可讀），我的食材因此不會失去數值（章程 B10）。
- 每一筆的明細：
  - 一份的熱量、蛋白質、碳水、脂肪、纖維、飽和脂肪、鈉；食材另列每 100g、一份幾克、生熟狀態（12.4 的 `state`）；
  - 過敏原、全素／蛋奶素；**衛福部那幾筆顯示「衛福部資料沒有過敏原資訊」**，不跑「會不會被擋」的判斷（不然有設過敏原的人會看到兩千多筆全部被擋）；
  - **能在哪些餐出現**：品項列 `valid_slots`；內建食材列「出現在哪些餐型、那些餐型的時段」；我的食材寫「只用在我的料理，不會出現在自煮分頁的餐型選項」；
  - 出處（12.1 的標示；衛福部的附整合編號）；
  - 狀態：已隱藏、已封存、常買；以目前設定會不會被擋（中性文字，跟選擇器同一套原因；衛福部那幾筆例外，見上）。
  - **複製來的我的品項**：明細裡唯讀並列「內建目前的數值」，讓使用者知道原版後來有沒有更新（decisions #61）。
- 動作：唯讀的那幾層是「加進我的食材」「標常買」「複製成我的版本」「隱藏」；我的資料是「編輯」「封存」。（第 13 節起：「標常買」「隱藏」改為「常吃」「不吃」。）
- 排序與呈現：依名稱或資料原順序，不依熱量排、不上色（第 6.1 節）。

**成分明細**：選擇器的摘要與推薦卡片可以展開，列出每個成分各佔多少熱量與蛋白質（例：糙米飯 1.2 倍 約 220 kcal、雞胸 約 130 kcal、用油 5g 約 44 kcal；單品：鮮奶 480ml 約 303 kcal）。
- 由 `engine/meal-content.js` 的函式提供，跟 `contentTotals` 用同一份元件加總，ui 不自己算（章程 C4.11）；只顯示數字，不評判。
- **只用在選擇器與推薦卡片**，不用在過去的紀錄：紀錄裡的自煮食材沒有逐項快照，事後重算可能跟當時存的 `totals` 對不上。
- 不影響 diff-recs 的推薦快照。

### 12.3 內建餐點的修訂：複製後再改，外加份量倍數

- 維持 10.2：不做修補層。「複製成我的版本」之後，所有欄位都能改（名稱、角色、`valid_slots`、營養成分、過敏原、素食、說明）；原本那筆自動隱藏。
- **份量倍數**：選擇器裡已選的商品與我的料理可以改份量（0.5、1、1.5、2 份），寫進元件的 `qty`，合計照乘。解決「便當飯只吃一半」「兩顆茶葉蛋」這類情況，不必為了份量另建一筆。倍數只影響這一餐。
  - `qty` 只用在 `product` 與 `dish` 元件；自煮骨架的食材不用，主要槽位本來就依預算縮放。
  - 角色上限算的是元件數，不是 `qty`（兩顆茶葉蛋＝1 個配菜）。
  - `data/db.js` 驗證 `qty` 只能是 0.5、1、1.5、2。（單品 `food` 另見第 3 節與 13.4：0.5 的倍數，0.5–12，`FOOD_QTY_MAX`，decisions #122；不重用 `QTY_OPTIONS`。）
  - 位置（B-1a）：超商／外食分頁的「已選」段每個已選品項一行份量晶片「半份／1／1.5／2」；飲料的份量在飲料步驟、選中的那杯下面（三分頁共用，切到自煮也看得到）。每行不顯示熱量，看摘要（章程 C4.11）。記錄名稱帶份量：「便當（半份）＋茶葉蛋 ×2」。

### 12.4 我的食材＝常買清單（新 store `custom_ingredients`）

> **decisions #131、#134 起**：衛福部來源的狀態、過敏原與素食跟著查詢檔、使用者不能改；「一份幾克」選填；衛福部來源的「不吃」＝移除（不封存）；自填的「刪除」＝封存（畫面說「刪除」）。細節以切片 8b 計畫定案後的本節為準。
>
> **切片 8b 定案（decisions #138，取代下面程式碼區塊與條列中衝突的部分）**：
> - 衛福部來源：`{ id: "cing_" + 整合編號小寫, source: "tfda", tfda_id, tfda_version, name, default_amount: null | > 0, note, created_at, updated_at }`——**不存** `state`、`per_100g`、`allergen_tags`、`vegan`、`lacto_ovo`、組別、單位，全部執行時讀查詢檔；沒有 `archived`：「不吃」＝刪掉這筆紀錄（同一個 transaction 移出常吃），提示列「復原」原樣放回；從「＋新增食材」再加回是新紀錄（名稱與一份要重設），id 相同所以組合裡的引用恢復。料理引用衛福部食材不依賴紀錄存在（id 反推整合編號讀查詢檔，給切片 9）。
> - 自填：`{ id: "cing_u_…", source: "user", name, group（代換表六大類或 other）, drink, state: raw|cooked|as_is, per_100g（kcal 必有且 ≥ 0，其餘 ≥ 0 或 null）, default_amount, allergen_tags: null | [], vegan, lacto_ovo, note, archived, created_at, updated_at }`；「刪除」＝`archived: true`（不動常吃，還原後常吃自然回來）。
> - `default_amount`（取代 `default_g`）：一份的量，單位跟著液體與否（液體 ml，其餘 g）；衛福部來源的液體依查詢檔 `drink`，每 100g 視為每 100ml（同代換表全脂奶 1 杯＝240g 的慣例），明細寫一句。衛福部食材的單位跟著查詢檔。
> - `filled`（補衛福部缺的欄位）延後；查詢檔已套用章程 B5.1 的補 0（decisions #137）。
> - 驗證：衛福部來源 `id === "cing_" + tfda_id.toLowerCase()`、`tfda_id` 符合 `^[A-Z][0-9A-Z]{5,8}$`；自填 id 以 `cing_u_` 開頭；`default_amount` null 或 0 < x ≤ 3000。
>
> **第 13.8 節起**：資料結構與驗證照本節；「常買清單」的語意拿掉（由常吃取代），封存的意思改成 13.8 的定義；入口在「我的食物」自煮子分頁；可以當單品記錄。本節提到的「常買」「`favorite_ingredient_ids`」「自煮分頁不因常買改排序」一律以第 13 節為準。

**定位**（decisions #56）：流程是「衛福部食材 → 我的食材 → 自組」。使用者先從衛福部全表挑自己實際會買的，之後自組只從這份短清單挑，不必每次在兩千多筆裡找。

```js
{
  id: "cing_xxx",
  name,                                   // 必填；衛福部來源預帶樣品名稱，可以改（明細另外顯示原本的樣品名稱）
  source: "tfda" | "user",
  tfda_id: "A0100101" | null,             // source 是 tfda 時必有
  tfda_version: "2025-update1" | null,    // 加入時的衛福部資料版本（章程 B10）
  per_100g: { kcal, protein_g, carb_g, fat_g, fiber_g, sat_fat_g, sodium_mg } | null,
      // user：必有，kcal ≥ 0（鹽、黑咖啡可以是 0），其餘可 null
      // tfda：null——數值執行時從 data/tfda_lookup.json 依 tfda_id 讀，結構上改不了（decisions #59）
  filled: { fiber_g?, sat_fat_g?, ... },  // 只給 tfda：使用者補「衛福部是 null 的欄位」，標「你填的」；衛福部有值的欄位不能補
                                          // 衛福部改版後原本 null 的欄位有了值：執行時衛福部優先、忽略 filled 的同名欄位，下次更新時自動清掉
  state: "raw" | "cooked" | "as_is",      // 生／熟／照現狀（加工品、乾貨）；tfda 跟著查詢檔（使用者不能改，decisions #134）；user 由使用者選
  default_g,                              // 選填（decisions #131）：一份幾克，> 0 或 null；null 時只能用克數記錄
  allergen_tags: null | [],               // 同 10.1；null＝未確認
  vegan: false, lacto_ovo: false,
  note,
  archived: false, created_at, updated_at,
}
```

- **加入衛福部食材**：在「食物資料」搜尋衛福部全表，挑選後「加進我的食材」。如果它的整合編號跟某個出處是 `tfda` 的內建食材相同（例：雞胸；由生米推算的熟糙米飯這類 `derived` 不比對），提示「內建已有這個食材，改成標常買」，避免同一個食材兩筆。
- **完全自填**（包裝食品，例：某牌豆干）：可以填每 100g，也可以照包裝填「每份的數字＋每份幾克」，存檔時由 engine 換算成每 100g（decisions #64）。
- **克數跟著狀態**：（decisions #134：衛福部可以加的 1887 筆是生 939、照現狀 832、乾 64、熟 48、濕 4；只有生樣品的寫一行「衛福部只有生的樣品，請用煮之前的重量」；不做生熟換算）表單與料理編輯器每一列克數旁邊顯示狀態；說明依狀態顯示（生：買來、煮之前的重量；熟：煮好的重量；照現狀：包裝上的重量）。衛福部 2213 筆的樣品狀態：生 945、熟 44、乾貨 67、沒寫 577（多半是加工品，當成照現狀）。
- **過敏原**：~~衛福部資料沒有過敏原欄位，加入後預設未確認，要使用者自己勾；~~ **decisions #131 起帶入 `data/reference/tfda_tags.json` 的標註（查詢檔裡的 `allergen_tags`、`vegan`、`lacto_ovo`）**；自填的照下面；有設過敏原的人照 10.3 的中性預告，不出現「改成確認不含就能選」這類引導（章程 C4.1、decisions #48）。我的食材不適用章程 B6.8（比照我的品項）。
- **內建食材標常買**：`ingredients.json` 的內建食材可以標「常買」，存在 `settings.favorite_ingredient_ids`（只存 id，不複製數值）。
- **常買清單**＝未封存的我的食材 ∪ 標了常買的內建食材，由 engine 的一個函式產生（選擇器與料理編輯器都呼叫它）；清單裡殘留已下架的內建 id 時略過，不出錯（章程 B9）。
- **常買與封存**：把我的食材從常買移除＝封存。封存只代表「不出現在常買清單與搜尋結果」，**引用它的料理照樣讀得到它的數值、照樣能用**；封存時列出哪些料理還在用它（中性文字）。
- **用途**：只用在「我的料理」的食材選單（只列常買清單，臨時要用沒列的可以在同一個畫面搜尋、當場加入）。不放進自煮分頁的餐型骨架（`allow` 由開發端維護，章程 B7），不影響推薦。自煮分頁的餐型選項**不因常買而改排序**（decisions #60）。
- 跟 Phase 4 採買清單的 `pantry`（家裡常備、不算進要買，開發端維護的食材欄位）**無關**，兩者不相干。

### 12.5 我的料理（新 store `custom_dishes`）

> **第 13.8 節起**：食材 `ref` 也可以是代換表分層品項（`fx_` 或內建食材 id），營養用 `food_tree.json` 裡 tools 算好的 `per_100g`（decisions #95）；食材選單常吃在前。

使用者自己的菜：用食材（常買清單裡的內建食材與我的食材）加克數自由組成，營養由食材加總。

```js
{
  id: "cdish_xxx",
  name,                                   // 必填
  ingredients: [{ ref, grams }],          // 至少 1 項，grams > 0；ref 只能是內建的蛋白質／主食／蔬菜／醬料軸食材或我的食材
                                          // （不能是烹調法、cooking_oil、seasoning_*：用油與調味用下面兩個欄位）
  oil_g,                                  // 整份食譜總共的用油克數，≥ 0（使用者輸入）；預設 5g × servings × 用油習慣（少油減半）
  seasoning: "light" | "normal",          // 每份的調味程度；預設：含醬料軸食材時清淡，否則一般（比照章程 B5.7）；「不加」跟 decisions #42 同一批待 C3
  servings: 1,                            // 這份食譜做幾份（≥ 1 的整數）；記錄一份＝總量 ÷ servings
  role: "main" | "side" | "snack",
  valid_slots: [...],                     // 規則同 10.3
  note,
  archived: false, created_at, updated_at,
}
```

- **型態**：料理沒有自己的快煮／開伙，記錄時用自煮分頁子切換的值（decisions #47、#57）。
- **營養**（`engine/meal-content.js`，章程 C2）：一份＝（食材每 100g × 克數的加總＋用油 `oil_g` 的數值〔`cooking_oil`〕）÷ `servings`，**再加上一份的調味鈉**（清淡約 300 mg、一般約 700 mg，照章程 B5.7 的 `seasoning_*`；調味是每份加，不除以份數）。null 照章程 C4.5 傳染（鈉、飽和脂肪例外，快照帶 `partial`）。衛福部來源的食材讀 `tfda_lookup.json`，衛福部是 null 的欄位才用 `filled`。
- **用油與調味跟章程 B5.6、B5.7、decisions #42 的關係**：料理的用油是使用者自己寫的整份食譜的一部分，跟食材克數一樣是使用者輸入，所以可以填任何非負的克數（包括 0）；這不是「自己選」裡一鍵的「不用油」選項，不違反 #42 的顧慮。調味程度是依程度估計的鈉、不是使用者量得到的數字，所以「不加調味」仍跟 #42 同一批待 C3。
- **硬性過濾**（`engine/filters.js`，每次顯示或引用時用當下的食材資料推導，不存在 `custom_dishes` 裡）：
  - 過敏原：食材的聯集，任一食材未確認 → 整道未確認（章程 B6.4 精神）；
  - 全素：每個食材都宣告全素；蛋奶素：每個食材都是全素或蛋奶素（章程 C4.2）；
  - 不吃清單：任一食材 id 或料理本身的 id 在不吃清單裡 → 整道被擋（只比 key，decisions #40）；
  - 第 6.3 節第 3 點（計畫顯示時重新過濾）與章程 C4.4 對料理照樣適用。
- **食材查不到時**（內建食材照 B9 下架）：整道料理歸「已不提供」，**不做部分加總**；已封存的我的食材不算查不到；衛福部下架的編號照 12.2 仍讀得到；查詢檔載入失敗照 12.2 處理，不算查不到。
- **封存的料理**：比照封存的我的品項（11.3 規則 1）——不出現在選擇器，組合引用時歸「已不提供」；紀錄照樣用快照顯示。
- **例外（修正第 6.3 節）**：我的料理豁免 6.3 的第 1 點（骨架 `allow` 與軸上限）與第 2 點（免開火），第 3 點照樣適用。6.3 的「計畫層不能繞過骨架」是為了推薦與計畫的組合品質；我的料理是使用者自己定義的菜，只用在手動記錄與手動排進計畫，引擎不會產生它，骨架本身也沒有放寬。
- **在選擇器裡**：自煮分頁「選餐型」上方一組「我的料理」。
  - 一餐可以放多道料理（例：滷雞腿＋燙青菜），受手動記錄的角色上限限制（decisions #57）；每道可以改份量倍數。
  - **同一餐不跟餐型自組混在一起**：選了料理就收起餐型那一段，反之亦然，並用中性文字說明「一餐用料理或用餐型自組，擇一」。飲料步驟照舊可以加。
  - 送出條件（修正 decisions #45 的說法）：自煮分頁「餐型完整」或「至少選了 1 道料理」就能送出（decisions #69）。
- **MealContent**（第 3 節）：新元件種類 `dish`（方案 A，第一輪審核採用）。
  - 紀錄：`{ kind: "dish", ref, qty, snapshot: { name, kcal, protein_g, carb_g, fat_g, fiber_g, sat_fat_g, sodium_mg, partial } }`，快照是一份的營養（含用油與調味），`qty` 照乘；`partial` 讓整餐的「部分品項無資料」照常顯示（章程 C4.5）。
  - 只有料理的一餐，`implicit` 記 `{ oil_g: 0, seasoning: null }`：用油與調味已經含在料理快照裡（章程 C4.11 加註）。計畫與組合的 `implicit` 是 null 時照第 3 節「套用當下預設」，沒有烹調法與骨架時預設剛好也是 `{ oil_g: 0, seasoning: null }`，要有 check-engine 斷言。
  - `data/db.js` 驗證：元件種類加 `dish`，紀錄與計畫的 dish 必有 `ref`、`qty`、`snapshot.name`、`snapshot.kcal`（名稱在快照裡，跟 `estimate` 的頂層 `name` 分開檢查；`saved_meals` 的 dish 只有 `ref`、`qty`，不帶快照，見 11.1）；含 `dish` 的一餐不得有 `ingredient`，`archetype_id`、`method_id` 是 null；`implicit` 依存放位置：`daily_log` 恰好是 `{ oil_g: 0, seasoning: null }`（避免用油重複計算），`meal_plan` 與 `saved_meals` 是 `{ oil_g: 0, seasoning: null }` 或 `null`（null＝套用當下預設，11.1、12.6）。`snapshotProblem` 允許快照帶 `partial`。
  - 組合引用（11.3）：`resolveSavedMeal`、`remapSavedRefs` 多收料理、我的食材與衛福部查詢表；這一餐的 `archetype_id` 是 null，略過 11.3 規則 4（骨架重新驗證）。
  - 推薦快照（diff-recs）不受影響：推薦引擎不產生 `dish` 元件，`contentFromRec` 不變。
  - **刻意的行為**：今天已記錄的一餐如果是料理，推薦判斷跨時段不重複（蛋白質、餐型、品項）時不看料理，料理裡的蛋白質不佔名額——因為料理不進推薦，這不是 bug。Phase 2 讓計畫的料理預先佔用當天預算時，`engine/today.js` 用「不是 `ingredient` 就用快照」的泛用寫法，不直接寫 `"dish"`（章程 C4.17 ③）。
  - 名稱：`dish` 元件＝我的料理，跟 `data/dish_archetypes.json`（餐型骨架）無關。
- 不進推薦、不進 Phase 4 採買清單的 MVP（料理的食材沒有採買欄位，decisions #62）。

## 13. 我的食物（2026-09-30 定案，兩輪獨立審核）

使用者先建好「自己會吃的食物」，選擇器與今日建議從這裡取；設定之後隨時能看、能改。依據：[設計草案第三版](review/2026-09-30-我的食物分頁-設計草案.md)（細節、實測數字、第一輪與第二輪意見的對照都在草案裡）；審核逐字 [2026-09-30-my-foods-tab-review](../collab/opus-review-log/2026-09-30-my-foods-tab-review.md)、[C3 專項審核](../collab/opus-review-log/2026-09-30-workline-d-c3-review.md)；decisions #74–#95。家人只影響煮多少（`household_size`、料理的 `servings`），不做每人各自的清單。

### 13.1 原則

- **食物代換表做自煮食材的主體**（分類、「1 份」多大），**衛福部營養成分資料庫當營養數值來源**；代換表的營養欄不顯示、不計算（章程 B2 `exchange`）。
- **安全底線（decisions #77）**：沒有過敏原或素食標註的東西（衛福部全表、標「未確認」的），使用者設了任何過敏原就不推薦、不可選；設了全素或蛋奶素就要正面宣告才可選。這是現行 `engine/filters.js` 的行為，本節所有新東西都照它，不放寬。
- 不評判（第 6.1 節、章程 C4.13）：常吃一定是使用者自己標的，不依紀錄頻率提示；不顯示六大類份數換算、脂肪分級、膽固醇或鉀的標記。

### 13.2 位置、搜尋、職責搬家

- 主分頁「我的食物」，在「今日建議」旁邊。**主分頁固定 5 個**：基本資料／今日建議／我的食物／本週總覽／運動紀錄，手機上等寬不橫捲；原本空的「採買清單」分頁拿掉，Phase 4 採買清單放在「本週總覽」的子頁（decisions #96）；餐點日曆週格子不做，未來 6 天的預選在今日建議裡切換（decisions #118、#119）。
- 頂端搜尋：名稱與別名；範圍是四個子分頁、我的品項、我的食材、我的料理、我的組合；結果標出子分頁與大類、子類（組合標「我的組合」，點了展開管理區塊）。不含衛福部全表（decisions #86，日後處理）。
- 從「基本資料」搬過來：我的品項管理（第 10.6 節）、已隱藏的內建品項（只能取消，不能新增）、不吃的全部清單（含推薦卡片「順便不要」加的與已下架殘留的 key，查不到的列「已不提供」可移除）；我的組合管理（第 11.5 節）直接放這裡。「基本資料」只留身體數據、目標、飲食限制與過敏原、低碳、用油習慣、體重回填、校正卡片、資料備份。

### 13.3 四個子分頁

| 子分頁 | 內容 |
|---|---|
| 超商 | 內建超商品項（不含飲料）＋我的超商品項；呈現同選擇器（第 6.3 節） |
| 外食 | 內建外食與宅配餐盒（不含飲料）＋我的外食品項 |
| 自煮 | 代換表分層（水果類與 `home_drink` 除外；蒸發奶是液體但在自煮）＋對不到代換表的內建食材＋我的食材＋我的料理 |
| 飲品・水果 | 現成飲料（內建 `role: drink`）、家裡的飲品（代換表乳品液體、無糖豆漿）、沖泡（13.8）、水果（代換表附-6） |

- 切片 2 只有超商、外食、飲品・水果（只有現成飲料）三個子分頁；自煮子分頁與家裡的飲品、水果在切片 4 跟分層資料一起出現，不放空殼（decisions #97）。

- 每一項：**常吃**、**不吃**、**明細**（一份多大、營養、出處、以目前設定會不會被擋）。~~我的品項、我的食材、我的料理只有「封存」，沒有「不吃」。~~ **說法統一（decisions #134）**：不是使用者做的（內建、代換表、衛福部來源的我的食材）一律「不吃」——衛福部來源的不吃＝從我的食材移除；使用者自己做的（我的品項、自填食材、我的料理、我的組合）一律「刪除」，收進「已刪除」組可「還原」（資料欄位仍是 `archived`）。「移除」只用在從這一餐拿掉與清掉已下架的殘留。明細數字由 engine 提供（章程 C4.11）。
- 內建超商、外食品項可以「複製成我的版本」；**被擋的也可以**，按鈕在明細裡、不在被擋原因旁邊，表單照第 10.3 節中性預告、過敏原照原品項帶入（decisions #84）。
- 同一個衛福部樣品的兩個身分（外食「鮮奶（一杯，約240ml，全脂）」與代換表「全脂奶（自己倒）」；「豆漿（無糖，大杯約300ml）」與「無糖豆漿」）：名稱照現有資料（已看得出外帶與自己倒），「家裡的飲品」組緊接在「現成飲料」組之後，明細互相提到，搜尋同時出現（decisions #85、#114）。配對由 `source.ref` 機械推出，只限同一個樣品；代換表裡同一樣品、不同食物的（白米↔白粥、糙米↔糙米飯）寫「同一種食材的其他形式」（decisions #108）。
- **標不吃時的提示**（decisions #115）：只在「我的食物」（「自己選」與今日建議「順便不要」不提示）。那一列照常移到「你標了不吃」並保持展開、畫面捲到那一列；明細裡對另一筆出現「也標不吃」按鈕，取消時出現「也取消」；不用確認對話框。訊息分兩種：共用內建 id 與現成品項寫「推薦與「自己選」都不會再選它」；`fx_` 品項寫「只擋這一項，不影響推薦裡的其他食物」。寫進不吃清單的 type 是 `food_tree`（比對只看 key）。

**分層（自煮與飲品・水果的代換表品項）**：
- 大類＝代換表六大類；子類＝代換表的分組欄（分組欄空白的列人工指定；乳品不分子類）；品項＝代換表一列拆出的品名，重複列合併、保留別名。蔬菜照每日飲食指南分葉菜、花菜、根菜、果菜、豆菜、菇類（代換表沒有海菜，這組先不出現），另加本 App 自己的「筍與莖菜」一組並標明；標籤「高鈣深色蔬菜」照指南名單逐項比對（decisions #90）。組內依名稱排序。手機上大類與子類都用可收合的區塊（預設收合、標題附目前列出的筆數），展開狀態在切子分頁、搜尋後保留；乳品類只有一層。
- **id（decisions #78）**：對得到 `data/ingredients.json` 內建食材的品項，id 就是內建食材 id（所以在這裡標不吃、常吃，跟推薦卡片是同一個 key）；其餘用 `fx_` 開頭並凍結。對不到代換表的內建食材也列在所屬大類（標「內建食材（代換表沒有這一列）」，顯示今日建議的一餐克數）。唯一性：分層 id 不等於任何 catalog uid；`fx_` id 不等於任何內建食材 id；分層 id 等於內建食材 id 時標 `builtin` 且只出現一次；不用使用者資料的前綴（章程 B12）。**例外**：烹調法、隱含成分（用油、調味）、醬料這三軸的內建食材不列在分層、不共用 id——代換表「大豆油」用 `fx_` id，不用 `cooking_oil`（「不吃大豆油」跟「烹調用油」是兩件事；同一樣品的標註仍必須相同，decisions #102）。代換表跟內建是**同樣本、不同食物**的（糙米↔糙米飯、什穀米↔雜糧飯、花椰菜↔花椰菜米）各自一個 id，所以在「我的食物」標糙米不吃不會擋掉推薦的糙米飯；切片 4 的同樣本提示延伸到這種情況（decisions #108）。
- 每一筆有結構化的 `tfda_id`（衛福部整合編號），同一樣品同標註、U6 配對都靠它（章程 B4、B6.9）；只有出處是美國農業部的內建希臘優格是 null。
- **1 份**：寫成「1 份（代換表）」並附家用單位，克數前寫生重、熟重、乾重、濕重或（水果）可食部分；共用內建 id 的明細另寫今日建議的一餐（「今日建議的一餐：生重 130g（約 4.5 份代換表）」）；對不到代換表的內建食材寫「內建一餐：熟重 150g（今日建議會依你的熱量調整）」。出處說明依 `source.derivation` 寫生熟等值推算或由生米推算熟重；缺值填 0 的欄位用使用者看得懂的一句話，不顯示開發註記（decisions #98、#116）；營養用可食部分計算（附-3 生重、附-6／附-7 可食量、附-4 可食重量），熟重與購買量只當顯示；液體用毫升，營養計算時照代換表附-1 換成公克。每個品項 1 份的營養由 tools 預先算好（章程 C2）：代換表品項跟現成品項用同一段換算程式（所以外帶「鮮奶一杯」跟代換表「全脂奶 240ml」數字完全相同）；共用內建 id 的用內建的每 100g 數值乘克數（跟今日建議算法相同，decisions #103）。
- **對應（decisions #79）**：人工逐項指定並寫理由；狀態由代換表決定（生熟乾濕、含糖）；有內建食材的用同一筆；泛稱列不收；衛福部沒有狀態相符樣品時，代換表有生熟等值列的用 `derived` 推算，沒有的不收。**果乾**：代換表以加糖計；衛福部有加糖樣品的照原名收，只有無加糖樣品的名稱加「（無加糖）」收進來，都沒有的不收。**優格(無糖)、優酪乳(無糖)不收**（衛福部的發酵乳都含糖；無糖優格用內建希臘優格或新增食材）（decisions #109，使用者已確認）。對應表、標註、不收清單與理由在 `data/reference/`，由 `tools/build-food-tree.js` 產生 `data/food_tree.json`。
- 不做衛福部第 4 層細項、不做代換表以外的「其他」大類；代換表以外的食物用「新增食材」（13.8）。
- 畫面名稱去掉代換表的符號與附註（◎、＊、△、#、「+5公克碳水化合物」「3個/斤」），會誤導的加說明（「雞排肉（生）」），原名留作別名。共用內建 id 的用內建的名稱。代換表的「+5 公克碳水化合物」「+1 茶匙油」不寫成「另含」（衛福部的數字已經包含），寫成「代換表把它算成 1 份蛋白質另加約 5g 碳水；上方營養已包含」。
- 「家裡的飲品」由資料欄位 `home_drink` 決定（全脂、低脂、脫脂奶與無糖豆漿），不依單位猜。

### 13.4 單品直接記錄（`food` 元件，decisions #82、#83）

- 「自己選」三分頁共用兩步，都不影響 `meal_type`：
  - **「飲品・水果」**（取代原本的飲料步驟）：現成飲料（照角色上限 1 杯）、家裡的飲品與水果（單品）、沖泡建立的我的食材（單品）。
  - **「加點單品」**：其餘代換表品項與我的食材，依大類 > 子類，可搜尋。搜尋框搜**全部**分層品項（含飲品・水果的品項），結果標出所在步驟（「在飲品・水果」）並可直接點選（decisions #122）。
- 每一步：常吃在最上面；不吃在最下方（第 6.3 節）；被過敏原或飲食限制擋的灰在各組最後。**切片 7 時兩個步驟只有分層品項**：「常吃在最上面」從切片 5 起、「我的食材」從切片 8 起、沖泡建立的我的食材從切片 10 起，各自到時再加（decisions #121）。
- 「選餐型」步驟上方有一行中性說明：只記單品可以不選餐型，直接到下面加點單品（decisions #122）。
- 份量：步進器，0.5 份一格，0.5–12（`FOOD_QTY_MAX`，decisions #122）；步進器 −／＋ 在 0.5 時 − 停用、12 時 ＋ 停用。旁邊寫 engine 算好的量，**以克數或毫升為主，必寫狀態詞**（生重、熟重、乾重、濕重、可食部分），`serving.display` 的「煮熟約」「購買量約」照份數乘（「4 份＝生重 120g（煮熟約 Ng）」）；量的計算只寫一次（`foodAmount`），名稱與步進器文字共用。家用量（`household`，例「1 碗」）只在乘得乾淨時才寫：有理數計算、約分後分母是 1、2、3、4 才寫（米杯放寬到 8）；可數單位（個、粒、張、片、根、顆）原值是 2 以上的整數時，結果是整數才寫；不寫小數；其餘只寫克數或毫升；份數 1 原樣寫（計畫 8.2 M3，decisions #122）。我的食材的 1 份是使用者設的 `default_g`，寫成「1 份＝你設的 40g」。**對不到代換表的內建食材**（糙米飯、藜麥等）也可以當單品，1 份＝內建一餐，寫成「1 份＝內建一餐 熟重 150g」（糙米飯）、「1 份＝內建一餐 乾重 45g」（藜麥）（decisions #95、#122）。單品的份量狀態自己一套，不重用 `qtyByUid`／`draftQty`。
- 已選的單品放在各步驟頂端各自的「已選」框，卡片本身標「已選 · N 份」；同一項再點不新增一筆（一餐裡同一個 `ref` 只有一個 `food` 元件），份量回到它的步進器；「移除」不跳確認（decisions #122）。
- 一餐最多 4 項單品（`FOOD_MAX_PER_MEAL`，`core/config.js`），**不佔**主餐、配菜、點心、飲料名額（章程 C4.8）；不套 `valid_slots`；只有單品也可以成為一餐；跟餐型、料理重複的照算、不擋、不提示。步驟裡一行中性說明「單品不含烹調用油；有用油可以加油脂類」。
- 自煮分頁再點一次已選的餐型＝取消餐型（hint：「只記單品可以再點一次「X」取消餐型」；已選餐型按鈕用 `aria-pressed`）（decisions #122）。
- 自煮分頁的送出條件：餐型完整，或至少 1 道料理，或至少 1 項單品，**或至少 1 杯飲料**（修正 decisions #45，#122；「只記飲料請到超商或外食分頁」的提示拿掉）；「沒有餐型、沒有料理、沒有單品、也沒有飲料」才回「請先選餐型」，有選餐型就照餐型的檢查（半套餐型加單品照樣擋下，不默默丟掉）。自煮的一餐沒有 `ingredient` 元件（只有單品、料理或飲料）：`daily_log` 的 `implicit` **恰好**是 `{ oil_g: 0, seasoning: null }`，`archetype_id`、`method_id` 是 null（`data/db.js` 寫入驗證；`contentTotals` 只在有 `ingredient` 元件時才加隱含成分，decisions #123）。
- 記錄名稱：`<品名> <量>`，量＝份數 × 1 份的量（g 或 ml，進位到 0.1），不寫份數；`raw` 的品項加「生」、`dry` 的加「乾」（「雞胸肉 生 120g」「藜麥 乾 45g」），熟食與液體不加（「白飯 160g」「全脂奶（自己倒） 480ml」）。名稱順序：（餐型與食材｜品項）→ 估算 → 單品 → 飲料，例「全脂奶（自己倒） 480ml＋白飯 160g」依此排。只有單品的一餐（三個分頁各一）名稱也要正確（`draftLogName` 不能假設有餐型）（decisions #122）。
- **克數記法**（decisions #136、#138）：全部單品的已選框都有「份｜克」切換（液體是「份｜毫升」）；克模式是數字輸入，整數 1–3000，失焦或 Enter 才生效；元件寫 `amount`（不寫 `qty`）。份→克取整數（`round(1 份 × 份數)`），克→份取最接近的 0.5 倍（至少 0.5）；所以兩種記法合計只在「克數＝份數 × 1 份」時完全相同。沒有 1 份的品項（沒設一份的我的食材）只有克，點選時預設 100。名稱照實際量寫（「雞胸肉 生 120g」），兩種記法同一格式。
- `data/db.js` 驗證：`food` 有 `ref`；`qty`（0.5 的倍數且 0.5–12，decisions #122）或 `amount`（整數 1–3000）恰好一個；紀錄與計畫有 `snapshot`：必有 `name`、`kcal`、`amount`、`unit`，其餘營養欄位是數字或 null，允許 `partial`（只給切片 8 起的我的食材用；切片 7 的快照是單一樣品，不會有）；組合不帶快照。
- 合計走 `buildDraftContent` → `contentTotals`；不縮放；null 照章程 C4.5 傳染。分層資料掛在 catalog 物件上（`catalog.foodTree`，decisions #92）；硬性過濾：分層品項由 `data/catalog.js` 正規化時補上 `uid`（＝id）、`allergen_tags`、`diet_tags`（不然不吃判斷比不中）；`passesHardFilters` 回傳原因代碼（過敏原／飲食／不吃），畫面依代碼決定位置。
- 推薦不產生 `food`、候選池不讀分層資料（章程 C4.17）。**刻意的行為**：推薦判斷跨時段不重複時不看單品（午餐記了雞胸單品，晚餐照樣可能推雞胸）。
- 衛福部來源的我的食材要讀 `data/tfda_lookup.json` 算快照；載入失敗照第 12.2 節暫停記錄，不當成查不到。
- 組合與計畫的 `food` 照第 11.1、11.3 節（只存 `ref` 與 `qty` 或 `amount`；歸「已不提供」的條件見 11.1），跟工作線 C、Phase 2 一起實作；日期切換的預約沿用同一個形狀。
