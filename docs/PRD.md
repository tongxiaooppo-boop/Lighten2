## 0. 這次要解決什麼問題

起點是一件小事：「自己選」手動組餐 modal 裡「現成品項模式」跟「自己煮模式」該不該共存。往下挖才發現：**這個雙模式切換，本質上是「自己選」modal 自己發明了一套跟 profile 既有的 `meal_prefs`（超商/外食/自煮快煮/自煮正常煮）不一致的分類**，導致「現成品項模式」的內容（超商/台式單品多選湊一餐）看起來又跟「美饗日曆」重複。

往下再挖，變成使用者想要的東西其實更大：**每一餐都該有一個型態（超商/外食/快煮/開伙），這個型態可以是引擎自動建議帶入的，也可以是使用者自己指定的；使用者還想要能「規劃一整週」要開伙/快煮吃什麼，並依人口數產生採買清單。**

這已經不是修一個 UI 元件的量級，而是要在三個既有的資料/UI 表面（profile 的 `meal_prefs`、今日建議的自己選 modal、美饗日曆）之外，補上一層「餐點計畫」的概念。這份文件就是在定這一層該怎麼設計。

**Opus 審核後的整體判斷（也是這份文件的立場）**：不要整個程式翻新。既有的推薦引擎、硬性過濾、每日動態預算、體重趨勢校正、餐型骨架自組邏輯都是健全的、經過多輪審核定案的，2.0 只需要**加一層**，不是**換一層**。

## 1. 核心概念一：三層資料模型

| 層 | 資料位置 | 內容 | 現況 |
|---|---|---|---|
| **L1 長期預設** | `profile.meal_prefs[slot]` | 每個時段一個型態，沒有日期概念 | 已存在 |
| **L2 餐點計畫** | 新 store `meal_plan`，key = `date\|slot` | 某天某時段：只指定型態，或型態＋具體內容 | 新增（Phase 2） |
| **L3 實際紀錄** | `daily_log` | 真的吃了什麼 | Phase −1 改成新格式：一筆一餐，`meal_type`＋MealContent 快照 |

**解析規則**（整份設計最核心的一條）：

```
某天某時段的有效型態 = meal_plan[date|slot]?.meal_type  ??  profile.meal_prefs[slot]

某天某時段的顯示內容 =
   已有 daily_log 紀錄        → 顯示已記錄（跟現在一樣）
   meal_plan 有指定 content   → 顯示計畫內容（不跑引擎，但顯示時要重新驗證硬性過濾）
   否則                       → 引擎依有效型態 filterBySource 產生建議（跟現在一樣）
```

今日建議的即時運算引擎**完全不改演算法**，只多一個輸入（有效型態），加上「計畫已指定內容時不跑引擎」這個分支。

**明確不做的事**：`profile.meal_prefs` 不加平日/週末兩組設定。長期預設維持單一值，需要跟平常不一樣時，靠 L2 的「週規劃」逐日覆蓋，並用「複製上週」降低重複輸入的成本。這是刻意的取捨（少一份要維護的資料結構），不是遺漏。

## 2. 核心概念二：型態不是「食材 vs 成品」的開關

使用者原始想法是「超商/外食/快煮/開伙，每種都要能選食材或成品」。逐一檢查後發現這個二分法不該讓使用者自己選：

- **超商、外食**：所謂「自組」，本質是「多個現成商品湊一餐」（沙拉+茶葉蛋+豆漿），營養值固定、不能縮放。這其實是「單品 vs 多品」，不是「食材 vs 成品」。引擎本來就有 `generateItemCombos` 在做這件事。
- **快煮、開伙**：這才是真正的食材自組（餐型骨架＋食材軸，`serving_g` 可縮放）。自煮沒有「成品」這個概念——冷凍水餃、微波調理包在資料上就是超商品項，不該在自煮型態裡重複出現。
- **快煮 vs 開伙**：不是兩個互斥的型態，是同一個型態（自煮）的不同 tier 上限（開伙 = tier 不限，快煮 = tier ≤🟡，「開伙」本身就包含「快煮」做得到的所有東西）。

**結論**：使用者看到的只有「型態」（超商｜外食｜自煮），型態決定 UI 要開哪一種選擇器（商品多選 vs 餐型骨架食材軸），不會有一個額外的「食材/成品」切換鈕讓使用者困惑——這個切換鈕正是今天模式選擇造成混亂的根源。

## 3. 核心概念三：統一的「一餐內容」格式（MealContent）

**Phase −1 一次定案**（0.1 第 4 點），實作在 `engine/meal-content.js`，推薦、自己選、餐點日曆、採買清單共用（章程 C2）。

```js
MealContent = {
  meal_type: "convenience" | "delivery" | "cook_quick" | "cook_full",
  archetype_id: "arch_stir_fry" | null,        // 只有自煮才有
  method_id:    "method_stir_fry" | null,
  components: [
    { kind: "ingredient", axis: "protein",   ref: "beef_shank" },
    { kind: "ingredient", axis: "staple",    ref: "brown_rice_cooked", is_primary: true },
    { kind: "ingredient", axis: "vegetable", ref: "cabbage" },
    { kind: "product",    role: "drink",     ref: "conv_dr01", qty: 1,
      snapshot: { name, kcal, protein_g, carb_g, fat_g, fiber_g, sat_fat_g, sodium_mg } },
    { kind: "estimate",   name: "喜宴", size: "L" | null,
      snapshot: { kcal, protein_g, carb_g, fat_g, fiber_g, sat_fat_g, sodium_mg } },
  ],
  implicit: { oil_g: 10, seasoning: "normal" | "light" | null },   // 只有自煮才有
}
```

**計畫與紀錄用同一個格式，差別只在這幾個欄位什麼時候有值**：

| 欄位 | 計畫（`meal_plan.content`） | 紀錄（`daily_log.content`） |
|---|---|---|
| `ingredient` 的份量 | 不存；當天才依剩餘預算算主要槽位縮放 | 主要槽位的元件存 `scale`（實際吃的倍數，不取整；只有主要槽位會縮放） |
| `product` / `estimate` 的 `snapshot` | 建立計畫時就存（品項之後被改被刪，計畫不跟著變） | 存 |
| `implicit` | 存使用者選的用油/調味（沒選則存 null，當天套用預設） | 存實際採用的克數與程度 |
| 整餐營養合計 | 不存（未來預算未知） | 存 `totals`（快照，食材資料之後修正也不回溯改紀錄） |

- `product` 存 `qty`；推薦生成沿用角色上限（1 主餐＋1 配菜＋1 飲料＋1 點心、最多 3 件）；手動記錄只限制角色數量上限，不要求主餐（0.1 第 6 點）；主餐上限依時段：早餐、午餐、晚餐 2，下午茶、宵夜 1，其他角色各 1（常數在 `core/config.js`，decisions #41）。
- 允許混合（自煮配一瓶超商豆漿），統一格式後不是特例。
- **隱含成分**：自煮的一餐一律帶用油（`cooking_oil`，煎 5g、炒 5g＋有蔬菜 5g；基本資料「用油習慣」設少油時減半，這就是推薦、計畫、自己選共用的預設用油；「自己選」另可選 1 或 2 茶匙）與調味程度（清淡約 300 mg／一般約 700 mg 鈉；已選醬料時預設清淡）。兩者都**不跟主要槽位縮放**。調味程度是「鹽等值的鈉估計」，不代表醬油、不帶過敏原；溫沙拉的調味只代表煎肉調味，不含沙拉醬（decisions #38）；推薦卡片與自煮合計註明「未含沙拉醬」（骨架 `not_included`，章程 B7.5）。細節見章程 B5.6–B5.7。
- **鈉與飽和脂肪**只用於顯示：合計時有資料的部分照加，另外註明「部分品項無資料」，不因一項缺資料就整欄變空（章程 C4.5）。其餘營養素維持 null 傳染。
- `estimate` 元件：查不到品項時的匿名估算（喜宴、朋友家），只存在這一餐裡，不存成品項。

**daily_log 一筆的欄位**（Phase −1a 實作定案，decisions #33）：`{ id, log_date, slot, meal_type, source, name, content, totals, created_at }`

- `name`：記錄當下的顯示名稱，跟 `totals` 一樣是快照（品項之後改名或下架，紀錄照樣顯示當時的名稱）。
- `meal_type` 怎麼決定（原則：有明確的型態來源就用它，沒有才推導）：
  - 推薦的自組食譜：時段偏好是 `cook_quick`／`cook_full` 而且沒有退回一般推薦時，就是那個偏好；偏好是 auto 或退回時，才依食材與烹調法難度推導（都 ≤🟡 是 `cook_quick`，否則 `cook_full`）。
  - 推薦的現成品項組合：依來源（超商 `convenience`、外食與宅配餐盒 `delivery`；推薦組合不跨來源）。
  - 自己選（Phase 0 起）：**一律等於分頁的值**——超商分頁 `convenience`、外食分頁（含估算、含我的品項）`delivery`、自煮分頁是快煮/開伙子切換的值；飲料步驟不影響（decisions #47）。
  - Phase 2 起「照計畫記下」用計畫的有效型態（第 1 節解析規則）。
  - 型態一旦寫進紀錄就不再推導（第 11.2 節從紀錄存成組合時沿用紀錄的型態）。
- `source`：`rec_accepted`（記錄推薦）、`manual`（自己選）；`from_plan`、`backfill` 留給 Phase 2、3。
- `implicit`：−1b 起，自煮（`cook_quick`／`cook_full`）的紀錄一定是 `{ oil_g: 非負數, seasoning: "light" | "normal" | null }`（實際採用的用油與調味，章程 C4.11）；其他型態是 `null`。
- `data/db.js` 寫入前驗證以上欄位與 `content` 的結構（元件種類、各種元件的必填欄位、`implicit` 依型態（自煮必有用油與調味、其他是 `null`）；`totals` 的營養欄位缺值要寫 `null`，不能省略欄位）。

**預算規則**（沿用 v1 大餐預約的精神，泛化到所有計畫）：
- `product`／`estimate` 元件：熱量固定（用快照），**預先佔用**當天預算。
- `ingredient` 元件（自煮）：熱量有彈性，**不預先佔用**，當天才依剩餘預算算縮放倍數（範圍維持既有 0.5–2.0）。
- 計畫層絕對不存縮放後的熱量——未來某天的預算，存計畫的當下根本不知道。

## 4. 「記住上次選過的型態」（picker_last_meal_type）

`profile.meal_prefs[slot] = "auto"`（無偏好）時，「自己選」modal 要停在哪一個型態分頁，使用者要的是「記住我上次在這個時段選了什麼」，不是固定停在某個型態。

這是一個**容易不小心長成第三層隱性偏好**的功能，設計上要守住三條硬規則：

1. **只有送出成功才寫入**，點分頁、取消、看一眼都不算。
2. **推薦引擎、統計、首頁 hero 永遠不讀它**——它只決定 modal 打開時停在哪一頁，不影響任何建議或數字。
3. **每個時段只存一個值，直接覆蓋**，不記時間、不記次數、不留歷史。

存放位置：`settings` store 的一個 key（`picker_last_meal_type: { breakfast: "convenience", ... }`），不放進 `profile`（放 profile 就等於升格成 L1 了）。

完整解析規則：
```
modal 預設型態 =
    plan[date|slot].meal_type          （Phase 2 才有；Phase 0 固定 null）
 ?? meal_prefs[slot]（如果是有效型態值）
 ?? lastPicked[slot]（如果是有效型態值）
 ?? "convenience"                      （fallback：auto 時段多半是下午茶/宵夜，自煮選項很少，停在自煮畫面太空）
```

程式介面是 `engine/picker.js` 的 `resolveDefaultMealType({ planned, pref, lastPicked })`：engine 只收 `lastPicked` 值，不知道這個 setting key；`settings` 讀取失敗當成空物件，不擋 modal。這裡「不合法的偏好就往下找 lastPicked」跟推薦引擎「不合法的偏好退回預設偏好」刻意不同，不要合併成同一個函式。

**刻意接受的副作用**：使用者在 auto 時段每次都選超商，modal 會一直停在超商，但今日建議首頁卡片還是照樣可能推自煮——因為推薦引擎不讀這個狀態。不會因此跳出「要不要把這個時段設成超商？」之類的提示，那等於在分析使用者行為後推銷偏好，違反不評判原則。

## 5. 週規劃、人口數、採買清單

### 5.1 定位：週規劃＝泛化的大餐預約

v1 的大餐預約是「預先登記未來某天某時段要吃什麼、預扣當天預算、確認後才寫入 `daily_log`」。週菜單規劃要的是同一件事，只是也用在自煮上。**不另開一個平行的「週規劃」模組**，而是由 `meal_plan`（見第 1 節）承擔，入口是「餐點日曆」——每天五個時段的格子。聚餐、喜宴這類「大餐」就是一筆含 `estimate` 或外食 `product` 的計畫，沒有另外的大餐旗標。

### 5.2 情境：一人一盤，份量按人數放大

確認過使用者要的情境是「每人一盤同樣的菜，份量依人數放大」，不是「三菜一湯大家夾」的台式共食模型（後者的營養估算方式完全不同，明確排除在 2.0 之外）。

- `profile` 新增 `household_size`（預設 1，全域預設值）。
- `meal_plan` 條目可以逐筆覆蓋 `servings`（早餐通常只有自己吃、晚餐才是全家，不能只有一個全域值）。
- **`daily_log` 只記使用者自己那一份**，家人吃的不算進使用者的營養/熱量計算。

### 5.3 採買清單 —— 唯讀彙總視圖，不是獨立資料

採買清單本身**不存資料**，是一個純函式 `buildShoppingList(meal_plan 條目[], 日期範圍) → 清單列[]`，計畫一改就重新算。唯一需要存的狀態是「哪些品項已經打勾買了」。

**聚合邏輯**（MVP 範圍）：
```
只彙總日期範圍內、今天以後（含今天尚未記錄的時段）、meal_type 為 cook_quick 或 cook_full、已指定 content 的計畫條目
（meal_plan 沒有狀態欄位；已被 daily_log 取代的時段不算）
對每個 ingredient 元件：
  數量 = 該食材 serving_g（名目份量，不管當天縮放）× servings
  依「採買身分」（purchase_key）彙總，不是依食材資料庫的 id
用油（cooking_oil）與調味不列入（屬常備品）
```

**已知的隱藏複雜度**（MVP 都要處理，否則清單第一眼就會誤導人）。欄位名稱以章程 B4 為準，Phase 4 再補採買專用欄位：
- **熟重換生重**：米飯類主食（糙米飯、雜糧飯）是「熟重」基準，直接寫「糙米飯 1050g」會誤導使用者去買多一倍的生米。用食材的 `cooked_to_raw`（章程 B4，Phase −1b 就補上）換算。其他主食（地瓜、南瓜、毛豆仁用生重，燕麥、藜麥用乾重）本來就是買的狀態，不需要換算（decisions #35）。
- **可數食材用單位**：蛋要顯示「顆」不是克，Phase 4 補 `purchase_unit` / `g_per_unit`（來源優先用食物代換表），而且要對**總數**取整，不是逐餐取整再加總。
- **烹調法不是可以買的東西**：用 `axis` 判斷，`method` 與 `implicit` 不進清單。
- **常備品**：燕麥、醬油、鹽、油這類一次用量很少、家裡通常有的，標 `pantry: true`，清單分「要買」「家裡常備」兩區，不算進「要買」的總量。

**明確不做**（MVP 範圍之外）：超商/外食品項不進採買清單、包裝規格換算（「米一包 1.5kg」）、賣場分區排序、庫存追蹤、削皮去骨損耗、價格、自動排一週菜單、匯出分享。清單全面標示「估算」。

### 5.4 「複製上週」的兩個陷阱

1. **不能連大餐/一次性計畫一起複製**：預算會被預先佔用，複製後等於讓一次性大餐每週自動重複扣預算。規則：預設不複製含 `estimate` 元件的計畫（估算的一餐本來就是一次性事件，見第 9 節）；目的日期已經有計畫的時段預設跳過、不覆蓋；只複製到今天以後的日期。
2. **不能從「實際吃了什麼」（L3）複製**：這會讓紀錄反過來變成偏好來源，跟第 4 節「不能讓 lastPicked 變成隱性偏好」是同一類問題。只從 L2 計畫複製；上週沒排計畫就顯示「上週沒有排計畫」，並提供「用目前的長期預設（L1）預填」的選項。

## 6. PRD 核心原則風險與防呆規則

這份設計新增了兩個容易跟既有核心原則衝突的東西，明訂防呆規則：

### 6.1 不評判「超吃」/ 不製造全有全無心態

「計畫」這個概念天生帶有評判性（「有沒有照計畫吃」），這是節食心態的已知陷阱，必須從設計上堵住：

- **禁止**在任何 UI 顯示：遵循率、「偏離計畫」、「未完成」、紅色未打勾標記、連續照計畫天數、計畫 vs 實際的熱量差比較。
- 實際紀錄（L3）跟計畫（L2）不一樣時，計畫條目**默默**被取代，畫面只顯示實際吃的東西，不提示「跟計畫不同」。
- 過去日期裡沒被記錄的計畫條目，直接不顯示或灰掉，不顯示「漏掉」。
- `daily_log.meal_type` 是新增的高風險欄位——有了它就能統計「這週外食 5 次」。**任何 UI 不得依 meal_type 做頻率統計並搭配評價性文字或顏色**，不得出現「外食比較多喔」「多自己煮吧」。只能用在解析規則、採買清單、中性顯示（例如一個圖示）。
- 商品挑選清單**禁止**依熱量高低排序或用顏色區分熱量高低，維持資料原始順序。
- 加飲料步驟不做糖量警告，不預設選「無糖」。

### 6.2 運動與飲食脫鉤

- 計畫層與採買清單**永遠不計算、不顯示未來日期的熱量預算**，自煮份量一律用名目份量（不去推算「那天可能有運動」而調整份量）。
- `meal_plan`、`picker_last_meal_type` 等新資料結構**不得有任何欄位引用 `exercise_log` 或運動計畫**，也不做「今天有運動，預設停在高蛋白自煮」之類的聯動。

### 6.3 既有自組食譜原則（三輪審核定案，不可退化）

- 計畫內容（`MealContent`）裡的 `ingredient` 元件，必須落在對應餐型骨架該軸的 `allow` 清單內，數量符合軸上限（`COMPOSE_MAX`）——計畫層不能變成繞過骨架、自由湊食材的後門。（例外：使用者自己定義的「我的料理」是另一種元件，不綁骨架、不進推薦，見第 12.5 節。）
- 免開火（`sm_no_cook`）的食安檢查，在計畫「存檔當下」跟「顯示當下」都要各跑一次。
- 計畫條目在**顯示時**要重新跑 `passesHardFilters`（過敏原/飲食限制/不吃清單），因為規劃完之後使用者可能更新了設定，導致原本合法的計畫變成不合法——被擋下要顯示中性提示，不能默默刪掉。
- 超商/外食的「多品組合」繼續套用既有的品項角色上限，並依角色分區/排序顯示（主餐、配菜在前，飲料獨立一步），避免重現「前十幾張卡片全是飲料」的笛卡爾積式混亂。Phase 0 的具體做法：內建品項先依角色分區（主餐 → 配菜 → 點心），區內依 `category` 分組，組與組內都照資料原順序（不按熱量排）；「我的品項」例外，整組放在分頁最後、不進角色分區；被擋的品項排在組內最後、灰階並寫原因。

## 8. 已知限制與明確排除

- **不支援台式共食（三菜一湯大家夾）**的份量/營養模型，只支援「一人一盤，份量按人數等比放大」。
- **採買清單是估算**，主食份量用名目份量、不預測當天縮放倍數；不處理包裝規格、庫存、損耗、保存期限、價格。
- **`profile.meal_prefs` 不分平日/週末**，需要規律性差異時靠週規劃逐日設定＋複製上週。
- **`picker_last_meal_type` 刻意不影響推薦引擎**，modal 記得的型態跟首頁建議可能不同步，這是刻意的設計，不是 bug。
- **不做內建品項的修補/覆蓋層**：想「刪掉」一個內建超商/外食品項就隱藏它，想「改」就複製成自己的版本，不會出現「內建資料 + 使用者差異」的合併邏輯。
- **不加第五種型態**：外食型態的定義擴大成「不是自己煮、也不是超商——別人做的」，涵蓋喜宴/朋友家等查不到品項時的匿名估算，不會為了這些情境另開型態。
- **圖片政策**：品項卡片全面不配圖（含使用者自建品項），只有今日建議推薦卡片保留 5 張既有的時段插畫（早/午/下午茶/晚/宵夜）當背景墊底，不是逐品項配圖。

## 9. 美饗日曆的收斂（第三輪定案）

美饗日曆不維持獨立的品項策展身分，它的功能被「超商」「外食」型態分頁取代，**在 Phase −1a 直接移除**（decisions #16；沒有使用者資料要遷移，也沒有人在日常使用，不需要過渡期）。它原有的 4 項職責去向：

| 美饗日曆原有功能 | 新歸屬 | 什麼時候有 |
|---|---|---|
| S/M/L 匿名估算（喜宴、吃到飽、朋友家） | `estimate` 元件，外食分頁最上方「找不到？直接估算」卡片，只存在這一餐裡；S/M/L 熱量常數（400／700／1200 kcal）已在 −1a 放進 `core/config.js` 的 `ESTIMATE_SIZE_KCAL` | Phase 0 |
| 建立具名的自訂食物（v1 唯一的新增入口，靠有沒有填名稱猜意圖） | 拆成兩個明確動作：「只估這一次」（estimate）和「存成我的品項」（快速新增，含過敏原欄位）；猜意圖的做法廢除 | Phase 0 |
| 預約未來／直接記錄過去兩種模式，含「時段已過不能預約」檢查 | 餐點日曆依日期決定寫 `meal_plan` 或 `daily_log`（回填），時段結束時間檢查沿用 | Phase 3 |
| 預約狀態 reserved→confirmed→cancelled | `meal_plan` 不設狀態欄位。「確認」＝「照計畫記下」寫一筆 `daily_log`；「取消」＝刪掉計畫；過期沒記錄的計畫直接失效，不提醒、不標「未完成」 | Phase 2 |
| 撤銷一餐（`undoDailyLog` 寫在 feast.js，今日建議的撤銷按鈕呼叫它） | 搬進 `data/db.js` | Phase −1a |
| 今日建議把「今天的預約」當暫時紀錄算預算 | 刪除；Phase 2 起由 `meal_plan` 的固定熱量計畫取代 | Phase −1a 刪、Phase 2 取代 |

接受的空窗（沒有人在日常使用）：
- Phase −1a 到 Phase 0：不能新增自訂食物、不能記錄查不到的一餐。
- Phase −1a 到 Phase 3：沒有「回填過去日期」與「預約未來」的入口。

「複製上週」**跳過含有 `estimate` 元件的計畫**——估算的一餐本來就是一次性事件（喜宴、聚餐），不需要另外的大餐或「一次性」欄位。

**對核心原則的提醒**：美饗日曆原本讓「先把大餐排進去」變成一件光明正大、被系統鼓勵的事，這對「不評判超吃」是有正面作用的使用入口。身分收斂之後，這層意義不能跟著消失——餐點日曆的空格子、外食分頁的估算卡片，文案要延續這個精神（例如「有聚餐？先排進來，其他餐會自動幫你調整」）。

## 10. 使用者自建品項（「我的品項」，第三輪新增）

使用者要能自己新增/編輯/刪除超商或外食品項（例如超商出的新品、剛發現的健康餐廳），不用等開發端更新 `convenience_items.json`/`taiwan_items.json`。

### 10.1 資料模型：擴充 `custom_foods`，不開新 store

沿用 `custom_foods` 這個 store（一筆一個 key），程式碼裡概念稱「我的品項」。沒有舊資料，所有欄位一開始就照下面的格式（decisions #9）。

```js
{
  id: "custom_xxx",
  name,                                         // 必填
  channel: "convenience" | "delivery",          // 必填（從目前分頁自動帶入）
  role: "main" | "side" | "snack" | "drink",    // 必填，預設依時段（早午晚＝main，下午茶/宵夜＝snack）
  valid_slots: [...],                           // 必填，依 role 推預設，且一定包含新增當下的時段
  kcal,                                         // 必填，正數
  protein_g, carb_g, fat_g, fiber_g, sat_fat_g, sodium_mg,   // 選填，未填為 null
  vendor, category, note,                       // 選填
  allergen_tags: null | [],                     // 必有此欄；null=未確認（預設）／[]=確認不含／[..]=含這些
  vegan: false, lacto_ovo: false,
  copied_from: null | "<內建品項 id>",
  archived: false,                              // 軟刪除，只提供這個，不做硬刪除
  created_at, updated_at,
}
```
不存圖片欄位。`data/db.js` 提供 `updateCustomFood(id, patch)`。寫入驗證見章程 B8。

### 10.2 內建品項的「增減」：隱藏＋複製，不做修補層

- **隱藏**：`settings.hidden_catalog_uids`，選擇器和推薦引擎都要濾掉。這是使用者主動操作，推薦引擎可以讀它（跟 `picker_last_meal_type` 不同，那是被動累積、引擎不可讀）。跟「不吃食材」的語意不同——「不吃」是灰階顯示原因（我不要），「隱藏」是整個消失（這個已經不存在或買不到），不要合併成同一個機制。
- **複製成我的版本**：以內建品項為底建立一筆自建品項（`copied_from: seedUid`），同時自動隱藏原本的品項。之後開發端更新內建資料，使用者複製過的版本不會跟著動——刻意接受的落差，UI 用小字標示「從內建品項複製」，開發端補正內建營養資料時要知道這件事對已複製的使用者沒有效果。

### 10.3 填寫負擔：延續 `custom_foods` 現有的容錯精神

快速新增（在選擇器裡）只要**名稱＋熱量＋角色晶片**（角色有預設值：早午晚餐預設主餐，下午茶/宵夜預設點心；`channel` 從目前分頁自動帶入），其餘欄位收在「更多（選填）」。`valid_slots` 快速新增時務必包含目前這個時段，否則新增完在這個時段看不到它。

Phase 0 的表單欄位（decisions #48）：
- 必填區：名稱、熱量、角色晶片（主餐／配菜／點心／飲料）、過敏原（未確認〔預設〕／確認不含／含：勾選）。
- 飲食宣告「這個品項是：全素／蛋奶素／都不是（預設）」：使用者有設飲食限制時放在必填區，沒設時放在「更多」。
- 「更多（選填）」：蛋白質、碳水、脂肪、纖維、飽和脂肪、鈉（沒填是 null），以及上面的飲食宣告。
- `valid_slots` 依角色預設：主餐＝早午晚宵夜、配菜＝全部、點心＝下午茶與宵夜、飲料＝全部，再加上目前時段。
- **送出前預告**：以使用者目前的過敏原／飲食設定，這筆照現在填的會被擋時，用中性文字寫出是哪個設定擋住（例：「你設了過敏原『蛋』，過敏原未確認的品項不能選」），**不寫「改成確認不含就能選」這類引導**（章程 C4.1）。
- 宣告全素卻勾了含蛋、乳製品、魚、甲殼類、軟體動物（或蛋奶素卻含魚、甲殼類、軟體動物）時，中性提示矛盾，不擋存檔；我的品項只受章程 B8 驗證，B6.8 不適用（章程 B1）。「全素但過敏原未確認」不提示（未確認是預設值）。

### 10.4 一併修掉的既有漏洞：自訂食物完全不做過敏原檢查

v1 的 `passesHardFilters` 對自訂食物完全跳過過敏原檢查（`!item.is_custom` 例外），跟「未確認就保守排除」相反。**Phase −1b** 拿掉例外並在 `db.js` 加寫入驗證（`allergen_tags` 欄位必有，預設 null）；**Phase 0** 的快速新增表單帶過敏原欄位（未確認／確認不含／含…，預設未確認）（decisions #17、#27）。Phase 0 起有新增入口但還沒有編輯畫面：建立時就被擋的情況由「送出前預告」處理；**建立之後才設過敏原（或之後才改成素食、當初沒宣告）的人，舊品項會變灰且到 B-1 之前無處可改，只能重建一筆**——刻意接受，灰階照常寫原因（decisions #49）。`allergen_tags === null` 一律當未確認；只有使用者設過敏原/飲食限制時才會擋。B-1 的管理畫面上線後，被擋的品項灰階顯示「過敏原未填，點這裡補填」，點進去就是編輯畫面。

### 10.5 要不要進今日建議候選池：分兩階段

- **B-1（先做）**：只能在「自己選」/「餐點日曆」手動選。
- **B-2（之後）**：資料填得夠完整（`kcal`/`protein_g` 都有，過敏原已確認過）就依 `channel` 自動併入推薦候選池，不設每筆的「允許推薦」開關（不想被推薦已經有「不吃」清單可用）。管理畫面用中性語氣顯示每筆狀態（例如「補上蛋白質就會出現在建議裡」），不催促。

### 10.6 UI 位置

- **選擇器裡快速新增**：超商/外食分頁最後一組「我的品項」（預設收合）下方放「＋新增到我的超商/外食品項」。新增完：能選且同角色還有名額就直接選中（飲料選進飲料步驟）；被擋或名額已滿就不選中，提示原因。
- **管理畫面**：放在「基本資料」分頁的一個區塊，不新開頂層分頁，內容含列表（可搜尋）、編輯、封存/還原、已隱藏的內建品項清單（可取消隱藏）。這個畫面擴大成第 12.2 節的「食物資料」查詢，查詢與管理是同一個畫面。

## 11. 我的組合（2026-09-28 新增，依獨立審核修訂）

使用者常吃的幾套固定組合（例如「平日早餐：飯糰＋茶葉蛋＋豆漿」、「雞胸肉糙米快炒」），存起來之後可以直接引用，不必每次從頭選（decisions #31、#32；審核紀錄 [2026-09-28-my-combos](../collab/opus-review-log/2026-09-28-my-combos.md)）。

**命名**：畫面上叫「我的組合」；程式與資料一律叫 `saved_meals`／`SavedMeal`，避免跟推薦引擎既有的「多品組合」（`generateItemCombos`）混淆。

**定位**：組合是**單餐的範本**，不是週模板（不推翻 decisions #4）；不進 L1/L2 解析規則，也不會自動填進任何計畫或紀錄。

### 11.1 資料模型：新 store `saved_meals`

```js
{
  id: "saved_xxx",
  name: "平日早餐",                  // 必填；建立時自動帶「品項名稱以＋連接」，使用者可改；可重複（以 id 區分）
  content: MealContent,             // 見下表
  archived: false,                  // 刪除＝封存，不做硬刪除
  created_at, updated_at,
}
```

`content` 是 MealContent（第 3 節）的「範本形式」：

| 欄位 | 組合 | 跟計畫的差別 |
|---|---|---|
| `meal_type` | 存來源那一餐的型態（建立時就知道，不另外推算） | 相同 |
| `ingredient` | 只存 `axis`、`ref`、`is_primary`；份量不存，引用當天依剩餘預算算主要槽位縮放 | 相同 |
| `product` | 只存 `ref`、`qty`，**不存 `role`、不存 `snapshot`**；角色與營養每次即時從 catalog（含我的品項）讀 | 計畫存快照；組合是長期範本，內建資料修正後應該跟著更新 |
| `estimate` | **不允許** | 估算的一餐是一次性事件（第 9 節） |
| `implicit` | 入口 1（「自己選」送出）：使用者在選擇器裡主動改過用油／調味才存值，否則 `null`；入口 2（從紀錄存）：一律 `null`。`null`＝引用時套用當下的預設用油與調味 | 相同 |
| 營養合計 | 不存 | 相同 |

- **轉換只有兩個函式，都在 `engine/meal-content.js`**（章程 C2），兩個建立入口依序呼叫：
  1. `toSavedContent(mealContent, { keepImplicit })`：純結構轉換，去掉快照、`role`、縮放倍數與合計。`keepImplicit` 為 true 時保留 `implicit`，否則設 `null`。入口 1 傳入「使用者是否在選擇器裡改過用油／調味」；入口 2 一律傳 false（紀錄裡分不出當時是預設還是使用者指定）。
  2. `remapSavedRefs(savedContent, catalog, hidden, customFoods)`：套用 11.3 解析規則 1–2（隱藏且有複製版本 → 換成複製版本；查不到或隱藏且無複製版本 → 移除），回傳 `{ content, dropped }`。`dropped` 非空時，存檔前用中性文字列出「以下品項已不提供，不會存進組合」。`resolveSavedMeal` 的規則 1–2 也呼叫同一個函式。
- **驗證分兩層**（章程 C1）：
  - `data/db.js` 寫入時只做結構驗證：名稱非空、至少 1 個元件、沒有 `estimate`、`product` 有 `ref` 與 `qty` 且沒有 `snapshot`／`role`。
  - 語意驗證（角色數量上限、骨架 `allow` 與軸上限、免開火食安）由 ui 在寫入前呼叫 engine 完成；用手動記錄規則（章程 C4.8），**不檢查時段**。
- 真正記錄時，照第 3 節寫進 `daily_log`，那一刻才存商品快照與 `totals`。

### 11.2 建立

兩個入口，都是使用者明確操作：
1. 「自己選」送出時可勾「存成組合」，名稱欄預先填好自動名稱。
2. 已記錄的一餐可以「存成組合」。**含 `estimate` 元件的那一餐不提供這個選項**。已下架或已隱藏的品項依 11.1 的 `remapSavedRefs` 處理（有複製版本就換成它，沒有才不存）。之後語意驗證若不通過（例如骨架已經改過），用中性文字列出原因、不存檔。

入口 2 是從 L3（實際紀錄）建立範本。第 5.4 節禁止「從 L3 複製成計畫」，理由是不能讓紀錄被動變成偏好來源；這裡是使用者對單一一餐的明確操作，不是系統依紀錄推導，所以不衝突。比照第 4 節的精神：**不得依紀錄頻率提示「你常吃這個，要存成組合嗎？」**，也不記使用次數。

### 11.3 引用

**解析只有一個函式**：`engine/meal-content.js` 的 `resolveSavedMeal(saved, catalog, profile, hidden, customFoods)`，回傳「可用元件」「被擋元件與原因」「已不提供的元件」。所有引用都經過它（章程 C4.16）。規則是**元件級**：

1. `ref` 查不到（已下架，或我的品項已封存）→ 歸「已不提供」。
2. `ref` 在 `hidden_catalog_uids` 裡：若有未封存的我的品項 `copied_from === ref`，改用那一筆（使用者「複製成我的版本」後組合自動跟上）；否則歸「已不提供」。隱藏的語意是「已不存在或買不到」（10.2），比照下架處理，不是灰階阻擋。規則 1–2 由 `remapSavedRefs` 實作（11.1），建立與引用共用。
3. 硬性過濾（過敏原/飲食限制/不吃清單）沒過 → 歸「被擋」，附原因。
4. 自煮部分依**目前的**骨架重新驗證（骨架或食材資料可能改過）：`archetype_id` 已不存在 → 所有自煮元件歸「被擋」（原因「這個餐型已不提供」）；食材不在該軸 `allow` → 該元件歸「被擋」（「這個餐型目前不提供這個食材」）；超過軸上限 → 依 `components` 順序，後面超出的歸「被擋」；違反免開火食安（章程 C4.3，引用等同顯示，要再檢查一次）→ 需要加熱的食材歸「被擋」（「免開火不能搭配需要加熱的食材」）。
5. 角色一律用 catalog 當下的 `role`；超過角色數量上限時，依 `components` 順序，後面超出的元件歸「被擋」。
6. `valid_slots` 是瀏覽用的過濾，**不是安全規則**：組合帶入的元件不受時段限制；骨架驗證也不檢查時段。

畫面：
- 「自己選」三分頁上方一列「我的組合」，**列出全部組合**（不分型態），每張顯示名稱、型態小圖示，名稱下小字列內容與熱量（依今天剩餘預算算出）。有元件不能用時，卡片加一行中性文字「有 N 項目前不能用：原因」。
- 只要還有可用元件，卡片就可以點；「可用元件」是 0 個時整張灰階、**不能點**，卡片上的中性文字說明原因。點選後切到組合的型態分頁（自煮含快煮/開伙子切換），把可用元件帶入選擇器；被擋與已不提供的元件不預選。已帶入的元件在選擇器裡一律顯示（即使不在這個時段的 `valid_slots`），可以取消。確認後才記錄，不做一鍵直接記錄。
- 餐點日曆（Phase 3 起）：引用組合一律**帶入三分頁編輯器**，不直接填入計畫或紀錄（回填過去日期會直接寫 `daily_log`，一樣要經過確認）。日曆情境的組合卡片**不做預算縮放**：只顯示商品的固定熱量，自煮部分寫「份量當天決定」（第 6.2 節：不計算未來日期的預算）。填進計畫的當下照計畫規則補上商品快照。
- 組合的排列：使用者建立的順序，不依熱量排序、不上色（第 6.1 節）。

### 11.4 推薦

**推薦引擎、統計、hero 都不讀 `saved_meals`**，組合只供手動引用（章程 C4.16）。之後若要讓組合進推薦候選，屬 C3 需審核的變更，且只能放符合推薦生成規則（章程 C4.7、低碳）的組合。

### 11.5 管理

「基本資料」分頁一個獨立的「我的組合」區塊（不依賴平行工作線 B-1）：列表、改名、**編輯內容**（用同一個選擇器直接編輯、存回同一筆，見第 12.6 節）、刪除（封存）/還原。改名、編輯或刪除不影響已記錄的餐（紀錄有自己的快照）與已排的計畫（計畫有自己的內容）。

### 11.6 匯出匯入（平行工作線 B-3）

組合引用我的品項的 id。匯入時 `saved_meals`、`custom_foods`、`hidden_catalog_uids` 在同一個 IndexedDB transaction 寫入；若匯入會重新產生我的品項 id，要同步改寫組合裡的 `ref`。第 12 節新增的 `custom_ingredients`、`custom_recipes` 也在同一個 transaction，id 改寫要連動（我的料理引用我的食材、組合引用我的料理）。

## 12. 食物資料：查詢與修訂（2026-09-29 新增，草案，待獨立審核）

使用者要能單獨查任何食物或食材的營養成分、能在哪些餐出現，也要能增加與修訂。第 10、11 節只涵蓋「我的品項」與「我的組合」的一部分，這一節把整件事一次定義（decisions #50–#56）。

### 12.1 原則：三層資料，只有使用者自己的那層能改

| 層 | 內容 | 使用者能做的 |
|---|---|---|
| 1. 基礎食材 | 衛福部食品營養成分資料庫（`data/reference/tfda-2025-update1.json`，2213 筆）與由它產生的 `data/ingredients.json` | 只能查。可以「加進我的食材」（數值照抄、不能改） |
| 2. 內建資料 | 內建超商／外食品項、自煮的食材與餐型骨架 | 只能查。內建品項可以「隱藏」或「複製成我的版本」（10.2）；食材與骨架由開發端維護（章程 B1、B7） |
| 3. 使用者的資料 | 我的品項（10）、我的食材（12.4）、我的料理（12.5）、我的組合（11） | 新增、修改、封存／還原 |

- **出處一律標示**：每個營養數字標「衛福部」「包裝標示」「估算」或「你填的」。使用者改過的東西一眼看得出來，App 附的原始數字不會被蓋掉。
- **推薦的邊界不變**：第 3 層只用在手動記錄（「自己選」、餐點日曆）。我的品項照 10.5 的 B-2 規則才進推薦；我的食材、我的料理、我的組合不進推薦（之後要改屬 C3，要審核）。
- **修改只影響之後**：紀錄存了快照與合計（第 3 節），計畫存了自己的內容（第 1 節），修改任何資料都不回溯。

### 12.2 食物資料查詢（唯讀入口）

- 位置：「基本資料」分頁的「食物資料」區塊，跟我的品項管理畫面（10.6）是同一個畫面，不新開頂層分頁。
- 搜尋範圍：基礎食材（含衛福部全表）、內建品項、我的品項、我的食材、我的料理、我的組合。可以依種類篩選。衛福部全表體積大，查詢時才載入精簡版（只留營養欄位與名稱、俗名、分類、內容物描述）。
- 每一筆的明細：
  - 一份的熱量、蛋白質、碳水、脂肪、纖維、飽和脂肪、鈉（食材另列每 100g 與一份幾克、生熟狀態）；
  - 過敏原、全素／蛋奶素；
  - **能在哪些餐出現**：品項列 `valid_slots`；食材列「出現在哪些餐型、那些餐型的時段」；
  - 出處（上面的四種標示；衛福部的附整合編號）；
  - 狀態：已隱藏、已封存、以目前設定會不會被擋（中性文字，跟選擇器同一套原因）。
- 動作：唯讀的那幾層是「加進我的食材」「複製成我的版本」「隱藏」；我的資料是「編輯」「封存」。
- 排序與呈現：依名稱或資料原順序，不依熱量排、不上色（第 6.1 節）。

**成分明細**：選擇器的摘要與推薦卡片可以展開，列出每個成分各佔多少熱量與蛋白質（例：糙米飯 1.2 倍 約 220 kcal、雞胸 約 130 kcal、用油 5g 約 44 kcal）。由 engine 提供，ui 不自己算（章程 C4.11）；只顯示數字，不評判。

### 12.3 內建餐點的修訂：複製後再改，外加份量倍數

- 維持 10.2：不做修補層。「複製成我的版本」之後，所有欄位都能改（名稱、角色、`valid_slots`、營養成分、過敏原、素食、說明）；原本那筆自動隱藏。
- **份量倍數**：選擇器裡已選的商品可以改份量（0.5、1、1.5、2 份），寫進 MealContent 的 `qty`（格式已支援），合計照乘。解決「便當飯只吃一半」「兩顆茶葉蛋」這類情況，不必為了份量另建一筆。倍數只影響這一餐。

### 12.4 我的食材（新 store `custom_ingredients`）

```js
{
  id: "cing_xxx",
  name,                                   // 必填
  source: "tfda" | "user",                // tfda＝從衛福部資料庫加入；user＝完全自填
  tfda_id: "A0100101" | null,             // source 是 tfda 時必有
  per_100g: { kcal, protein_g, carb_g, fat_g, fiber_g, sat_fat_g, sodium_mg },  // tfda：照抄、不能改；user：kcal 必填，其餘可 null
  default_g,                              // 必填：一份幾克
  allergen_tags: null | [],               // 同 10.1；null＝未確認
  vegan: false, lacto_ovo: false,
  requires_cooking: true | false,         // 需要煮熟嗎；預設 true（保守）
  archived: false, created_at, updated_at,
}
```

**定位：我的食材就是使用者的「常買清單」**（decisions #56）。流程是「衛福部食材 → 我的食材 → 自組」：先從衛福部全表挑自己實際會買的，之後自組只從這份短清單挑，不必每次在兩千多筆裡找。

- **加入**：在「食物資料」搜尋衛福部全表（名稱或俗名，例：打「雞胸」），挑選後「加進我的食材」。名稱預帶樣品名稱，可以改；數值照抄，編輯畫面唯讀並標「衛福部 整合編號」。
- **完全自填**：包裝食品（某牌豆干）照包裝標示填，標「你填的」，數值都能改。
- **內建食材也能標常買**：`ingredients.json` 的內建食材可以一鍵標成常買（存在 `settings.pantry_ingredient_ids`，只存 id，不複製數值）。
- **生重**：衛福部數值大多是生重每 100g，表單寫明「克數照買來、煮之前的重量填」；衛福部的「內容物描述」（生、熟、去殼…）在明細裡顯示。
- **過敏原**：衛福部資料沒有過敏原欄位，加入後預設未確認，要使用者自己勾（有設過敏原的人要勾「確認不含」才選得到，同 10.3 的送出前預告）。
- **用途**：
  1. 「我的料理」的食材選單只列常買清單（我的食材＋標了常買的內建食材）；臨時要用沒列的，可以在同一個畫面搜尋、當場加入。
  2. 自煮分頁的餐型選項裡，標了常買的內建食材排前面並加標記，**不隱藏其他選項**（常買清單還沒建好時也選得到）。
  3. 不放進餐型骨架（骨架的 `allow` 由開發端維護，章程 B7），**不影響推薦**。之後若要讓常買食材在推薦加分，屬 C3 改推薦演算法，要另外審核。
  4. Phase 4 採買清單的 `pantry`（家裡常備）之後可以接這份清單。

### 12.5 我的料理（新 store `custom_recipes`）

使用者自己的菜：用食材（基礎食材＋我的食材）加克數自由組成，營養由食材加總。

```js
{
  id: "crec_xxx",
  name,                                   // 必填
  meal_type: "cook_quick" | "cook_full",  // 必填，使用者選
  ingredients: [{ ref, grams }],          // 至少 1 項；ref 是 ingredients.json 或我的食材的 id；用油、調味也用食材表示（cooking_oil、seasoning_*）
  servings: 1,                            // 這份食譜做幾份；記錄一份＝總量 ÷ servings
  role: "main" | "side" | "snack",
  valid_slots: [...],                     // 規則同 10.3
  note,
  archived: false, created_at, updated_at,
}
```

- 營養：食材每 100g × 克數加總 ÷ 份數，null 照章程 C4.5 傳染（鈉、飽和脂肪例外）。
- 過敏原與素食由食材推導：任一食材過敏原未確認 → 整道未確認；全部食材都宣告全素才算全素（章程 B6.4、C4.2 的精神）。不另外讓使用者勾。
- 免開火：沒有烹調法概念，不套免開火檢查；`requires_cooking` 只在查詢頁顯示。
- **例外（修正第 6.3 節）**：我的料理不綁餐型骨架、不受軸上限。6.3 的「計畫層不能繞過骨架」是為了推薦與計畫的組合品質；我的料理是使用者自己定義的菜，只用在手動記錄與手動排進計畫，不進推薦，所以另開一條路，不放寬骨架本身。
- 在選擇器裡的位置：自煮分頁「選餐型」上方一組「我的料理」，選了就是整道菜（可以改份量倍數），不再選餐型與食材。記錄時 `meal_type` 用料理自己的值，子切換跟著切過去。
- 在 MealContent 裡怎麼記（**待審核決定**）：
  - 方案 A（建議）：新增元件種類 `{ kind: "recipe", ref, qty, snapshot }`，快照存這一份的營養；`implicit` 記 `{ oil_g: 0, seasoning: null }` 並在元件上註明用油已在食材裡。這是 MealContent 格式的變更（0.1 第 4 點說 −1 定案），要改 `db.js` 驗證與相關加總。
  - 方案 B：把料理的每個食材攤成 `ingredient` 元件並加上 `grams` 欄位。格式變動更大，而且紀錄看不出是哪道料理。

### 12.6 我的組合改成可以直接編輯（修正第 11.5 節）

- 管理區塊多一個「編輯內容」：用同一個三分頁選擇器打開這個組合的內容，存回同一筆（更新 `updated_at`），不再要求「帶入 → 調整 → 另存 → 封存舊的」。
- 存檔前照 11.1 的兩層驗證；不影響已記錄的餐（有快照）與已排的計畫（有自己的內容）。
- 組合裡的商品本來就即時讀品項資料（11.1），所以編輯我的品項後，引用它的組合自動跟上；我的料理同理（組合只存 `ref`）。
- 組合可以包含我的料理（元件 `recipe`，只存 `ref`、`qty`）。

### 12.7 資料驗證與章程

- `custom_ingredients`、`custom_recipes` 比照章程 B8 的「我的品項最低驗證」：必填欄位、數字非負、`allergen_tags` 必有、ref 存在（我的料理的食材不能指向已刪除的東西；指向已封存的我的食材時，照 11.3 的「已不提供」規則處理）。要在 CHARTER B1 表格與 B8 補上這兩個 store（C3，跟這一節一起審）。
- 衛福部資料照抄的數值，檢查程式要能驗證跟 `data/reference/` 完全相等（章程 B12 的精神），使用者不能改。

### 12.8 不做

- 使用者修改基礎食材或內建資料本身的數值（修補層）。
- 使用者新增或修改餐型骨架、把我的食材加進骨架。
- 我的食材、我的料理、我的組合進推薦（之後要做屬 C3）。
- 依使用頻率提示「要不要存成料理／組合」（第 4 節、11.2 的精神）。
