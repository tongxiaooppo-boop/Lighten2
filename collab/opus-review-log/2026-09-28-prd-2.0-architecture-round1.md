# PRD 2.0 架構討論 — 第一輪跟 Opus 的完整問答

日期：2026-09-28
背景：使用者原本要交給 Cline 的任務是「自己選 modal 拿掉現成品項模式」，討論中發現這個分類跟 profile 的
`meal_prefs`（超商/外食/自煮快煮/自煮正常煮）脫節，使用者拍板要整份 PRD 開 2.0：
每一餐都要能有「型態」（超商/外食/快煮/開伙），可自動建議也可自選；自選時各型態要能定義食材或成品；
使用者可規劃一整週的快煮/開伙菜單，設定人口數後產生採買清單。

## 送給 Opus 的完整 prompt

（見本次 session 的 Agent 呼叫內容，逐字如下）

你是獨立架構審核者，被找來跟另一個 Claude session（負責這個專案日常開發）討論一個手機減脂追蹤 App「輕盈計畫」的 PRD 2.0 架構設計。這是開放式的架構共同設計討論，不是審核一份已經寫好的提案——請你自己判斷架構該怎麼切、指出風險、提出你認為更好的替代方案，不用附和使用者或現有 Claude session 的既有想法。

# 專案現況（給你判斷用的背景，不是要你照抄）

這是一個純前端（vanilla JS，無框架，localforage/IndexedDB 做本地儲存）的個人減脂飲食追蹤 App，沒有後端伺服器，沒有多使用者。核心分頁：
1. **今日建議**（`js/ui/tab-today.js`）：引擎（`js/engine/recommend.js`）依使用者 profile 自動算出五個時段（早餐/午餐/下午茶/晚餐/宵夜）的建議餐點，也有「自己選」手動覆蓋 modal。
2. **美饗日曆**（`js/ui/tab-ledger.js`）：使用者手動預約/記錄「大餐」（外食/超商/連鎖健康餐盒），跟今日建議的自動引擎邏輯是分開的兩條路。
3. **基本資料**（`js/ui/tab-profile.js`）：使用者填年齡/體重/活動量/過敏原/飲食限制，並且已經有一個逐時段的「來源偏好」設定：`profile.meal_prefs = { breakfast: "convenience", lunch: "convenience", afternoon_tea: "auto", dinner: "cook_full", snack: "auto" }`，每個時段可選 `off`/`auto`/`convenience`/`delivery`/`cook_quick`/`cook_full`。這組值目前只拿來過濾「今日建議」引擎的候選池（`filterBySource()`），沒有平日/週末區分（舊版本原本有 `prep_time_weekday/weekend` 全域設定，後來被這個逐時段設定取代並拿掉了）。

推薦引擎候選池的三個資料來源（`recommend.js` 開頭註解）：
- 自組食譜：`data/dish_archetypes.json`（目前只有 5 個「餐型骨架」），槽位參照 protein_sources.json/staples.json/sauce_methods.json/raw_ingredients.json，每個食材項目有自己的 serving_g。這套「餐型骨架＋食材軸」的自組邏輯經過三輪 Opus 審核才定案，目前也用在「今日建議→自己選→自己煮」手動組餐 modal。
- 超商即食品項：`data/convenience_items.json`，引擎本來就會把超商品項組成「多品項組合」（generateItemCombos）。
- 台式外食/連鎖健康餐盒：`data/taiwan_items.json` + convenience_items.json 裡 channel=delivery 的品項。

今天原本要做、現在要整個作廢重寫的任務：使用者原本要把「自己選」手動組餐 modal 裡「現成品項模式」跟「自己煮模式」的雙模式切換，直接刪掉現成品項模式只留自己煮。但討論到一半，使用者發現這兩個模式的存在本身就是因為「自己選」modal 的分類邏輯跟 profile 那套 meal_prefs 完全脫節、各搞一套，才會搞出重複又矛盾的東西。

資料紀錄現況：daily_log（source_type 目前有 manual_composed 等值）跟 feast_reservation（大餐預約，只能存單一品項，還沒有飲料欄位——使用者上一輪提的、還沒動工的需求）。

# 使用者今天提出的 PRD 2.0 新需求（原話翻譯整理，如實轉達）

1. 每一餐（五個時段）都要能有「型態」，型態可以「建議自動帶入」也可以「使用者自選」——型態分四大類：超商、外食、快煮、開伙。
2. 使用者自選時，四種型態各自都要能定義成「食材」（自己組合/自組）或「成品」（單一現成品項）——不是只有開伙才有這個區分。
3. 使用者可以「設定一週」的快煮/開伙菜單——這是全新概念，現有系統完全是「單日/單餐」運作。
4. 設定「人口數」後，系統依照這一週規劃好的快煮/開伙菜單，彙總需要的食材份量，產生一份「採買清單」——全新功能。

使用者明確說「需要整個程式翻新了」，並要求「整個 PRD 做一個 2.0」。

# PRD 對這個 App 的核心既有原則（供你判斷新設計會不會踩線）

- 運動與飲食資料要架構上跟心理上都完全脫鉤。
- 不評判使用者「超吃」，只陳述數字不歸因。
- 彈性點數獨立於運動之外。
- 「自組食譜」的槽位設計原則：不對稱槽位、每個食材自己的份量基準、避免無限制笛卡爾積湊出荒謬組合。

# 要求 Opus 回答的問題

1. 「型態」概念應該放在哪個資料層級？升級 profile.meal_prefs 還是獨立「週菜單規劃」結構？兩者要不要同時存在（長期預設＋當週覆蓋＋當日臨時覆蓋，三層）？
2. 「食材 vs 成品」二分法套用到四種型態，資料結構能不能共用同一套？
3. 「一週菜單＋人口數＋採買清單」架構上怎麼設計？MVP 範圍該砍多小？有沒有隱藏複雜度？
4. 有沒有踩到 PRD 核心原則風險？
5. 怎麼分階段？今天的 Cline 任務要作廢還是先做中繼版本？
6. 使用者這個新想法有沒有整體方向有問題、該被推翻或大幅簡化的部分？

## Opus 的完整回覆

（審核依據：Opus 另外直接讀了 repo：js/engine/recommend.js、js/engine/feast.js、js/database.js、data/*.json schema、輕盈計畫PRD_v4.0.md 5.1–6.3 節、collab/to-cline.md）

### 0. 先講結論

1. 不要做「整個程式翻新」。現有核心（每日動態預算、passesHardFilters 共用硬性過濾、餐型骨架加主要槽位縮放、體重趨勢校正）是健全的，2.0 不該碰它們。2.0 真正要加的只有兩樣：(a) 一個統一的「一餐內容」資料格式；(b) 一個以日期×時段為 key 的「餐點計畫」store。採買清單只是建在 (b) 上面的一個唯讀彙總視圖，不需要自己的資料。
2. 最重要的發現：「週菜單規劃」跟「大餐預約」其實是同一個概念。feast_reservation 本來就是「未來某天某時段、預先登記要吃什麼、會先重新分配當天預算、吃完才寫進 daily_log」。週菜單也是這樣。2.0 不該多開一個平行的週規劃模組，應該把大餐預約泛化成「餐點計畫」，美饗日曆也就變成這個計畫的日曆視圖。不這樣做，會有兩個 store 都代表「未來要吃的餐」，預算重算要讀兩邊，還得處理兩邊衝突。
3. 「四型態 × 食材/成品」的 8 格矩陣，建議不要做成使用者看得到的概念。超商和外食的「自組」，本質是「多個現成品項組合」，不是「食材」。真正的食材層級只存在於自煮。這個二分法應該是資料的內部屬性（元件是 product 還是 ingredient），使用者看到的只有型態。
4. 「快煮」「開伙」在資料層是同一種型態（自煮），差在備餐難度上限。UI 可以保留這兩個詞，資料上不該拆成兩個平行型態。
5. 今天那份 Cline 任務（刪掉現成品項模式）請作廢，方向跟 2.0 相反。2.0 要的是「現成品項選擇器依型態過濾保留、模式切換換成型態切換」，不是刪掉它。任務裡的 Part 4（蛋白質/蔬菜多選）跟 2.0 無關，可以保留照做。
6. 採買清單有好幾個使用者大概沒想到的硬問題：主食是熟重要換算成生重、自煮份量每天會隨預算縮放、家人份量跟使用者的減脂份量不同、調味/烹調法混在同一個池子裡。MVP 要砍得很小，而且要誠實標示「估算」。
7. 最大的範圍疑問要先問使用者：「開伙＋人口數」如果指的是全家共食的台式家常菜（三菜一湯、大家夾），目前「一人一盤」的餐型骨架模型根本不適用。這件事一定要先確認再開工。

### 1. 方向性問題：哪些應該推翻或大幅簡化

#### 1.1 推翻：「需要整個程式翻新」
使用者說「整個程式翻新」，但看完程式碼的判斷是：2.0 需求幾乎全部是加一層（計畫層），不是替換既有層。推薦引擎、硬性過濾、預算、體重校正、餐型骨架都不用重寫。一次性重寫會把三輪 Opus 審核才定案的東西（非對稱槽位、各食材自己的 serving_g、主要槽位 0.5–2.0 縮放、防笛卡爾積）整批重新暴露在退化風險裡，卻換不到任何功能上的收益。2.0 應該是增量加上一次資料格式統一，不是大爆炸重寫。

#### 1.2 大幅簡化：「四種型態各自都要能定義成食材或成品」
逐一檢查：
- 超商：「成品」＝買一個便當；「食材自組」＝沙拉加茶葉蛋加豆漿。後者其實仍然是多個現成商品，營養值固定、不能縮放，跟自煮的食材（有 serving_g、可以縮放）本質不同。引擎早就用 generateItemCombos 做多品組合了。所以超商的二分法其實是「單品 vs 多品」，不是「成品 vs 食材」。
- 外食：一樣只有「單品 vs 多品」。唯一真正有「自組」意義的外食是自助餐（按菜色夾），但自助餐的逐菜營養估算非常不可靠，資料也沒有，建議明確列為 2.0 不做。
- 快煮/開伙：這才是真正的食材自組（餐型骨架）。至於「成品」：自煮的成品是什麼？冷凍水餃、微波調理包？那在資料上就是超商品項。硬把「自煮成品」塞進自煮型態，只會讓同一個品項出現在兩個型態裡。

結論：使用者心裡想的「每個型態都能選單一或組合」可以滿足，但實作上是一個統一的「元件清單」資料格式（見第 3 節），UI 依型態自動決定要開哪一種選擇器，不要讓使用者面對一個「食材/成品」切換開關。這個開關正是今天模式切換造成混亂的根源，2.0 不該換個名字再做一次。

#### 1.3 簡化：「快煮」「開伙」不是兩種型態
現行 filterBySource：cook_quick 是自組食譜且 tier≤🟡，cook_full 是自組食譜且 tier 不限（包含🟢🟡）。開伙是快煮的超集，不是互斥的一類。對週規劃和採買清單來說，兩者完全沒差，都要食材。
- 資料層：meal_type: "cook" 加上 max_tier: "quick" | "full"。
- 當計畫條目已經選好具體食譜時，tier 可以從食譜本身推導出來，不需要另外存（避免存衍生狀態）。max_tier 只對「只指定型態、還沒選內容」的條目有意義，用途是給引擎過濾候選池。
- UI 可以繼續顯示「快煮/開伙」兩顆按鈕，對使用者沒有損失。
- 「開伙」要不要等於現在的「正常煮」？判斷是：開伙＝cook_full（tier 不限）。但如果使用者講的「開伙」其實是「為全家煮」的意思，那是另一回事，見 1.4。

#### 1.4 必須先問使用者：「開伙＋人口數」是什麼意思？
目前 5 個餐型骨架全部是一人一盤的模型，份量是依使用者自己的減脂預算縮放的。使用者一提「人口數」，情境很可能是替家人一起煮。這時候有兩種完全不同的情況：
- A. 每人一盤同樣的菜，家人份量不同：還能用現有模型，採買量＝每道菜名目份量×人數，使用者自己的那一份照常縮放。MVP 可行。
- B. 台式共食（三菜一湯、大家夾）：使用者吃到的是共享菜色的「某個比例」。營養估算要改成「整道菜營養 ÷ 使用者夾的比例」，整套自組邏輯跟份量縮放邏輯都不適用。這是另一個產品，不該混進 2.0。

請現有 session 在寫 PRD 之前，務必先跟使用者確認是 A 還是 B。如果是 B，採買清單這條線要整個重新討論。

#### 1.5 資料廣度才是週規劃的真正瓶頸（使用者大概沒意識到）
自組食譜目前只有 5 個餐型骨架，午晚餐能用的只有 3 個（炒類、烤/舒肥定食、溫沙拉）。一週如果有 7–14 餐要自煮，換蛋白質、蔬菜雖然能變化，但「菜的樣子」一週會重複 4–5 次。週規劃功能做得再漂亮，使用者規劃兩週就會覺得單調。擴充餐型骨架（例如湯麵類、蒸類、滷類、便當類）應該列為 2.0 的平行工作線，而且每個新骨架都要照三輪審核定下的原則逐一設計，不能為了數量亂塞。

### 2. 「型態」放在哪個資料層級？跟今日建議是什麼關係？

#### 2.1 答案：三層，但只有兩層需要新資料

| 層 | 資料 | 性質 | 狀態 |
|---|---|---|---|
| L1 長期預設 | profile.meal_prefs[slot] | 每個時段一個型態，沒有日期 | 已存在，保留，暫不加平日/週末 |
| L2 餐點計畫 | 新 store meal_plan，key＝date\|slot | 某天某時段：只指定型態，或型態＋具體內容 | 新增（也吸收 feast_reservation） |
| L3 實際紀錄 | daily_log | 真的吃了什麼 | 已存在，加 meal_type 欄位 |

「當日臨時覆蓋」不需要獨立一層：今天臨時改主意，就是改今天的 L2 條目，或直接記錄到 L3。多一層就多一套優先順序要維護，沒有收益。

解析規則（整個 2.0 最核心的一條規則，要寫進 PRD）：
```
某天某時段的有效型態 = meal_plan[date|slot]?.meal_type  ??  profile.meal_prefs[slot]
某天某時段的顯示內容 =
   已有 daily_log 紀錄        → 顯示已記錄（跟現在一樣）
   meal_plan 有指定 content   → 顯示計畫內容（不跑引擎，但要重跑 passesHardFilters 驗證）
   否則                       → 引擎依有效型態 filterBySource 產生建議（跟現在一樣）
```
今日建議的即時引擎完全不用改演算法，只是多一個輸入（有效型態），外加「計畫已指定內容時不跑引擎」。

#### 2.2 為什麼 L1 暫時不加平日/週末
- L2 已經能處理「這週六晚餐我要開伙」，而且能表達得更精確。
- 平日/週末各一組是 L1 跟 L2 之間的一個折衷層，之前的 prep_time_weekday/weekend 就是這樣被拿掉的。在使用者還沒證明「每個週末都要手動改同樣的東西」之前，不要把它加回來。
- 真的需要時，用「複製上週計畫」這個動作比加一個週模板資料結構便宜得多。

#### 2.3 計畫條目兩種粒度，都要支援
- 只有型態：{meal_type: "cook", max_tier: "quick", content: null}，意思是「那天晚餐我會快煮，內容讓引擎當天建議」。這其實就是逐日期覆蓋 meal_prefs，而且不進採買清單（內容還不知道）。
- 型態＋內容：{meal_type: "cook", content: {...}}，意思是固定菜單，會進採買清單。

#### 2.4 預算：固定熱量 vs 彈性熱量（泛化大餐預約的關鍵規則）
PRD 6.3 規定預約中的大餐要「事先重新分配當天預算」。泛化到計畫之後：
- product 元件（超商、外食、大餐）：熱量固定，跟現在的預約大餐一樣，預先佔用當天預算。
- ingredient 元件（自煮）：熱量有彈性（主要槽位可以縮放 0.5–2.0），不預先佔用固定值。當天由 achievableNutrition 依剩餘預算算出縮放倍數，跟現在一樣。

這條規則讓「規劃一整週自煮」不會把未來每天的預算鎖死。計畫條目本身絕對不存縮放後的熱量，未來某天的預算當下根本不知道。

### 3. 「食材 vs 成品」的統一資料格式

#### 3.1 建議格式：一餐＝元件清單
```js
MealContent = {
  archetype_id: "protein_stir_fry" | null,
  method_id:    "sm_stir_fry" | null,
  components: [
    { kind: "ingredient", ref: "ps_beef",           axis: "protein" },
    { kind: "ingredient", ref: "st_brown_rice",     axis: "staple", is_primary: true },
    { kind: "ingredient", ref: "broccoli",          axis: "vegetable" },
    { kind: "product",    ref: "conv_dr01",         role: "drink", qty: 1 },
  ],
  estimate: { size: "M", kcal: 700 } | null
}
```
- ingredient 元件不存克數，克數＝該食材的 serving_g（資料層唯一真相），主要槽位的縮放倍數當天才算。
- product 元件存 qty（沿用現在的品項上限規則：1 主餐＋1 配菜＋1 飲料＋1 點心）。
- 允許混合：自煮加一瓶超商豆漿本來就存在。統一格式讓它不再是特例。
- 這一個格式同時用在三個地方：meal_plan.content、daily_log、大餐預約。
- 美饗日曆「主餐＋飲品」這個掛著沒做的需求，自動就解決了：它只是 components 裡多一個 role: "drink" 的 product。千萬不要在 feast_reservation 上加一個 drink_item_id 欄位，那是在 2.0 前夕多挖一個之後要遷移的坑。

#### 3.2 驗證規則（守住三輪審核定下的原則）
- 有 archetype_id 的內容，所有 ingredient 元件都必須在該骨架對應軸的 allow 清單裡，數量要符合軸的上限（Part 4 定的 COMPOSE_MAX）。計畫層不能變成繞過骨架、自由組食材的後門。
- sm_no_cook 的食安檢查，在計畫存檔時跟當天顯示時都要檢查。
- 計畫條目在顯示時要重跑 passesHardFilters，因為使用者規劃完之後可能新增了過敏原或不吃食材。被擋的條目要顯示中性提示，不要默默刪掉。

#### 3.3 daily_log 的 source_type vs 新增的 meal_type
兩個正交的維度，不要混在一起：
- meal_type：這餐是什麼型態（超商/外食/自煮）。給使用者跟未來統計看的。
- source_type：這筆紀錄是怎麼產生的（接受建議、手動、照計畫、大餐確認）。給稽核跟撤銷用的。
舊資料的 meal_type 可以從 source_type 跟元件推導回填，推不出來就留 null，不要硬猜。

### 4. 週菜單＋人口數＋採買清單

#### 4.1 資料模型
```js
// store: meal_plan，key = "2026-10-05|dinner"
{
  date: "2026-10-05", slot: "dinner",
  meal_type: "convenience" | "delivery" | "cook",
  max_tier: "quick" | "full" | null,
  content: MealContent | null,
  servings: 3,
  status: "planned" | "logged" | "cancelled",
  daylog_id: null,
  is_feast: false,
  created_at, updated_at
}

// settings: household_size_default = 1
// settings: shopping_checked = { "<rangeKey>": ["ps_beef", "broccoli", ...] }
```
採買清單本身不存。它是純函式 buildShoppingList(meal_plan 條目[], 日期範圍) → 清單列[]，計畫一改就重算。唯一需要存的是「哪些已經打勾」。

人數要能逐筆改，不能只有全域一個值。早餐通常只有自己吃、晚餐才是全家。

#### 4.2 聚合邏輯
```
對日期範圍內每一筆 status=planned、meal_type=cook、content 不為 null 的條目：
  對每個 ingredient 元件：
    qty_g = 該食材 serving_g × 預期縮放倍數 × servings
    依「採買身分」彙總（不是依 ref id，見 4.3 第 3 點）
product 元件：MVP 不列入
```
「預期縮放倍數」：
- 使用者自己那份：主要槽位用 1.0（名目份量），清單標註「主食份量會依當天預算調整，這裡是估算」。
- 家人那份：一律名目份量 ×(servings−1)。
- 不要為了算得準去預估未來每天的預算。

#### 4.3 隱藏複雜度
1. 熟重 vs 生重：staples.json 裡多種主食是 cooked 基準，需要在食材資料上加 purchase 欄位（cooked_to_raw）。
2. 可數食材：蛋要顯示「顆」，需要 purchase: { unit, g_per_unit }，且要對整體總數取整。
3. 聚合的 key：需要一個 purchase_key（canonical id）收斂不同池子裡的同一種食材。
4. sauce_methods.json 混雜烹調法跟醬料：要加 purchasable: true/false。
5. 常備品：燕麥、醬油等用 pantry: true 標記，分「要買」「家裡常備」兩區。
6. 保存期限：MVP 讓使用者自選日期範圍（預設 7 天），不做到期提醒。
7. 庫存：明確列為不做。
8. 削皮/去骨損耗：MVP 不處理，標註「未計損耗」。
9. 計畫被跳過：不是系統要處理的事，計畫條目改成 cancelled 或被實際紀錄取代就好。

#### 4.4 MVP 範圍
要做：只彙總 meal_type=cook 且已指定 content 的條目；日期範圍可選（預設 7 天）；輸出食材名稱＋總量（克數四捨五入到 10g，可數食材整數，熟重換生重）；分「要買」「家裡常備」；人數逐筆可改；全部標註「估算」。
不做：超商/外食品項、包裝規格換算、賣場分區排序、庫存、損耗、價格、自動排一週菜單、匯出分享。

#### 4.5 週規劃的 UI 入口（避免新增分頁）
美饗日曆改成「餐點日曆」，擴充成每天五個時段的格子。內容選擇器跟今日建議「自己選」共用同一個元件。「把今天的建議帶入計畫」跟「複製上週」兩個便宜動作就能滿足 80% 需求。自動排一週列為後期功能。

### 5. PRD 核心原則風險檢查

#### 5.1 運動與飲食脫鉤：中等風險
- 陷阱一：未來某天的預算如果預先計算，會出現「運動日菜單份量比較大」，等同把運動換算成食物。規則：計畫層跟採買清單永遠不計算、不顯示未來日期的熱量預算，自煮份量一律用名目份量。
- 陷阱二：不得有任何欄位引用 exercise_log 或運動計畫。

#### 5.2 不評判超吃：高風險（計畫功能天生就有評判性）
「計畫」一出現，就會產生「照計畫了沒」這個評判維度，容易變成全有全無的節食陷阱思考。
- 禁止：遵循率、「偏離計畫」、「未完成」、紅色未打勾標記、連續照計畫天數、計畫 vs 實際的熱量差比較。
- 實際紀錄跟計畫不同時，計畫條目默默變成被取代的狀態，UI 只顯示實際吃的東西。
- 過去日期裡沒被記錄的計畫條目，直接不顯示或灰掉，不要顯示「漏掉」。
- 文案禁用字要加上：「達成、失敗、偏離、破功、照表操課」。

#### 5.3 彈性點數：背景已過時
PRD 已在 2026-09-27 把「週彈性帳本/彈性點數」整個刪掉，改成體重趨勢自動校正。對 2.0 有意義的是：計畫條目永遠不能算進「完整記錄日」或「近 7 天平均」，只有 daily_log 算。大餐預約「預約不寫 daily_log、確認才寫」的規矩，要原封不動套用到所有計畫條目。

#### 5.4 自組食譜原則：中等風險，三個退化點
- 計畫內容繞過骨架：已用 3.2 的驗證規則處理。
- 採買清單如果自己算份量，會出現第二套份量邏輯：只讀 serving_g，不准有任何份量常數。
- 超商「自組」如果做成不限數量、不限角色的多選，會重新製造笛卡爾積的荒謬組合（今天截圖「前十幾張全是飲料」就是沒有角色排序的症狀）。繼續沿用品項角色上限，依角色分區或排序顯示（主餐、配菜在前，飲料放到獨立步驟）。

#### 5.5 資料安全（新發現）
計畫是未來的資料，存檔當下合法，之後可能因為過敏原變更而不合法。「顯示時重新驗證」必須做，這跟 PRD 5.7 當初補上「美饗日曆挑選器沒套過敏原」那個漏洞是同一類問題。

### 6. 分階段建議

#### Phase 0：取代今天的 Cline 任務
作廢「刪除現成品項模式」（Part 1–3）。保留 Part 4（蛋白質/蔬菜多選），跟 2.0 無關，可以照原規格做。
改做：
- 「自己選」modal 的切換，換成型態分頁：超商｜外食｜自煮（快煮/開伙），預設停在 meal_prefs[slot] 對應的型態。
- 超商、外食分頁：沿用現有現成品項多選邏輯，但依 channel 過濾，飲料移到最後一區或獨立步驟。
- 自煮分頁：現有餐型骨架流程，依快煮/開伙過濾 tier。
- daily_log 開始寫入 meal_type。manual_combo 這個 source_type 不要刪。
- 驗收：三個分頁各自能送出、meal_type 寫對、硬性過濾在三個分頁都生效、node tools/check-engine.js 全過。

#### Phase 1：統一 MealContent 格式＋美饗日曆主餐＋飲品
定義 MealContent，daily_log 新紀錄改寫 content（保留 component_ids 相容舊讀取端），feast_reservation 加 content（舊 item_id 讀取時轉換）。美饗日曆支援主餐＋飲品。
驗收：新舊紀錄都能正確顯示；大餐主餐＋飲料的熱量/蛋白質/纖維正確計入當天預算重算跟缺口計算。

#### Phase 2：meal_plan store＋解析規則（只做自煮跟只指定型態）
新增 store，實作解析規則，今日建議讀有效型態。建立/編輯先放在今日建議跟一個簡單的週格子。預算規則見 2.4。過渡期規則：同一時段已有有效 feast_reservation 就不能再建 meal_plan 條目。
驗收：規劃明天晚餐自煮某食譜後，明天今日建議顯示該食譜、份量依當天預算縮放；只指定型態的條目讓引擎只推該型態；計畫不影響近 7 天平均。

#### Phase 3：feast_reservation 併入 meal_plan
遷移腳本（設 schema_version，遷移前自動把舊 store 匯出一份備份到 settings），美饗日曆改讀 meal_plan。
驗收：舊預約（含已確認、已取消）遷移後顯示一致；feast_reservation_id 的關聯沒有斷。

#### Phase 4：採買清單 MVP
前置資料工作：食材資料補上 purchase（cooked_to_raw、unit/g_per_unit）、purchase_key、pantry、purchasable。實作 4.4 MVP。
驗收：用幾組手算範例核對總量，熟轉生換算正確，蛋顯示整數顆，烹調法不出現在清單上。

#### Phase 5（可選）：自動排一週、週模板/平日週末預設、包裝規格換算、自助餐。

#### 平行工作線：擴充餐型骨架
沒有這條線，Phase 2–4 做完使用者也會因為菜色單調而不用。每個新骨架照三輪審核定下的原則設計，逐一審。

### 7. 開工前要問使用者的問題

1. 「開伙＋人口數」是一人一盤、家人吃一樣的菜（A），還是台式共食三菜一湯（B）？（決定採買清單能不能做）
2. 週菜單是「某一週的具體計畫」（有日期），還是「每週重複的固定菜單」（模板）？建議前者加上「複製上週」。
3. 能不能接受「食材/成品」不出現在畫面上，由型態自動決定選擇器？
4. 能不能接受採買清單是「估算」，主食份量可能跟實際煮的不一樣？
5. meal_prefs 是 auto 的時段，「自己選」預設停在哪一個型態？
6. 美饗日曆改名「餐點日曆」、兼當週規劃入口，還是維持大餐專用、另外開一個規劃入口？（建議合併）
