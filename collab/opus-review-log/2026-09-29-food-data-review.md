# 食物資料查詢與修訂（PRD 第 12 節草案）審核

日期：2026-09-29　實作者：Opus（Lighten2 主導開發）　審核者：新開的獨立 Opus agent

## 背景（對話摘要）

Phase 0 完成後，使用者問：食材或原有組合能不能單獨查詢營養成分、熱量、能在哪些餐出現，以及怎麼增減與修訂，PRD 有沒有規範。實作者回報：只有超商／外食品項的「隱藏＋複製成我的版本」（PRD 10.2）與我的品項管理（B-1）、我的組合管理（11.5，內容不能直接編輯）有規範；單獨查詢、食材與骨架的增修都沒有。

使用者補充：「不只是可以增加食材，而是可以修訂。當然衛福部那類的基礎食材營養成分無法修改，能改的是自己組合＋便利／外食餐點內容及營養成分。」

實作者建議（使用者回「照你的建議」）：
1. 三層資料：基礎食材與內建資料只能查；使用者自己的資料能改；數字標出處。
2. 「食物資料」查詢頁（含衛福部全表），併進 B-1。
3. 內建餐點維持複製後再改，外加份量倍數。
4. 新增我的食材（從衛福部加入或自填）與我的料理（不綁骨架、只用在手動記錄、不進推薦）。
5. 我的組合改成可以直接編輯。
6. 順序：B-3 匯出匯入 → B-1（擴大）→ B-4 我的食材與料理。

PRD 第 12 節草案、0.1 第 12 點、6.3 例外、10.6、11.5、第 7 節路線圖已改；decisions #50–#55 已記。

## 四、衛福部全表

**20. 查詢時才載入精簡版是可行的。** 我實測的大小：

| 版本 | 原始大小 | gzip 後 |
|---|---|---|
| 完整參考檔 | 1.08 MB | 162 KB |
| 精簡版（id、名稱、俗名、分類、內容物描述、7 個營養欄位、數值取 1 位小數） | 388 KB | 82 KB |
| 精簡版，不含內容物描述 | 229 KB | 65 KB |

缺值的筆數：纖維 785、飽和脂肪 457、鈉 51、脂肪 50、蛋白質 30；熱量與碳水都沒有缺。

**21.【一定要改】「數值照抄、不能改」要寫出可以驗證的做法。** 建議三道：
1. 由 `tools/` 產生精簡檔，放在 `data/` 底下（不放 `data/reference/`，B10 規定那裡只放檢查程式用的參考資料）。進位用 `tools/lib/ingredient-values.js` 同一份算法。check-data 逐筆比對 2213 筆，要跟 `computePer100g({source:{type:"tfda",ref}})` 完全相等。
2. 前端照抄，不做任何計算，避免 C2 違規出現第二份進位邏輯。
3. db.js 的 `updateCustomIngredient`：`source` 是 `tfda` 時，拒絕修改 `per_100g`、`tfda_id`、`source`。用 check-engine 加 fake-db 斷言。

  更簡單的替代做法：`tfda` 來源的我的食材**不存數值、只存 `tfda_id`**，執行時從精簡檔讀。這樣結構上就改不了，衛福部改版也照 B10 流程生效，紀錄本來就有快照不受影響；代價是有用到衛福部食材的料理，在選擇器打開時要先載入精簡檔。兩種做法請擇一寫定。B-3 匯入時，衛福部來源的數值要依 `tfda_id` 重新核對。

**22.【建議】衛福部欄位是 null 的情況。** 纖維缺 785 筆，大多是肉類和魚貝類。照 C4.5 會一路傳到整餐的纖維，變成「無資料」，纖維缺口的提示也跟著失效。內建食材是用 B5.1 的 derived 0 處理，使用者加的沒有這條路。這件事交給使用者決定（見第六節）。

## 五、路線圖

**23.【建議】B-3 → B-1 → B-4 的方向對，但 B-1 太大。** 建議拆成：
- **B-1a**：我的品項管理，也就是編輯、封存、補填過敏原、隱藏清單、複製。它解除 decisions #49 的死路，是現在使用者最痛的地方，建議緊接在 B-3 之後。`qty` 很小，可以併進這裡。
- **B-1b**：食物資料查詢，包含精簡檔的產生工具與 check-data 比對。
- **B-1c**：成分明細。
- **B-4a**：我的食材與常買清單。
- **B-4b**：我的料理，加上 MealContent 的 `recipe` 元件與第 3 節、C4 的修訂。
- **C** 裡「組合包含料理」依賴 B-4b；12.6 的直接編輯屬於 C。

**24.【建議】B-3 先做，但匯出格式要帶版本號。** 那時新 store 還不存在，所以格式要帶 `schema_version` 與 store 清單，之後新增的 store 才接得上；匯入缺少的 store 當成空的。另外 `settings.pantry_ingredient_ids` 要列進匯出範圍，而且內建 id 不需要改寫。

**25.【建議】B-4b 跟 Phase 2、4 的關係要寫清楚。**
- B-4b 如果早於 Phase 2，Phase 2 驗收要加「計畫含料理」的斷言。
- Phase 4 採買清單（5.3）只彙總 `ingredient` 元件，料理的食材進不進清單要明寫（我的食材沒有 `purchase_key`）。

## 六、#56 常買清單（補充審核）

**26.【一定要改】`pantry_ingredient_ids` 的命名跟 Phase 4 的 `pantry` 意思相反。**
- PRD L194 的 `pantry: true` 是「家裡常備，**不算進要買**」（油、鹽、燕麥），而且是開發端維護的食材欄位。
- 常買清單是「我**會去買**的東西」。
- 12.4 第 4 點說「Phase 4 的 pantry 之後可以接這份清單」，語意是錯的，照做會讓常買的東西從「要買」區消失。
- 建議：
  - 改名，例如 `favorite_ingredient_ids`，畫面叫「常買」；
  - 刪掉第 4 點，或改寫成「採買清單可以依常買清單排序」；
  - `pantry` 仍然是開發端的欄位，兩者不相干。

**27. 資料放在兩處（我的食材 store + settings 的 id 清單）可以接受，但要補三件事：**
- **【一定要改】定義「常買」和「封存」的關係。** 我的食材等於常買，所以從常買移除就是封存；這正好說明封存不能讓料理失效（第 2 點）。
- **【建議】由一個函式產生常買集合。** 用 engine 的 `favoriteIngredientSet(customIngredients, favoriteIds)`，選擇器與料理編輯器都呼叫它。內建食材下架後，清單裡殘留的 id 要容錯（B9）。
- **【一定要改】讀取要進 check-arch 白名單，比照 C4.15、C4.16。** 只准自煮分頁、料理編輯器、食物資料頁、匯出匯入讀取；推薦、統計、hero 不得讀取。「不影響推薦」是 #56 的前提。

**28. 自煮分頁把常買排前面，跟 C4.13 與 PRD 6.1 不衝突。** 那兩條禁止的是依熱量排序或上色，常買是使用者主動標記，性質跟隱藏清單一樣，不是被動累積。但要寫明：
- **【建議】** 標記只用中性文字「常買」，不用星號或顏色。
- **【建議】** 不依使用次數自動排序，否則就變成第 4 節要防的隱性偏好。
- **【建議】** 被擋的選項排最後（6.3 第 4 點）的規則優先於常買排前面；組內照資料原順序，穩定排序。
- **【建議】** 效益有限：每個骨架每軸的 `allow` 大約只有 2–11 項，排序的幫助不大，要不要做交給使用者決定。

**29.【建議】避免重複與誤解：**
- 從衛福部加入的編號如果等於某個內建食材的 `source.ref`（例如雞胸），提示「內建已有，改成標常買」，避免同一個食材兩筆。
- 在畫面上說明：我的食材不會出現在自煮分頁的骨架選項裡，只用在我的料理。

## 七、要交給使用者決定的事

| 題目 | 選項 | 建議 | 理由 |
|---|---|---|---|
| P1 我的料理的型態 | 每道料理固定快煮或開伙／跟著自煮分頁子切換 | 跟著子切換 | 符合 decisions #47，也少一個欄位 |
| P2 一餐可以有幾道料理 | 只一道／多道並受角色上限限制／可以跟骨架自組混在一起 | 多道並受角色上限，不跟骨架混 | 「滷雞腿＋燙青菜」很常見；跟骨架混會讓 `implicit` 的語意打架 |
| P3 料理的用油與調味 | 編輯器固定有「用油＿g」一列加調味程度（不加／清淡／一般）／讓使用者自己加食材 | 固定欄位；用油預設依用油習慣，調味預設一般 | 不然大多數料理會漏算油和鈉。「不加」屬於 decisions #42 那批待 C3 審的選項 |
| P4 衛福部欄位是 null | 維持 null／使用者可以只補 null 的欄位並標「你填的」／比照 B5.1 自動填 0 | 只補 null 欄位 | 不改衛福部原本就有的數字，同時避免纖維整餐變成「無資料」 |
| P5 常買排前面 | 做／不做 | 可以先不做 | 選項本來就很少 |
| P6 複製品項的落差 | 不顯示／明細唯讀並列內建目前的數值 | 並列顯示 | 成本低，也不用做修補層 |
| P7 料理進採買清單 | Phase 4 不進／只把內建食材列進去 | 不進（MVP） | 我的食材沒有採買用的欄位 |
| P8 在基本資料編輯組合時的主餐上限 | 2／1／先選時段再編輯 | 2 | 手動上限只是防誤觸，而且 11.1 規定不檢查時段 |
| P9 自填食材的輸入方式 | 只能填每 100g／也能照包裝的「每份＋克數」填 | 兩種都能填 | 台灣包裝標示通常是每份的數字 |

**總結論：草案要先修改。** 方向可以接受：分三層、方案 A、我的料理只用在手動記錄、常買清單都合理。但第 1、2、3、4、7、8、9、10、11、12、16、21、26、27 點標【一定要改】的地方，要改完再送一次審。

另外還有 #56 相關的必改（第 26、27 點），`pantry` 的命名衝突最優先。
