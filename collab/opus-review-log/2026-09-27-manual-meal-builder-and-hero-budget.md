# Opus 第一輪審核：A/B/C 設計

## 先講總結論
- **A 的方向偏了。** 使用者說的是「有些食材不吃」，這是**食材層級的偏好**。目前的倒讚只排除「確切組合」，換一組照樣會出現同一個食材，這才是根本原因。A 做的是一條繞過推薦引擎的路，他以後每一餐都得自己挑，推薦功能對他就沒用了。應該先做「不吃的食材」清單，接進 recommend.js 的過濾；手動組餐可以做，但排第二。

## 1. A 跳過過敏原／飲食限制的篩選：不合理，會讓安全性倒退
- 「使用者自己選」只能免掉**軟性**邏輯：評分、多樣性降權、倒讚排除、蛋白質封頂、種類數量上限。
- **硬性**限制（過敏原、飲食限制）必須照樣套用。過敏原設定的意義就是防手滑，不能因為換了一個入口就失效。
- 具體做法：
  - 把 recommend.js 裡的硬過濾抽成一個共用函式，例如 `isAllowed(item, profile) → {ok, reason}`，推薦引擎、手動組餐、美饗挑選器三個地方都呼叫它。
  - 碰到過敏原的品項：卡片直接灰掉，寫明原因（例如「含：花生」），不能選。不要直接隱藏，否則使用者會以為資料庫裡沒有這個品項。
  - 飲食限制「成分未確認」的品項：預設也灰掉。可以提供「我確認可以吃」的單次放行，放行紀錄只在這一次有效。
  - 使用者自訂的食物：信任使用者的標註，但如果自訂食物本身沒有過敏原欄位，要在 schema 裡補上。
- 順便檢查：**美饗挑選器現在有沒有擋過敏原？** 如果沒有，這個漏洞今天就已經存在，應該一起修。

## 2. 缺口提示直接用 `checkHardConstraints`：口徑和時間點都不對
- **蛋白質：** 它算的是「今天已吃 vs 全天目標」。早餐時打開手動組餐，缺口會顯示差 80g 以上，接著叫他加一顆茶葉蛋，這個提示沒有意義。
  - 應該改成**這一餐應分到的份額**：`剩餘蛋白質 × 這個時段的權重 ÷ 剩下時段的權重總和`，跟 budget.js 分配熱量是同一套邏輯。
  - 草稿（還沒送出的選擇）也要算進去。
- **纖維：** 用的是「本週平均 vs 下限」，這是週指標。一餐對週平均的影響大約只有 1/20，拿週缺口建議「這一餐加一道配菜」是誤導。
  - 改成「今日份額」，或者乾脆只在這一餐纖維密度明顯偏低時才提示。
- **架構建議：** 把 budget.js 從只分配熱量，擴成分配一組營養素（kcal、蛋白質、纖維）。這樣推薦引擎寫死的「蛋白質封頂 25g」也可以改用時段份額。兩邊用同一個口徑，不會各說各話。
- **推薦的加購品項要受熱量限制：** 只挑「加上去後不會超過這個時段熱量配額＋容許誤差」的品項，按「每 100kcal 能補多少缺口」排序。不然會出現加了 200kcal 只為補 7g 蛋白質的情況。
- **送出前先預覽：** 用「已吃紀錄＋草稿」跑一次 budget.js，把對後面時段的影響顯示出來，例如「送出後晚餐剩 420kcal」。這比營養缺口提示更有用。

## 3. B 跟 A 的銜接
- 已經被記錄的時段，budget.js 本來就會跳過，所以不會有 `recs[slot]`。只要**時段狀態一律從 daily_log 推導**，就不會重複計算。
- 但這條路上有幾個洞：
  - **找不到候選的時段不計入** → hero 數字會突然變小，使用者會以為自己能吃的變少了。這是錯誤訊息。
  - **推薦結果如果有隨機性或輪替**，每次重新渲染 hero 都會跳動；倒讚一次 hero 也會變。推薦結果需要**可重現**：以「日期＋當前狀態」當種子，或把當天的推薦結果存起來。
  - **美饗預約（feast_reservation）的時段怎麼算？** 現在描述裡沒有交代 budget.js 會不會把預約時段扣掉、hero 要不要算進去。這件事必須先拍板。
  - **超出預算的時候：** 全部卡片加總如果大於剩餘預算，B 的 hero 會顯示一個比預算還大的「建議熱量」，等於在鼓勵多吃。

## 4. 理論剩餘額度降級成附註：不同意
- **根本修法（改 recommend.js）：** 改成**依序分配**。挑完第一個時段的真實品項後，把實際熱量和配額的差額帶到下一個時段，由剩下的時段重新分配。這樣卡片加總會自然貼近剩餘預算，只剩最後一個時段的誤差。
  - 自組食譜可以縮放，應該優先排在後面的時段，拿來吸收前面的差額。
- **UI 上兩個數字都顯示，並把因果關係明寫：**
  - hero 主數字：「今天還能吃 1,450 kcal」（預算）
  - 次一行：「下面這組建議合計 1,520（+70）」，差額一定要明寫出來。
  - 每張卡片的展開區塊：「分配到 500 → 這組 700（+200，超商品項無法調份量）」。
- 把預算藏起來，使用者只會更不懂卡片上的熱量是怎麼來的。要讓他看懂，就得看到「預算 → 各時段配額 → 真實品項 → 差額」這條鏈。

## 5. C 夠不夠
- **不補鈉、糖、熟重是對的**，不要為了新功能編數字。但畫面上要明寫「目前不追蹤鈉／糖」，不要默默沒有這一項。另外請去確認這三項是不是使用者原話裡明確要求的；如果是 AI 自己腦補的，就不用當成需求。
- **真正的坑是資料覆蓋率：**
  - 美饗用「小／中／大」份量記錄的項目**只有熱量、沒有三大營養素**。自訂食物也可能缺欄位。taiwan_items 則需要確認 fat/carb/fiber 欄位真的有寫進資料庫（之前就發生過沒寫進去的事）。
  - 直接把數字加總，大餐那天的脂肪、碳水會**嚴重少算**，使用者反而會覺得自己吃得很乾淨。
  - 必須區分「欄位是 null」和「數值是 0」，並顯示覆蓋率，例如「另有 1,200 kcal 沒有營養素明細」。這一句正好適合放在展開區塊裡。
- **碳水目標是用剩下的熱量反推的**，不是營養建議值。畫面上要標成「參考值」，並在展開區塊說明怎麼算的。否則使用者會以為一定要吃到那麼多碳水。
- **P/F/C 三大營養素佔總熱量的百分比**：資料已經有，順便顯示，成本很低。

## 6. 三個方案會不會互相打架：會，必須先定一個統一的時段狀態
- 定一個單一函式 `getSlotState(date, slot)`，**只從 daily_log、feast_reservation、enabledSlots 推導**。A、B、C 和 budget.js 都只讀這個函式，不各自判斷。
- 狀態值：`disabled / pending_rec / no_candidate / feast_reserved / logged(source=rec|manual|feast)`
- **daily_log 的 schema 要定清楚：**
  - 必須有 `slot` 和 `source` 欄位。

## 三個取捨點的明確回答

### 1. 兩套缺口口徑並存、不改 matcher.js：同意，但計算要放在 engine 層，不能放 UI 層
隔離的理由成立，推薦排序不應該在這輪被動到。不過要改兩件事：

- **位置：** 單餐份額的計算寫成 `js/engine/budget.js` 裡的純函式，例如 `slotNutrientShare(targets, todayLogs, enabledSlots, slot)`，UI 只負責呼叫。算在 UI 裡沒辦法測試，也一定會被複製到別處。
- **公式有坑，要照這個寫：** 你描述的是「把已吃＋草稿當成部分完成，重跑分配，取這個時段的份額」。問題是 `recalcTodayBudget` 只要看到某時段有東西就會把它當成已吃，於是這個時段的份額會被算成 0，缺口永遠是負的。正確做法：
  - 份額 = **不含草稿**的剩餘量 × 本時段權重 ÷（含本時段在內、所有未吃時段的權重總和）
  - 缺口 = 份額 − 草稿加總
  - 蛋白質、纖維、kcal 三項都用同一組權重算。
- **標註：** 在程式碼註解和 PRD 裡明寫「兩套口徑刻意並存，matcher 是給排序用的」，免得以後有人把它們「統一」掉。

### 2. 維持「1 主餐＋1 配菜＋1 飲料＋1 點心」上限：同意
理由接受。但交接文件要補兩條規則，否則 Cline 會卡住：

- **自訂食物算哪一類？** 自訂食物如果沒有 category，要嘛讓使用者建立時選一個，要嘛一律算「配菜」，並且一餐最多 1 個。沒定清楚，上限就套不上去。
- **下午茶、宵夜的上限：** 比照推薦引擎的規則，不需要主餐，其他類各 1。

### 3. 一筆記錄、名稱用＋串接、不留個別品項明細：有條件同意
「跟現有記錄這餐的存法一致」這個理由我接受。但「這樣就不用改 schema」這個理由不成立：IndexedDB 是 schemaless，只要不建 index，多存一個欄位**不需要 migration**，`undoDailyLog` 也完全不受影響。多存一個欄位幾乎沒有成本，不存的損失卻是永久的，所以：

- **必要條件：** 多存 `component_ids: [...]`，存純 id 陣列，不建 index，UI 不讀它。現有的「記錄這餐」組合也順手一起存。
- **為什麼非存不可：** 不是為了以後做分析，而是**條件 1 的涵蓋率判斷現在就需要它**（見下面）。`manual_combo` 這個 source_type 裡混著自組食譜、台式、超商、自訂食物，光看 source_type 分不出哪些脂肪／碳水是真的 0、哪些是缺資料。

## 動工前必須寫進交接文件的 4 個條件

**條件 1：缺資料要寫 null，不能寫 0（這條不做會造成資料損毀）**
你查到的事實比我想的嚴重：`fromTaiwan()` 寫死 `carb_g: 0, fat_g: 0`，而手動組餐會把各品項加總後寫進 daily_log。不處理的話，**每一筆新紀錄都會把「未知」存成「0」**，以後無法回頭分辨。

- `fromTaiwan()` 以及超商品項的轉換，缺值一律回傳 `null`。
- 加總規則：組合裡**任何一個**品項是 null，這個營養素的加總就寫 null，不能當 0 加。蛋白質、纖維如果也有缺值，同樣處理。
- **全面檢查所有讀 fat_g/carb_g 的地方**，確認不會因為 null 算出 NaN：C 方案的累積量、P/F/C 佔比、所有 reduce 加總。累加時略過 null，同時累計「缺資料的 kcal」。
- 涵蓋率判斷：
  - 新紀錄看欄位是不是 null。
  - 舊紀錄（改版前寫進去的 0）才用 source_type 屬於台式外送／超商來判斷，這是向下相容的 fallback。
- 手動組餐挑選器即時顯示的加總，缺資料時顯示「—」並加一行說明，不要顯示 0g。

**條件 2：`component_ids` 欄位**（見第 3 點）。

**條件 3：hero 主數字的定義要寫死**
你寫的「今天還能吃 X＝依序分配後、還沒處理的時段配額總和」有歧義：依序分配跑完之後，所有時段都「處理過」了，照字面解讀會是 0。

- 主數字固定定義為 `targetKcal − 已吃（含美饗預約）`，也就是原本的 `remainingKcal`，**不受推薦結果影響**。
- 次要行是卡片加總。落差＝次要行 − 主數字。

另外，依序分配會把前面時段超出的熱量往後推。一旦被 `Math.max(0)` 夾住，晚餐的配額可能只剩 0 或幾十 kcal，畫面上就會變成「找不到組合」。要分兩種情況顯示：

- 配額低於某個門檻（建議 150 kcal，寫成常數）：顯示「今天的額度已經用完／所剩不多」，不要跑推薦。
- 配額正常，但真的沒有候選：才顯示「這個時段沒有找到符合的組合」。

兩種原因的處理方式不同，不能共用同一句文案。

**條件 4：美饗挑選器補上硬性過濾是行為變更，要驗收**
- 原本能選的品項會變成灰色。交接文件要列成預期中的行為變更，驗收時也要檢查。
- 已經存在的美饗預約不要回頭去擋，只影響新增的預約。
- 挑選器要套用哪些排除，要寫明：
  - 手動組餐：過敏原、飲食限制、`disliked_ingredients` 三者都套用。
  - 美饗挑選器：過敏原、飲食限制必套。`disliked_ingredients` 是否也套，請你這次一併拍板；我建議也套，保持一致。
