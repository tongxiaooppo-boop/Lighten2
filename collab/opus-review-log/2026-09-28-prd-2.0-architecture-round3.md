2. 第 2 點（使用者自建品項）：

   - 刪除一律是軟刪除（封存）。

3. 第 3 點：品項卡片全部改成純文字版面，不要「有圖就顯示、沒圖留空」。先跟使用者確認「5 張」指的是哪 5 張（F3）。

### 1. 第 1 點：美饗日曆被超商/外食取代

#### 1.1 沒有引入新的架構問題，反而拿掉了一個特例
現在美饗日曆有自己的品項規則：`filterForSlot(slot, profile, { includeConvenience: false })`，只看台式品項和自訂食物。收斂之後這個特例直接消失：日曆的格子編輯器就是三分頁選擇器，差別只在寫入的地方——今天用「自己選」寫 daily_log，未來日期寫 meal_plan。「大餐」原本另外做的東西都拆解掉了：預約時預先佔用預算，本來就是規則對所有商品元件的通則；is_feast 也沒有任何地方在讀。

#### 1.2 美饗日曆有、新架構還沒涵蓋的 4 件事

| 美饗日曆現有功能 | 新歸屬 |
|---|---|
| a. S/M/L 匿名估算（查不到品項時用：喜宴、吃到飽、朋友家） | MealContent 新增第三種元件 `{ kind: "estimate", name?, size?, kcal, protein_g?, ... }`。UI 放在外食分頁最上方「找不到？直接估算」卡片。不會存成品項，只存在這一餐裡。也補上「自己選」現在記錄不了查不到的一餐這個缺口 |
| b. 同一個表單順手建立具名的自訂食物（靠有沒有填名稱來判斷要不要存） | 拆成兩個明確動作：「只估這一次」（a）和「存成我的品項」（第2點快速新增）。用有沒有填名稱猜意圖的做法廢除 |
| c. 預約（未來日期）與直接記錄（過去日期）兩種模式，含「今天這個時段已經過了就不能預約」的檢查 | 日曆格子依日期決定寫到哪裡：未來（或今天還沒過的時段）寫 meal_plan，今天已過的時段或過去日期寫 daily_log（回填）。回填過去日期是現有功能，Phase 3 不能弄丟，要列進驗收清單。時段結束時間檢查（SLOT_END_HOUR）搬過去沿用 |
| d. 預約狀態 reserved→confirmed→cancelled 的確認流程 | meal_plan 沒有狀態欄位。「確認」改成今日卡片上「照計畫記下」按鈕，按下去用計畫內容寫一筆 daily_log。「取消」就是刪掉這筆計畫。過了日期還沒記錄的計畫直接失效，不提醒、不標「未完成」 |

#### 1.3 Phase 3 簡化後的內容
1. 遷移 feast_reservation：只搬 status==="reserved" 且日期是今天以後的。已確認的早就寫進 daily_log，已取消的直接丟掉。每一筆對應成 `{date, slot, meal_type: "delivery", content}`：有 item_id 的變成商品元件，沒有的變成估算元件（帶 size 和 estimated_kcal）。
   - id 命名空間的雷：feast_reservation 存的是原始 id（"ln01"），item-picker 的 uid 是 "tw_ln01"；自訂食物是 "custom_..."。遷移時要照 resolveFeastItem 的查找順序換成 uid。遷移時一併寫入營養素快照，之後不用再查一次。
   - daily_log 舊紀錄裡的 feast_reservation_id 不動，只當歷史資料。
2. 刪掉 feast.js 裡 reserve/confirm/cancel 的邏輯，以及 tab-ledger.js 的整張表單；改寫成週格子加上三分頁編輯器。
3. is_feast：新紀錄不再寫入，舊資料保留。取代 round 2 的「複製上週預設跳過 is_feast」規則，改成「預設跳過含有 estimate 元件的計畫」。估算的一餐本來就是一次性事件，剛好可以代替大餐旗標，不用另外新增「一次性」欄位。
4. Phase 3 的先決條件：第 2 點的線 B-1 必須已經上線。

#### 1.4 對核心原則的提醒
美饗日曆原本對「不評判超吃」有一個看得見的正面作用：「先把大餐排進去」是被系統鼓勵、光明正大的事。身分收斂之後，這個使用入口不能跟著消失。餐點日曆的空白格子、外食分頁的估算卡片，文案要保留這層意思，例如「有聚餐？先排進來，其他餐會自動幫你調整」。這是文案和 UX 的要求，PRD 要寫下來。

### 2. 第 2 點：使用者自建品項（完整設計）

#### 2.1 資料模型：擴充 custom_foods，不開新 store
逐一比較（既有參照、舊資料、概念、格式乾淨度）後，拆開的成本明顯比好處大，選擴充。程式碼裡可以把概念改叫「我的品項」，store 名稱不改。

格式（v2，除了標示必填的都可以省略）：
```js
{
  id: "custom_xxx",
  name,                         // 必填
  channel: "convenience" | "delivery" | null,   // 新建立的必填（從目前分頁自動帶入）；舊資料是 null
  role: "main" | "side" | "snack" | "drink",    // 新建立的必填（預設 main）；舊資料缺這欄就當 side
  valid_slots: [...],           // 可省略，省略時依 role 推預設
  kcal,                         // 必填
  protein_g, carb_g, fat_g, fiber_g,            // 可省略，null
  vendor,                       // 可省略：「7-11」「某某健康餐盒」
  category,                     // 可省略
  allergen_tags: null | [],     // 三種狀態：null=沒填（未確認）；[]=確認不含；[..]=含這些
  diet_tags: [],
  note,
  archived: false,              // 軟刪除
  created_at, updated_at
}
```
- 沒有 image 欄位（跟第3點一致，也避免把圖片塞進 IndexedDB 把容量撐大）。
- 一律軟刪除（archived: true）：選擇器和候選池都看不到它，但用 id 還是查得到，舊紀錄和舊計畫不會斷掉。管理畫面提供「還原」。
- database.js 要新增 updateCustomFood(id, patch)。不提供硬刪除的 API。

#### 2.2 內建品項（JSON 裡的超商/外食品項）怎麼「增減」
使用者說的「增減」一定會延伸到「這個超商已經下架了」「這家餐廳的熱量我想改」。不做修補/覆蓋層（開發端更新 JSON 會產生衝突，合併規則難理解）。改成兩個簡單動作：
- 隱藏：settings 新增 key `hidden_catalog_uids: [uid...]`。選擇器和推薦引擎都要濾掉這些品項。這是使用者明確操作，推薦引擎可以讀它（跟 lastPicked 不同，那是被動累積資料）。管理畫面可取消隱藏。跟 disliked_ingredients 的 type:"item" 語意不同：「不吃」灰階顯示原因＝「我不要」；「隱藏」整個消失＝「這個已經不存在或買不到」。不要合併成同一個東西。
- 複製成我的版本：以內建品項為底，建立一筆預先填好的自建品項（copied_from: seedUid），同時自動把原本品項加進隱藏清單。之後開發端更新這個內建品項，使用者的版本不會跟著更新——刻意接受的落差，UI 用小字標示「從內建品項複製」。

#### 2.3 要填多少欄位
快速新增（在選擇器裡）：只要名稱＋熱量，再加一排角色晶片（主餐/配菜/點心/飲料，預設依時段：早午晚餐預設主餐，下午茶宵夜預設點心）。channel 從目前所在分頁自動帶入。其他欄位收在「更多（選填）」：蛋白質/碳水/脂肪/纖維/過敏原/飲食標籤/店家品牌。
valid_slots 預設值：主餐預設早午晚，配菜/點心/飲料預設全部時段。快速新增時一定要包含目前這個時段，不然新增完當場在這個時段看不到它。
跟現在「只填 kcal/protein，其他 null」的精神一致：必填從「名稱＋kcal」變成「名稱＋kcal＋角色」，角色有預設值，實際上多點一下都不用。蛋白質沒填時缺口那行顯示「—」，缺口數字照樣算。

#### 2.4 過敏原和飲食限制：一定要跟 F1 一起修
拿掉 !item.is_custom 這個例外。自建品項的 allergen_tags===null（包括所有舊資料）一律當成 UNVERIFIED_ALLERGEN，套用 PRD 5.7 同一套規則。只有使用者 profile 有設過敏原或飲食限制時才會擋，沒設的人完全不受影響。
手動選擇器裡，被擋住的自建品項照樣灰階顯示原因，但原因改成「過敏原未填，點這裡補填」，點下去打開這筆品項的編輯畫面（只對自建品項這樣做；內建品項維持現在的「成分未確認」）。使用者填了 [] 或具體標記，就照常用 passesAllergens 判斷。填錯的責任在使用者。表單上用一行小字說明「會用這個欄位幫你過濾」。飲食限制比照辦理。
⚠️ 行為會改變：修完之後，有設過敏原的使用者，他所有舊的自訂食物都會變成灰階。這個修正一定要跟編輯畫面一起上線，不能只先修過濾，不然會出現「東西被擋住、卻沒有地方可以修」的死路。PRD 和上線說明要寫到這件事。

#### 2.5 要不要進今日建議的自動候選池
分兩階段：
- B-1：只能手動選（「自己選」和日曆）。
- B-2：依資料完整度自動加入，不加每一筆的開關。條件：沒有封存/沒有被隱藏；kcal 和 protein_g 都有填；如果使用者有設過敏原或飲食限制，allergen_tags 不可以是 null。符合條件的依 channel 併入推薦引擎的超商或外食展開。管理畫面每一筆顯示狀態：「會出現在建議裡」／「補上蛋白質就會出現在建議裡」，中性語氣，不催促。不做每一筆的「允許推薦」開關：不想被推薦已經有「不吃」清單可用。
為什麼不一開始就讓它進候選池：新增品項不等於希望系統推薦它，快速新增的資料一定不完整。依完整度控制，讓進入候選池這件事自己說得清楚理由，又不用使用者多管一個設定。

#### 2.6 UI 位置和排程
兩個入口：
1. 選擇器裡快速新增：超商/外食分頁最後一組「我的品項」下面放「＋新增到我的超商品項」（外食分頁寫「外食品項」）。新增完直接選中。
2. 管理畫面：放在「基本資料」分頁裡的一個區塊「我的品項」，不新開頂層分頁。內容：列表（可搜尋，依 channel 分組）、編輯、封存/還原、「已隱藏的內建品項」清單（可取消隱藏）、每一筆建議狀態（B-2 才有）。

排程：平行線 B，但有排程依賴：
- B-1（格式 v2 加 updateCustomFood、快速新增、管理畫面、隱藏清單、複製成我的版本、F1 修正加補填入口）：Phase 0 之後就可以開始，而且一定要在 Phase 3 之前上線，因為 Phase 3 會拆掉目前唯一的建立入口（F2）。
- B-2（進入推薦候選池）：B-1 之後隨時可以做，跟 Phase 1–4 都沒有依賴。
- B-3：資料匯出/匯入 JSON。repo 裡目前沒有匯出功能。以前使用者的資料只有紀錄；現在會開始自己花時間建品項清單，瀏覽器資料一清掉就全部沒了。這件事從「有會更好」變成「值得做」。

Phase 0 需要順手做的一個小調整（成本很低）：normalizeCustom 改成把欄位帶過去——role: f.role || "side"、valid_slots: f.valid_slots || ALL_SLOTS、channel: f.channel || null，濾掉 archived。partition 規則：channel 有值就只放對應分頁，channel 是 null（舊資料）就兩個分頁都放。這樣 B-1 上線時 Phase 0 的程式碼不用再改。

### 3. 第 3 點：圖片回歸文字

先確認「5 張」指的是哪 5 張（F3）。repo 裡沒有餐型骨架的圖，只有 5 張時段插畫。判斷使用者指的是時段插畫：保留在推薦卡片上固定使用 MEAL_DEFAULT_IMAGE[slot]，拿掉 PROTEIN_IMAGE 的食材照。如果使用者真的想要 5 張餐型骨架圖，那是要另外產生新圖的內容任務，不在這輪範圍。

版面：品項卡片全部改成純文字版面，不要「有圖就顯示、沒圖留空」。理由：
1. 照這個決定，品項網格裡根本不會有任何一張圖。保留 .feast-item-card-img-empty 那塊空白色塊，只會讓每張卡片白白多出一個正方形，更容易出現「要滑很久」。
2. 自建品項永遠沒有圖，混在有圖的卡片裡會像「次等品項」。

做法：cardHtml 拿掉圖片區塊，改成緊湊文字卡片：名稱（粗體）、熱量、選填小字（店家或分類）、被擋住時顯示原因。網格欄數可以因此變多。刪掉 TAIWAN_ITEM_IMAGE（item-picker.js 和 tab-ledger.js 各有一份，重複程式碼，一起清掉）。itemCardHtml（tab-ledger.js）會在 Phase 3 整個消失；Phase 0 先不用管它。圖片檔案先留在 repo（CREDITS.md 有授權紀錄），只是不再被引用。

建議把這件事併進 Phase 0：本來就在重做商品網格，同時改成純文字卡片幾乎不增加成本，也直接改善超商分頁密度。美饗日曆因共用 cardHtml，也會跟著變成純文字。

### 4. 三個新決定之間的矛盾和地雷

1. 可編輯品項 × MealContent 只存 ref，這是最大的雷。Phase 2/3 的商品計畫靠規則預先佔用預算，需要知道熱量。如果計畫只存 ref，每次讀取時才去查：使用者改了某個自建便當的熱量，早就排好的計畫會悄悄改掉佔用的預算；品項封存之後還要處理查不到的情況。Phase 1 定案：商品元件和估算元件寫入時存快照 `{ kind, ref, name, kcal, protein_g, carb_g, fat_g, fiber_g }`，ref 只用來連回品項和分組。食材元件照 round 1 規則存 scale，不存熱量。round 2 的草稿格式，商品元件要補上快照欄位。
2. 美饗日曆的身分收斂 × F2：拆掉美饗日曆等於拆掉唯一能建立自訂食物和匿名估算的地方。線 B-1 和 Phase 1 的估算元件，是 Phase 3 的先決條件。路線圖要畫出這條依賴箭頭。
3. 大餐概念消失 × round 2 的「複製上週」規則：原本依賴 is_feast，改成「跳過含有 estimate 元件的計畫」。round 2 那段要一起改掉，不然文件前後矛盾。
4. 自建品項 × PRD 5.7：F1 是現在就存在的破口，第 2 點會放大它。修正和補填入口必須一起上線，且要向使用者說明「舊的自訂食物可能會變灰，點進去補填過敏原就好」。
5. 外食的語意要重新定義：估算元件（喜宴、朋友家）放在外食分頁，會讓「外食」實際上變成「不是自己煮、也不是超商」，即「別人做的」。PRD 的型態定義要改成這個說法，不然之後有人會糾結「在朋友家吃算不算外食」，或想加第五種型態。不要加第五種型態。
6. 內建品項複製後的落差：開發端之後修正內建資料，複製過的使用者版本不會跟著更新。刻意接受的代價，但開發端補正內建資料時要知道這件事對已經複製的使用者沒有效果。建議記在 collab/convenience-items-nutrition-todo.md 這類資料維護文件的開頭。
7. 「5張圖」的理解很可能錯了（F3）。照轉達者的理解會做成「保留5張根本不存在的圖」。請先回頭跟使用者確認再寫進 PRD。
8. 核心原則的新檢查點：自建品項的「會/不會出現在建議裡」狀態文案要中性，不可催促式；隱藏清單和「複製成我的版本」是使用者主動操作，不累積行為資料，沒有風險；過期沒記錄的計畫直接失效，不出現「未完成」；這輪變更都沒碰 exercise_log，沒有新風險。
