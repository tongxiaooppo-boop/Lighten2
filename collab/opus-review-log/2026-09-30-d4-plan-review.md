## 2. 【一定要改】

### M1 用「＝」判斷等值推算會命中 8 筆，不是 3 筆；內建熟食的推算也漏了

**證據**：`source.note` 含「＝」的有 8 筆。
- 真正的等值推算 3 筆：`fx_congee`「附-4 粥(稠) 125g＝米 20g」、`fx_fresh_noodles`、`fx_cooked_noodles`。
- 另外 5 筆不是：`fx_whole_milk`、`fx_evaporated_milk`、`fx_lowfat_milk`、`fx_skim_milk` 的「附-1「1 杯＝240 公克」換算」，以及 `soy_milk` 的「1ml＝1g」。
- 對應表裡有 `equivalent` 的恰好 3 筆（`data/reference/food_tree_map.json`）。照計畫的寫法，check-engine 斷言一跑就會失敗；如果改成放寬斷言，全脂奶的出處會多一句「依代換表的生熟等值推算」，這是錯的。

**同類漏洞**：`brown_rice_cooked`（糙米飯）、`mixed_grain_rice_cooked`（雜糧飯）是熟食，但用的是**生米**樣品（ingredients.json：`"ref":"A05013 × 0.5"`，cooked_to_raw 0.5）。分層的 `source.note` 只寫「內建食材…decisions #103」，不含「＝」。照計畫，糙米飯的出處會寫「衛福部（整合編號 A05013）」。使用者去查 A05013，看到的是生糙米每 100g 354 kcal，對不上糙米飯的 182 kcal。白粥的 A05002 是生白米，也是一樣的問題。

**建議**：採 Q6 的替代方案，由 build 工具在 `source` 輸出結構化欄位，例如 `derivation: "equivalent" | "cooked_from_raw" | null`，再由 check-data 同步驗證。
- 等值推算：寫「依代換表：粥 125g＝米 20g 推算」。
- 內建熟食：寫「由生米樣品依熟重係數推算，可能略高估」。內建的 note 本來就說高估 10–25%，這是營養師會想讓使用者知道的事。

這會是一個 `data` commit。`food_tree.json` 走 `fetchJson` 會帶版本字串（catalog.js L19），stamp-version 照跑即可。check-engine 斷言：`derivation` 非空的恰好是這 5 筆，而且出處文字不含 `TFDA|decisions|×|#\d`。

### M2 份量文字沒有生熟乾濕，雞胸肉「30g」、藜麥「45g」會被當成熟重

**證據**：
- 雞胸肉 `state: raw`、`serving.display: null`，照計畫會顯示「1 份（代換表）＝30g」，完全沒寫生重。
- 附-3 豆魚蛋肉只有 17 筆有「煮熟約 Ng」。
- `quinoa` 是 dry 45g；`fx_rice` 是 raw 20g（1/8 米杯），`fx_cooked_rice` 是 cooked 40g。
- 內建食材自己的 `serving_label` 都有寫「生重約130g」「熟重約150g」「乾重約45g」。章程 B5.5 要求份量「註明生重或熟重」；PRD 13.3 也寫「營養用可食部分計算（附-3 生重…）」。
- 對減脂使用者來說，肉類生熟重量差約 25–35%，蛋白質與熱量會估錯同樣的比例。

**建議**：`foodTreeServingText` 依 `state` 加量詞：
- raw：肉、魚、蔬菜、米寫「生重」；水果寫「可食部分」
- cooked：「熟重」
- dry：「乾重」
- wet：「濕重」
- as_is：不加

例：「1 份（代換表）＝生重 30g」「1 份（代換表）＝可食部分 70g（大的 1/2 根或小的 1 根），購買量約 95g」「內建一餐：乾重 45g」。

check-engine 用雞胸（生重）、藜麥（乾重）、白飯（熟重）、香蕉（可食部分）、全脂奶（as_is，無量詞）各斷言一次。

### M3 `<details>` 的展開狀態每次重畫都會消失

**證據**：
- `tab-foods.js` L45 每次點擊都重設 `#foods-body` 的 `innerHTML`。
- 現有 `detailsGroup(title, count, inner, open)`（list.js L187–L190）的 `open` 只從 `openUid` 推出來。
- 計畫只寫「有列被點開、或剛標完不吃的那一類保持展開」。

實際會出現的情況：
- 使用者展開「蔬菜類」、點開「高麗菜」、再點一次收起明細，`openUid` 變成 null，整個蔬菜類收合，畫面跳回頂端附近。
- 展開兩個大類時，點其中一類的列，另一類就收合。
- 搜尋後清空，全部收合。

**建議**：
- `foodsState` 加 `openSections`（Set 或物件，key 例如 `cook:protein`、`drinks:fruit`、`cook:protein:seafood`）。
- 在 `#tab-foods` 用**捕獲階段**聽 `toggle`（`toggle` 事件不冒泡，要 `addEventListener("toggle", fn, true)`），把狀態寫回 `openSections`。
- render 時 `open` 由 `openSections` 或「含 `openUid`」決定。
- 切子分頁時是否清空，要寫明（建議保留）。
- mobile-walkthrough 要用**點 summary** 展開，不能用 `openFolded()` 直接設 `d.open`（mobile-walkthrough.mjs L90）。加一步：「展開兩個大類 → 點開再收起一列 → 兩類仍然展開」。

### M8 缺值填 0 的說明取 `field_sources[f].note` 原文，會出現開發用語

**證據**：
- 實際 note 是「TFDA 此欄無資料；動物性食材不含膳食纖維，填 0」（116 欄，5 種寫法），跟計畫舉的「纖維：衛福部沒有這一欄…當 0」不同。

**建議**：依 `field_sources[f].ref` 的四類理由（動物性食材／蔬菜／水果／油脂，B5.1 白名單）在 engine 對照成使用者文字，例：「纖維：衛福部沒有這一欄；動物性食材不含纖維，以 0 計」。同一種理由多欄時合併成一句。check-engine 斷言所有分層品項的 `foodTreeSourceText` 都不含 `TFDA|decisions|×|#\d|填 0`。

## 3. 【建議改】

**S1 模組結構：避免 list.js ↔ tree.js 循環 import 與 C2 重名。**
tree.js 需要 `nutrientLines`、`allergenText`、`dietText`、`linesHtml`、`foodsRowHtml`、`detailsGroup`、`dislikedKeys`、`blockOf`、`NO_PROFILE_NOTE`，這些都在 list.js，大多沒 export。list.js 的 `foodsSubtabHtml` 又要呼叫 tree.js 組飲品・水果與自煮，兩個檔會互相 import。check-arch 的 C2 規則是同一個頂層名稱只能定義一次（check-arch.js L245–L260），複製一份會失敗。
建議把列、明細共用的 helper 抽到 `js/ui/foods/rows.js`，list.js 與 tree.js 都 import 它；`foodsSubtabHtml` 依子分頁分派。

**S2 自煮子分頁不要出現「我的品項／＋新增到我的自煮品項／已隱藏／已封存」。**
現有 `foodsSubtabHtml` 不分子分頁一律畫「我的品項」與新增鈕（list.js L204–L209）。`customFoodEditing` 在 `subtab` 不是 drinks、delivery 時預設 convenience＋main（custom-foods.js L39–L42），在自煮按新增會做出一筆超商主餐，違反 #94、#97「不放空殼」。
飲品・水果也要寫明組的順序。建議：灰字說明 → 現成飲料 → 家裡的飲品 → 水果（收合）→ 我的品項 → 你標了不吃 → 已隱藏 → 已封存 → 全部清單。「你標了不吃」合併現成與分層兩種；頂端「灰色的 N 項」的筆數要把分層算進去。

**S3 大類裡的子類也收合，只畫展開的內容。**
豆魚蛋肉類 90 筆、蔬菜類 73、全穀雜糧 69，一次展開約 4–6 千 px。建議兩層 `<details>`：大類 → 子類，都附筆數；小的大類（乳品 10）可以只有一層。配合 M3 的狀態，render 時收合的區塊不產生 333 列 HTML，每次點擊重建的 DOM 才不會太大。

**S4 飲食限制的灰字對肉類會誤導。**
蛋奶素使用者會看到 108 筆「飲食限制未確認」，包括雞胸肉。分層的 `vegan`／`lacto_ovo` 是人工確認過的布林值。建議：`allergen_tags` 含未確認的（素雞塊、素肉燥）寫「飲食限制未確認」，其餘寫「不符合你的飲食設定」。由 engine 依 code 與標籤給字，不改 filters.js 的 reason。decisions #113 寫「看不到」，實際是「灰色、不能選」，順便改。

**S5 內建一餐與共用 id 的份量說法。**
- 「今日建議的一餐：150g」不準確：自組食譜主要槽位會縮放 0.5–2.0 倍（meal-content.js L137–L140），今天推薦可能是 225g。建議寫「內建一餐：熟重 150g（今日建議會依你的熱量調整）」，並跟 PRD 13.4 的「1 份＝內建一餐 130g」統一，切片 7 會沿用。
- `builtin_meal` 的出處不能寫「1 份的量照食物代換表」（計畫第 3 項沒有分支）。
- 共用 id（雞胸肉等 27 筆）的明細建議多一行：「今日建議的雞胸肉一餐是生重 130g（約 4 份代換表）」，取自 `ingredients.serving_g`，由 engine 產生。這一行能把「30g／35.6 kcal」和今日建議的 130g 接起來，抽查審核 L323 擔心的正是這個混淆。

**S6 含糖果乾要有一行中性事實。**
`sugar: "added"` 的芭樂乾、鳳梨乾、芒果青沒有 note，名稱也沒寫加糖；無加糖的三筆名稱與 note 都有寫。建議明細加一行「衛福部樣品：有加糖」或「無加糖」（只陳述樣品，不警告，不違反 C4.13「飲料不做糖量警告」）。8-7 搜尋芭樂乾時斷言看得到這一行。

**S7 同樣本提示的措辭與範圍。**
- 分層之間（白米↔白粥、麵條乾濕熟、糙米↔糙米飯）用「同一種食材的其他形式：」；跟現成品項之間才用「同一個衛福部樣品：」。「衛福部樣品」對使用者是術語，白粥還是由白米推算的。
- 取消不吃時也提示「也取消」，否則會留下半邊。
- 寫明「自己選」（meal-picker/index.js L321）與今日建議「順便不要」**不**提示，並記進 PRD 13.3。

**S8 `foodsWhereOf` 與 `sameSampleEntries` 的邊界。**
- 用明確欄位辨認分層品項（例：有 `group` 欄位），不要用「沒有 `role`」反推。
- 自查補上 `recordsOfSubtab`（list.js L162）。
- `sameSampleEntries` 要排除 `tfda_id` 為 null 的配對（希臘優格），加斷言。
- 回傳項要有 `where`，並標出是否已標不吃。

**S9 搜尋結果。**

- 結果順序寫明：現成、分層、我的品項，或依子分頁順序。

**S10 文件與註解。**依「已決定取代就拿掉」原則：
- `disliked.js` L2「自煮子分頁出現前只能在這裡取消」要改。

**S11 check-arch 的 C4.17 ③ 沒掃 picker.js。**計畫說「picker 不讀分層（check-arch 擋）」不精確。可以順手把 `js/engine/picker.js` 加進 `RECOMMEND_FILES`，或改計畫文字。picker.js 目前沒有 `"food"`、`foodTree` 字面量，要先確認；它有 `ROLE_DEFAULT_SLOTS.drink` 等，應該不會誤報。

## 5. 行動版 UX 與營養師角度

**333 筆在手機上怎麼瀏覽**
- 自煮 268 筆、飲品・水果 65 筆。一層收合在大類展開後仍有 70–90 列，每列約 60px（名稱＋meta 兩行），單類 4–6 千 px。建議兩層收合＋狀態記憶（M3、S3）。收合的區塊不畫內容，可以把每次點擊重建的 HTML 從 333 列降到展開的幾十列。
- 標不吃之後列會搬到底部：清單長時，使用者會以為東西消失了。剛標的那一列要捲到可見，或暫時留在原處（M4）。
- 子分頁列實測 360／390 寬都不橫捲、按鈕 44px。
- 搜尋是主要入口，別名要看得出命中了什麼（S9）。

**份量與出處文字會不會誤導**
- **共用 id 的「1 份（代換表）」和今日建議的一餐**：寫「1 份（代換表）」是對的，但只寫 30g、35.6 kcal，使用者會拿它跟今日建議的雞胸（130g、約 150 kcal）比，以為數字不一致。建議加一行今日建議的一餐（S5），兩個數字並列就不會誤會。
- **內建一餐**：「今日建議的一餐：150g」忽略了 0.5–2.0 倍縮放（S5）。
- **生熟**：目前計畫最大的營養誤導點（M2）。雞胸、豬肉、魚大多只寫「30g」「35g」，使用者多半秤熟肉，會少算約三成。
- **液體毫升**：「240ml（1杯）」清楚。營養照 1ml＝1g 計，牛奶實際密度約 1.03，誤差可以忽略；蒸發奶的 note 已說明。豆漿 190ml 沒有家用單位，可以不補。
- **果乾含糖**：無加糖三筆的名稱與 note 都清楚；加糖三筆（芭樂乾、鳳梨乾、芒果青）完全沒有標示（S6）。熱量本身照加糖樣品算、是準的，但使用者會把芭樂乾當成跟芭樂同類。
- **出處**：衛福部樣品是生米、畫面卻是熟飯或粥的，一定要說明是推算（M1）。缺值填 0 的說明不能露出「TFDA」「填 0」（M8）。
- **過敏原**：36 筆的已知過敏原被「未確認」蓋掉（M5）。這是安全資訊的呈現問題，不是過濾問題（過濾本身是對的）。

**同樣本提示會不會造成困惑**
- 鮮奶、豆漿這種「外帶一杯」與「自己倒」的配對，提示有意義，不提示反而像 bug（#85 的理由）。
- 分層之間的配對（白米↔白粥、麵條乾濕熟、花椰菜↔花椰菜米）用「同一個衛福部樣品」這個說法不好懂，建議改成「同一種食材的其他形式」（S7）。
- 糙米→糙米飯的提示很有價值：它會真的影響推薦（糙米飯是推薦主食）。

**不評判（章程 C4.13）有沒有被違反**：大致沒有。
- 組內用 Collator 依名稱排，不依熱量排。
- 被擋的只灰、不上色。
- 「高鈣深色蔬菜」是中性標籤。
- 計畫的文字沒有 check-arch 禁用字。
- note 裡「比目魚…請選「鱈魚」」有指示語氣，但屬於事實說明，不是評價。
- 不做 T6「跟一般 1 份差很多」提示，符合 PRD 13.1「不顯示脂肪分級」的精神。
- 需要注意的是 S4：蛋奶素使用者會看到上百筆「飲食限制未確認」灰字。這不是評判，但訊息不準，應該修。
