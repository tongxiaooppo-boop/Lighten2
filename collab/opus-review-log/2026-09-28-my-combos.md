# 獨立審核：「我的組合」（commit c66d26f）

## 必須修改

**M1. 寫入驗證放在 `data/db.js` 並呼叫 `engine/meal-content.js`，違反分層**
- 依據：CHARTER C1.2「`data/` 不 import `engine/`」〔機〕；PRD 11.1 卻寫「寫入驗證（`data/db.js`）：…通過 `engine/meal-content.js` 的驗證」。照這樣寫，check-arch 一定會擋。
- 改法：拆成兩層。
  - db.js 只做結構驗證：名稱非空、至少 1 個元件、沒有 `estimate`、`product` 沒有 `snapshot`、有 `ref`/`qty`。這跟 B8 的做法一致。
  - 語意驗證（角色上限、`allow`、軸上限、免開火）由呼叫端（ui）先呼叫 engine 做完，再寫入。
  - PRD 11.1 和章程要寫清楚分工。

**M2. `hidden_catalog_uids` 與「複製成我的版本」會讓組合壞掉**
- 依據：PRD 10.2「複製成我的版本…同時自動隱藏原本的品項」；PRD 11.3 把「隱藏清單」和硬性過濾並列，結果是灰階。
- 情境：使用者把組合裡的內建豆漿複製成自己的版本並修正數字，原品項就被隱藏。組合還指著原 id，於是被灰階或略過。使用者照系統鼓勵的方式修正資料，組合反而壞了。
- 改法（擇一，寫進 11.3）：
  - (a) 引用時解析：ref 被隱藏，而且有一筆未封存的 `custom_foods` 的 `copied_from === ref`，就改用那一筆。
  - (b) 複製的當下，在同一個 transaction 內把所有組合的 ref 改指新 id。
  - 建議用 (a)：不改資料，只在一個函式裡處理。
- 同時要定義「被隱藏」歸哪一類。它的語意是「已不存在或買不到」（10.2），應比照下架：略過並中性提示，不要跟過敏原阻擋一樣灰階。

**M3. 「整個組合灰階」和「略過單一品項」粒度矛盾，且沒有對應選擇器現有行為**
- 依據：PRD 11.3 第 3 點說被擋的組合灰階；第 4 點說下架時帶入略過該品項。三件事都沒定義：3 件裡只有 1 件被過敏原擋，整組是否不能用？骨架 `allow` 被平行工作線 A 改掉之後怎麼辦？內建資料修正改了品項 `role`，造成兩個主餐，又怎麼辦？
- 改法：統一成「元件級」判定。
  - 組合卡片永遠可以點，卡片上用中性文字列出「有 N 項目前不能用：原因」。
  - 帶入時，被擋或下架或隱藏的元件不預選。
  - 整組只剩 0 個可用元件時，才整張灰階。
  - 過敏原仍由選擇器既有的硬性過濾擋住，安全性不變。
  - 驗證一律用 catalog 當下的 `role`，不信組合裡存的 `role`（因為營養已經改讀 catalog，`role` 也應該一致）。

**M4. `valid_slots` 的「提示」規則不存在，選擇器實際是隱藏**
- 依據：`js/ui/item-picker.js:129` 依 `valid_slots` 過濾；`js/ui/tab-today.js:628` 骨架也依 `valid_slots` 過濾；PRD 10.3 說「否則新增完在這個時段看不到它」。PRD 11.1 卻寫「照 `valid_slots` 規則在選擇器裡提示」。
- 後果：早餐組合帶入宵夜時，會出現已選但畫面上看不到、無法取消的元件；只限午晚餐的骨架在早餐引用時，骨架驗證也會失敗。
- 改法：明訂 `valid_slots` 是瀏覽用的過濾，不是安全規則。帶入的元件不受它限制，已選元件在選擇器裡一律顯示。另外要明訂組合引用的骨架驗證不檢查時段。

**M5. 用油與調味的「沒選則 null」在「從紀錄存成組合」這條路徑上沒有定義**
- 依據：PRD 3 節的表規定 `daily_log.implicit` 存實際克數與程度，裡面分不出「用預設」和「使用者指定」。PRD 11.1 說沒選就是 null、引用時套用當下預設。
- 後果：從紀錄存成組合會把當時的預設克數寫死。之後使用者把「用油習慣」改成少油，組合不會跟著變，這正是 null 設計要避免的事。調味也一樣：已選醬料時的預設清淡（#28）會被寫死成使用者的選擇。
- 改法（擇一）：
  - (a) 從紀錄存成組合時，`implicit` 一律設為 null（使用者帶入後可以再改）。
  - (b) `daily_log.implicit` 加一個「是否使用者指定」旗標。這會改 MealContent 格式，屬於 A1，要在 −1a 定案前決定。
- 建議用 (a)。從選擇器送出這條路徑，只有使用者主動改過才存值。

**M6. 餐點日曆引用有兩個問題：可能一鍵直接記錄，也可能顯示未來預算**
- 依據：PRD 7 節 Phase 3 規定日曆依日期寫 `meal_plan` 或 `daily_log`（回填過去）；PRD 11.3 寫「把組合填進某個時段的計畫」；PRD 6.2 規定「永遠不計算、不顯示未來日期的熱量預算」。
- 問題 1：組合填進過去日期，等於直接寫 `daily_log`，違反 11.3「不做一鍵直接記錄」。
- 問題 2：11.3 的卡片熱量「依今天預算算出」，在日曆的未來日期情境違反 6.2。
- 改法：
  - 日曆引用一律帶入三分頁編輯器（Phase 3 本來就用它），不直接填入。
  - 日曆裡的組合卡片，只顯示商品的固定熱量加上「自煮份量當天決定」，不做預算縮放。

**M7. 章程 B9、C1.5 沒把 `meal_combos` 列進去**
- 依據：B9 下架規則只列 `meal_plan`、`daily_log`、`copied_from`；C1.5 的「一筆一個 key」清單也沒有 `meal_combos`。
- 改法：兩處都補上 `meal_combos`。B9 的 check-engine 斷言要加一條：組合引用已刪除的 id 時，解析不拋錯，並回報缺少的元件。

**M8. C4.16 的 check-arch 寫法不可行或不精確**
- (a) 依 C2，IndexedDB 存取本來就只在 db.js。其他檔案呼叫的是 db.js 匯出的函式，不會出現 store 名稱，所以 grep `meal_combos` 永遠會過，實際上沒有檢查。應改成：列出 db.js 裡組合的「讀取」函式名，限制只有白名單檔案可以 import 或呼叫它們。
- (b) 白名單漏了兩處：
  - 入口 2（「已記錄的一餐」存成組合）實際在 `tab-today.js`，hero 也在同一個檔案。把這個檔案放進白名單，規則就形同虛設。
  - B-3 匯出匯入要讀整個 store，會被擋。
  - 改法：讀取函式和寫入函式分開管。寫入（`createCombo`）可以在較多檔案出現；讀取（`listCombos`/`getCombo`）只限選擇器、管理區、日曆、匯出匯入四個檔案，寫出具體檔名。
- (c) 後半句「引用時重新跑硬性過濾與骨架驗證」沒有任何檢查方式，違反章程開頭「沒有標註檢查方式的規則不應該存在」。
  - 改法：在 `engine/meal-content.js` 定義唯一的 `resolveCombo(combo, catalog, profile, hidden, customFoods)`，回傳可用元件、被擋元件與原因、缺少的元件。
  - check-engine 對它斷言以下情況：過敏原、隱藏後改用複製版本、下架、骨架 `allow` 失效。
  - 「ui 每次引用都經過它」標〔人〕。

## 建議修改

1. **命名衝突**：engine 已有 `generateItemCombos` 和「多品組合」，B6.4 也用了「組合的過敏原」。store 叫 `meal_combos`、函式叫 `*Combo*`，grep 和閱讀時都會誤中。建議程式裡改名，例如 `saved_meals`/`SavedMeal`；UI 仍可以叫「我的組合」。
2. **不要另外推算 `meal_type`**：11.1 用 `prep_tier` 推算快煮或開伙，跟計畫和紀錄「存來源的 `meal_type`」不一致。從開伙存的全 🟢 組合會被改判成快煮，填進計畫時還會改變有效型態。兩個入口本來就知道 `meal_type`，直接存就好。帶入時把選擇器切到該分頁和子切換；還要寫明組合列顯示所有組合，還是只顯示同型態的組合。
3. **11.2 自相矛盾**：「去掉…估算元件」和「含估算元件的那一餐不提供」只能留一個，建議留後者。另外，紀錄裡已經下架或隱藏的 ref 要在存成組合時濾掉或提示，不要存進死參照。
4. **單一轉換函式**：兩個入口共用 `toSavedContent(mealContent)`，放在 `engine/meal-content.js`，入口 1 也對剛寫入的紀錄內容呼叫它，符合 C2，避免兩份去快照、去縮放的邏輯。也可以考慮只留入口 2：送出後在已記錄的卡片上按「存成組合」，少一個送出流程的勾選框。
5. **跟 5.4 第 2 點、第 4 節的關係要寫明**：5.4 禁止從 L3 複製成計畫，理由是「紀錄變成偏好來源」。入口 2 是從 L3 建立組合，因為是使用者明確操作所以可以接受，但要寫一句說明，避免下一輪審核判定矛盾。同時比照第 4 節加一條禁止：不得依紀錄頻率提示「你常吃這個，要存成組合嗎？」
6. **跟 decisions #4 的關係**：#4 以「少一份要維護的資料結構」否決了週模板。#31 應註明組合是單餐、不是週模板，不推翻 #4，而且組合不進 L1/L2 解析規則，也不自動填入計畫。
7. **B-3 匯出匯入**：組合引用 `custom_foods` 的 id，匯入時要跟 `custom_foods`、`hidden_catalog_uids` 在同一個 transaction 寫入；如果匯入會重發 id，要同步改寫組合的 ref。在 B-3 驗收裡寫明。
8. **依賴順序**：管理區塊位置寫「我的品項旁邊」，封存或還原我的品項也屬 B-1。寫明 C 是否依賴 B-1；若不依賴，C 先做時管理區放哪裡也要說。
9. 11.5 補一句：組合內容不能直接編輯，要改就帶入、調整、另存新組合、封存舊的。這樣使用者不會找不到「編輯」。

## 可以接受的取捨

- 組合不存商品快照、計畫存快照：兩者用途不同。組合不佔預算，是範本；計畫佔預算、要穩定。Phase 3 填入時才補快照也一致。前提是 M2、M3 的解析規則寫清楚。
- 食材 id 改名：組合在 Phase 0 之後才出現，食材 id 已在 −1b 凍結（B4），不會碰到改名；刪除由 M7 的 B9 規則處理。
- 我的品項過敏原未確認：沿用 C4.1 和 10.4 的元件級硬性過濾就夠了（配合 M3），不需要另訂規則。
- 低碳不套用在組合引用：符合 C4.8 和 #26。11.4 把「之後進推薦」列為 C3 審核事項並限制符合 C4.7，寫法正確。
- 名稱可以重複、依建立順序排、不記使用次數：符合不評判原則，簡單，可以接受。
- 不做一鍵記錄、只做帶入：多一次點擊，但避免把過敏原或下架狀態藏起來，值得。

結論：需修改後實作（M1–M8 修完即可，不需要重新設計）。
