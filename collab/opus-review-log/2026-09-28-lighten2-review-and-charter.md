## 結論

1. **四項具體指控都屬實**：item-picker 把缺過敏原當 `[]`、feast.js 台式品項漏碳水和脂肪、`daysSince` 時區錯、`oil_level` 沒人讀。但架構 review 漏了**同一類、更嚴重的問題**，而且「演算法層健全，只搬家、不改邏輯」這個說法不成立：
   - `recommend.js` 把 null 當 0 算，直接違反章程 B3 第 5 條。
   - 自組食譜的過敏原合併時，缺欄會被當成安全。
   - `passesHardFilters` 對自訂食物**整個跳過過敏原檢查**。
2. **Phase −1 前後矛盾**：它自稱「完成後 App 行為跟 v1 一致」，但同一個 Phase 裡又要修資料、加用油、統一過濾規則、換 DB，這些都會改變行為。一定要拆成兩段：
   - 純重構：用錄下的推薦結果比對（golden master）證明行為不變。
   - 修正：附上改動前後的差異報告。
   現在的 check-engine 只驗證「規則有沒有被違反」，不驗證「輸出有沒有變」，重構時抓不到推薦結果被悄悄改掉。
3. **食物資料 review 我抽查了 26 筆 TFDA 編號，全部存在，數字也對得上**，判定大致正確。但有三個系統性漏洞：
   - **完全沒審過敏原**：燕麥依台灣法規屬含麩質穀物、泡菜的 TFDA 樣品含魚露、照燒醬的醬油含黃豆，三個都漏標；詞彙表也缺「花生」。
   - **官方數字被估算覆蓋**：麥當勞 7 筆的 note 寫明脂肪是官方標示（例：fw08 34g），資料裡卻被反推值蓋成 19.3g。TFDA 換算的飲料明明有碳水和脂肪實測值，也被反推。這正是章程 A2 禁止的事，review 卻寫「數值先不動」。
   - **「外食 69 筆全部估算」、「TFDA 沒有收錄現成品項」兩句不對**：TFDA 有飯糰、水餃、小籠包、鍋貼、蚵仔煎、茶葉蛋、手搖奶茶等。反過來，超商那 35 筆有不少是品牌或類別的綜合值（例如「JohnnyBro（蛋白餐/減醣）」、「光泉／棒蛋白」），不是單一商品，歸成 `label_unsourced` 太寬鬆。
4. **用油「煎 5g／炒 10g」合理，可以當預設值**，但要補三件事：
   - 做法：把油建成一個真正的食材（TFDA M1100101 大豆油 883.9 kcal），當作這一餐的隱含成分，不要在烹調法上另開 `oil_g` 特例欄位。
   - 規則：油量不跟主要槽位一起縮放。
   - 說法：「推薦熱量整體上升」不準確。縮放會自動吸收，實際效果是主食份量變少。
5. **章程方向對，但擋不住「修修補補」的關鍵條款缺了**：
   - 缺「修 bug 必須先寫一條會失敗的斷言」。
   - 缺「產品概念變更要先改 PRD、留決策紀錄」。使用者說的根源是「概念一改再改」，但章程只管資料和程式碼。
   - 有幾條寫了卻檢查不了，例如 B3「每條都要有 check-engine 斷言」，第 10、11 條（畫面不出現運動、不評判）是 UI 層，Node 測不到。
   - 「不通過就不能提交」沒有 CI 或 hook 強制，等於靠自覺。
6. **章程的資料模型設計有矛盾**：
   - 每筆只有一個 `source`，但同一筆的熱量和碳水出處不同，寫不下。
   - `confidence` 其實可以從每個欄位的出處推導出來，另外存一份只會多一個不同步的來源。
   - 另有三處規則會直接擋掉或改變現有資料：
     - 「熱量為正數」會讓 0 kcal 的烹調法檢查失敗。
     - 「高/低 ≥1.5 倍不進推薦池」會悄悄把牛肉麵、美式咖啡等 6 筆踢出推薦池。
     - 「複合料理一律含未確認」會讓 30 幾筆外食被擋，review 沒評估這個影響。
7. **跟 PRD 2.0 的最大衝突**：PRD 10.4 明訂「自訂食物的過敏原修正，必須跟 B-1 的編輯畫面同時上線」，否則會卡死。章程 A8 加上 Phase −1 的統一 `filters.js`，會在 Phase −1 就讓有設過敏原的使用者無法使用任何自訂食物，而 v1 的自訂表單根本沒有過敏原欄位。另外，PRD 第 0 節「加一層不是換一層」、第 7 節「不做一次性大改」，跟 Phase −1 的做法相反，要在 PRD 明文改寫這個立場。
8. **架構有兩個更簡單的做法**：
   - **engine 不依賴 data 層**：資料由呼叫端傳進來，engine 全部是純函式，Node 測試不用再模擬 fetch 和 IndexedDB。「引擎不讀 `picker_last_meal_type`」、「不讀運動紀錄」也就能用 import 關係機械檢查。
   - **IndexedDB 改成一筆紀錄一個 key**：不要整個陣列存在同一個 key 底下再配寫入佇列，這樣競爭條件自然消失，不需要佇列。

### 1.2 review 漏掉或寫錯的地方

- **【一定要改】`recommend.js` 違反「null 傳染」**。第 2.4 節的表寫 recommend 用 `sumOrNull`，只對了一半：
  - 自組食譜的 `itemContribution` 用 `num()`，null 會變成 0。
  - `fromConvenience`／`fromTaiwan` 的 `kcal`、`protein_g`、`fiber_g` 也用 `num()`（只有碳水和脂肪保留 null）。
  - 目前資料沒有 null，所以還沒出事。但 B-2（我的品項進推薦池，蛋白質可省略）一上線就會出事。所以 recommend 不能「只搬家」，第 0 節第 1 條和第 1 節的「保留」判定要改。
- **【一定要改】自組食譜的過敏原合併把缺欄當安全**：`unionTags` 直接略過非陣列的值（`recommend.js:451`）。目前靠資料每筆都有欄位擋著。章程 A10「食材 allergen_tags 不為 null」能補上這個洞，但 review 第 2.1 節應該列出來，而且 `filters.js` 要明文規定「組合裡任一成分缺欄，整組就是未確認」。
- **【一定要改】`passesHardFilters` 的 `!item.is_custom` 例外**（`recommend.js:216`）：自訂食物完全不做過敏原檢查。PRD 10.4 已知這個問題，但架構 review 的安全段完全沒提，而 Phase −1 的統一 filters 會直接改變這個行為（見第 4 節的衝突）。
- **【建議改】`disliked_ingredients` 用名稱當 key**（`protein_name`、`vegetable_name`）。資料 review 要把「花椰菜」改名「白花椰菜」，改名就會讓「不吃」清單失效。2.0 應該改用 id。`recipe_feedback` 用的組合 id 是把食材 id 串起來的字串，id 一改，降權紀錄就對不上；MealContent 之後的組合要怎麼識別，review 也沒講。
- **【建議改】手動記錄沿用推薦的組合規則**：v1 手動選也要求「非下午茶必須有 1 個 main」（`tab-today.js:465`）。review 說 `validateContent` 由推薦、自己選、日曆共用，等於把「推薦怎麼組」變成「使用者能記錄什麼」，早餐只喝一杯拿鐵會記不了。要區分「推薦生成規則」和「記錄驗證規則」，這要使用者拍板。

### 1.3 方向評估（ES modules＋catalog＋meal-content＋新 schema）

大方向正確，也是對症下藥：v1 的問題確實是同一件事有多份實作，不是演算法錯。以下是更簡單或需要補的地方：

- **【建議改】engine 改成純函式，不依賴 data 層**。review 定的依賴方向是 `ui → engine → data → core`，允許 engine 去讀 catalog 和 db。建議改成 engine 只能 import `core/` 和 `engine/`，資料由 ui 層（或一層很薄的 app 層）讀好再傳進去。好處：
  - Node 測試不需要模擬 fetch 和 IndexedDB（v1 用 `vm` 加假 fetch，就是因為 `loadAxes` 在引擎裡自己 fetch）。
  - B3 第 10、12 條（不讀運動、不讀 `picker_last_meal_type`）直接變成「engine 底下不准 import `data/db.js`」，一行 grep 就能檢查。
- **【建議改】IndexedDB 一筆紀錄一個 key**。v1 把整個清單存在單一 key `items`，才會有讀改寫的競爭問題；review 的解法是加寫入佇列。更簡單的做法：`daily_log`、`meal_plan` 用紀錄自己的 id 當 key（原生 IndexedDB 加 `keyPath` 和 `log_date` 索引，或 localforage 每筆 `setItem(id)`，v1 的 `recipe_feedback` 已經這樣做），競爭條件自然消失。「複製上週」要全有全無的話，原生 IndexedDB 的 transaction 就辦得到，不需要自己寫佇列。
- **【建議改】沒決定要不要留 localforage**。它是 CDN 上的全域變數，不是 ES module。留著的話 `db.js` 還是要讀 `window.localforage`，跟 B1「不透過 window」衝突，要寫成明文例外，或改用原生 IndexedDB 包一層薄的封裝。
- **【建議改】ES modules 的部署細節沒寫**：
  1. v1 靠 `?v=20260927d` 破快取，但 module 內部的 `import` 不會帶版本參數。GitHub Pages 的快取是 `max-age=600`，手機上可能載到新舊混雜的模組。要選一個做法：import map 加版本、部署時統一改版本字串，或接受「部署後要重新整理」。
  2. module 不能用 `file://` 開，本機開發一定要起一個 server，交給 Cline 時要寫明。
  3. Node 要 `package.json` 的 `"type":"module"`；catalog 若用相對路徑 fetch，Node 那邊要能注入讀檔方式（改成純函式就沒這個問題）。
- **【可以之後】同源共用儲存**：review 注意到 GitHub Pages 同一個帳號下的專案同源、要換 DB 名稱，這點很好。但 `settings` 裡的 key 和未來任何 localStorage 也一樣共用，一律加前綴就好。

### 1.4 Phase −1 範圍

- **【一定要改】拆成兩段**：
  - **−1a 純重構**：只包含 core 抽出、ES modules、catalog 接上舊資料、filters 和 meal-content 收斂。驗收標準是 check-engine 全過，加上**固定 N 組設定下的推薦輸出逐字相同**（重構前先把輸出錄成快照）。
  - **−1b 修正**：資料重做、用油、null 規則修正、過濾統一，每一項都附快照差異，讓使用者看得到推薦結果變了什麼。
  - 另外，「31442 項照樣全過」只在 −1a 有意義。資料一改，候選池大小就變了，檢查項數會跟著變，驗收標準應該寫「全過」，不是寫死 31442。
- **【建議改】不要修一個註定要刪的東西**：feast.js 和美饗日曆 Phase 3 就刪了，Phase 3 前補碳水脂肪只是順手的小事。但如果 Lighten2 在 Phase 3 之前不會拿來日常使用，更省事的做法是 −1 根本不搬 feast 和 tab-ledger。這要看使用者打算什麼時候開始真的用 Lighten2（見第 5 節）。
- **範圍大小**：去掉上面兩點，四個步驟本身合理，不算太大。缺的是：
  - 一支檢查依賴方向和重複函式名稱的小腳本（`tools/check-arch.js`，幾十行）。
  - 快照比對工具。
  兩者都應該放進 −1。

### 2.2 漏掉的系統性問題

- **【一定要改】過敏原和飲食標籤完全沒審**。除了上面的燕麥、照燒醬、泡菜，現成品項也有：
  - 燕麥奶（conv_dr04、conv_pk04 標 `[]`；bf02 只標乳製品）要加麩質或未確認。
  - **詞彙表缺「花生」**。台灣法定過敏原裡花生獨立於堅果；豆花、涼麵醬、刈包、燒餅都常見花生。TFDA 的「豆花(花生)」就含花生醬。以前的審核紀錄甚至拿「含：花生」當範例，詞彙表裡卻沒有這個詞。
  - 「低碳」是 profile 裡的**硬性過濾選項**，但標籤是人工標的，沒有門檻。例如 conv_ch03 碳水 40g 也標了低碳。
- **【一定要改】官方數字被估算覆蓋**。麥當勞 bf11–14、fw06–08 的 note 寫明「脂肪為官方標示」，但目前 fat_g 是反推值：

  | id | note 寫的官方值 | 目前資料 |
  |---|---|---|
  | bf11 | 16 | 11.4 |
  | bf12 | 20 | 13.8 |
  | bf13 | 23 | 15.1 |
  | bf14 | 19 | 13.5 |
  | fw06 | 13 | 6.5 |
  | fw07 | 13 | 11.4 |
  | fw08 | 34 | 19.3 |

  改回官方的蛋白質和脂肪後，碳水應該用熱量扣掉來推（fw08 碳水會從 73.6 變成約 40）。dr06（無糖豆漿）、dr08（全脂鮮乳）是用 TFDA 每 100g 換算，TFDA 本來就有碳水和脂肪實測值，卻用「脂肪佔熱量 X%」反推。**「2026-09-27 補碳水/脂肪」這一整批都要當可疑資料重審**，不能「數值先不動」。
- **【建議改】「TFDA 沒有收錄現成品項」不對**。TFDA 有 R0300101 三角飯糰、R0300201 糯米飯糰 335／100g、R2200201 冷凍豬肉水餃、R2301101 小籠包、R2201401 鍋貼、R3000301 蚵仔煎、R3000101 油條、K0112101 茶葉蛋、Q2104201 豆花，還有 O07 開頭的一系列手搖奶茶，連甜度都分。外食有十幾筆可以從 `estimate` 升級成 `derived`（TFDA 每 100g × 份量）。
- **【建議改】`label_unsourced` 分得太寬**。超商那 35 筆裡，有些是多個商品合併（「香草烤雞沙拉／雞胸肉沙拉」、「光泉／棒蛋白」、「烤多蛋白餐盒／烤蛋白餐盒」、conv_pk03 的 137.5 明顯是平均值）；連鎖餐盒和宅配（Miss Energy、JohnnyBro、NISORO…）是整個品牌菜單，不是一個商品。這些應該歸 `estimate`，只有能對應到單一商品的才算 `label_unsourced`。
- **【建議改】蔬菜的生熟標示**：review 把 5 筆蔬菜標 🔁，份量上是對的，但蔬菜每 100g 才 15–40 kcal，生熟差異對熱量的影響微乎其微。建議章程直接規定**蔬菜一律以生重為基準、`serving_g` 是生重**，省掉蔬菜的 `cooked_to_raw`。生熟換算只留給穀物和肉類，真正會影響採買清單的也只有這些。

### 2.3 用油建議

- 煎 5g、炒 10g（食物代換表油脂類 1 份／2 份）**當預設值合理**。一人份熱炒 1–2 茶匙是常見量；煎的時候有部分油留在鍋裡，5g 已經不算低估。`sm_air_fry` 給 0 可以接受，但它同時代表「烤」，烤箱常會刷油，可以在說明文字註明。
- **【建議改】做法**：新增一筆食材 `cooking_oil`（來源 TFDA M1100101 大豆油），烹調法用 `implicit: [{ref:"cooking_oil", g:10}]` 帶進 MealContent，走同一套營養計算。不要在烹調法上另開 `oil_g`，免得變成 meal-content 裡的特例分支。
- **【一定要改】寫明**：油量不跟主要槽位的 0.5–2.0 倍縮放一起放大縮小；油要出現在紀錄快照裡；「推薦熱量上升」的說法要改。主要槽位會自動縮放吸收多出來的熱量，實際效果是「主食份量變少、部分組合超出縮放範圍而被刷掉」，要用快照比對確認影響多大。
- **【使用者拍板】**：要不要讓使用者設「少油／一般」？每個家庭用油量可以差 2–3 倍，這是自煮熱量最大的誤差來源。

## 3. 章程

### 3.1 能不能防止「修修補補」

B2（單一真相來源、禁止複製一份再改）和 B3（不可退化的規則）是對的，但缺兩個真正有效的機制：

- **【一定要改】修 bug 規則**：「每個 bug 修正都要先在 check-engine 或 check-data 加一條會失敗的斷言，修完變成通過，同一個 commit 提交」。v1 的修補循環主要就是從不需要審核的「修 bug」通道進來的（B4 明文把修 bug 列為免審），沒有回歸測試，同一類 bug 就會一再回來。
- **【一定要改】概念變更規則**：使用者說重來的原因是「概念一改再改」，這是需求層的問題，但章程只管資料和程式碼。要補：
  - 改到型態、L1/L2/L3、MealContent、分頁結構這類概念時，**先改 PRD、留決策紀錄，再改程式碼**。
  - 開一份 `docs/decisions.md`，一行一條，記「決定了什麼、否決了什麼、為什麼」，避免同一個問題被重新討論。
  - B5.4 的「以最近一次審核定案的規格為準」要寫清楚是哪一份文件（見第 4 節）。

### 3.2 寫了但無法執行或檢查的規則

- **【一定要改】B3「每條都要有 check-engine 斷言」**：第 3、4 條（存檔和顯示時各檢查一次）、第 10 條後半、第 11 條（不評判的文案和配色）是 UI 層，Node 斷言測不到。要誠實分成：
  - **機器檢查**：check-engine、check-data、check-arch 的 import 關係和 grep 規則，例如禁止在 `engine/` 底下 import `db.js`、禁止 UI 出現「遵循率」「未完成」等字樣。
  - **人工清單**：放進手機實機腳本。
- **【一定要改】「不通過就不能提交」沒有強制手段**：加一個 GitHub Actions，每次 push 跑 `check-data`、`check-engine`、`check-arch`（或 pre-commit hook）。否則 Cline 或 Sonnet 忘了跑，也不會有人發現。
- **【建議改】A9.7「附前後比較（某個代表性設定下五時段推薦熱量的變化）」**：手動做、格式不固定。改成一支腳本（例如 `tools/diff-recs.js`）自動輸出，跟 Phase −1 的快照比對共用。
- **【建議改】A5.5「serving_g 優先對齊代換表份數倍數」**：例子本身就不是倍數（130g ≈ 4.3 份），這條沒辦法檢查。改成「serving_label 註明約幾份代換表份數」就好。
- **【建議改】`label_unsourced`「只准減少不准新增」**：要讓 check-data 對一份凍結的名單比對，才檢查得了，要寫進 A10。

### 3.3 規則本身的矛盾

- **【一定要改】單一 `source` 對上逐欄位 `confidence`**：超商品項的熱量來自包裝、碳水是估算；食材的營養值來自 TFDA、份量來自代換表、熟重是推算。一筆一個 `source` 寫不下。
  - 建議：記錄層級的 `source` 當預設，再加選填的 `field_sources: { carb_g: {type, ref}, ... }` 覆寫個別欄位。
  - **`confidence` 不要另外存**：依 A3 的定義，它就是「每欄出處類型＋有沒有 ref」的函式，由 catalog 推導就好。多存一份只會產生新的不一致。
- **【一定要改】A10「熱量為正數」**：`axis=method` 是 0 kcal，無糖茶、美式咖啡的區間下限是 0，會直接檢查失敗。改成「非負」，另外規定食材除了 method 以外要大於 0。
- **【一定要改】A4「kcal_range 高/低 ≥1.5 不進推薦池」**：v1 的規則是「沒有 `kcal_rep` 而且比例 ≥1.5 才排除」。照章程的寫法，ln04 牛肉麵、dr09 美式咖啡（5–15，比例 3 倍但毫無意義）、tc01、tc02、tc05、tc08 會被悄悄踢出推薦池。要嘛照 v1 語意寫，要嘛改成「比例 ≥1.5 而且差距 ≥150 kcal」，並把它列為一項會改變行為的修正。
- **【建議改】A6.2「複合料理一律含未確認」**：目前 69 筆外食裡，蛋餅、飯糰、牛肉麵這類標了具體過敏原、卻沒有未確認的至少有 30 筆，套用後這些全部會對「設了任何過敏原」的使用者被擋掉。規則本身是對的（安全優先），但這是一項重大行為變更，要列進 −1b 的差異報告，並讓使用者知道。
- **【建議改】A2 出處分級混了兩個領域**：食材是 tfda > usda > derived；商品是 label ≈ official_web > estimate；`exchange` 是份量和生熟重專用。放在同一張由高到低的表，再配上「有高等級不得用低等級」，會讓人誤以為代換表的營養值比包裝標示可靠。拆成「食材」和「現成品項」兩條順序。
- **【建議改】id 凍結時間點**：A4 寫「一經使用不得改名」，範例卻用新 id `chicken_breast`（現在是 `ps_chicken_breast`），broccoli 的 id 跟名稱也不符。寫明「id 在 Phase −1b 完成時凍結，之前可以一次改完」。現在是唯一可以免費改名的時機（因為沒有使用者資料）。

### 3.4 缺少的條款

- **【一定要改】飲食標籤的固定詞彙和定義**：A6.1 只固定了過敏原詞彙。「低碳」「高蛋白」如果要留，應該由數值自動算出來（例如每份碳水 ≤ X g），不要人工標。「一般」和「無特殊限制」兩個選項是重複的。
- **【建議改】TFDA 改版程序**：TFDA 出新版時，重跑所有 ref 的比對，列出差異再更新。另外 `tfdb-2025-simplified.json` 放在 `collab/`（協作暫存區），但 check-data 依賴它，應該搬到 `data/reference/` 之類的地方做版本管理。
- **【建議改】營養值由腳本產生，不要手抄**：食材存 `source.ref`，`per_100g` 由腳本從 TFDA json 產生；或者 check-data 直接要求跟 TFDA 值（四捨五入後）**完全相等**，而不是「差 5% 才警告」。手抄錯誤就是現在這份資料的主要病因，抄錯了應該算錯誤，不是警告。
- **【建議改】資料下架規則**：刪掉一個食材或品項時，`meal_plan` 或「我的品項」的 `copied_from` 還指著它怎麼辦（顯示中性提示、不崩潰）。
- **【可以之後】外部相依政策**：新增 CDN 函式庫要經過 B4 審核。

### 3.5 太重的地方

- **【建議改】B4 每個餐型骨架都要獨立 Opus 審核、逐字存檔**：PRD 平行工作線 A 本來就要大量擴充骨架（目前午晚餐只有 3 個），一個一個審會很痛苦。改成「一批骨架一起審」。
- **【建議改】已在 PRD 定案的 schema 變更免審**：Phase 2 的 `meal_plan`、B-1 的 `custom_foods`、Phase 4 的採買欄位都已經在 PRD 定案，照 PRD 做的 store 變更也會觸發 B4。加一句「照已定案 PRD 實作的不必再審，偏離 PRD 才審」。
- **【可以之後】`data/CHANGELOG.md` 跟 git log 重複**：只要規定 commit 訊息格式（例如 `data(fix): ps_shrimp 改對 TFDA J2200501`）就能取代。保留也可以，但不要讓它變成另一份會跟實際不同步的資料。
- **【可以之後】B5.3 手機實機腳本**：「動到畫面流程就跑一次」可以接受，但建議只在每個 Phase 驗收時跑完整版，平常只跑有受影響的那一段。

## 5. 需要使用者拍板的問題（附我的建議）

1. **Phase 3 之前會不會日常使用 Lighten2？**
   - 建議：先回答這題。會用，就保留美饗日曆，只補碳水脂肪；不會用，−1 就不搬 feast.js 和 tab-ledger，省下修一個註定要刪的東西的工夫。
2. **自訂食物的過敏原在 −1 怎麼處理？**
   - 建議：−1 就在自訂表單加過敏原欄位（預設「未確認」），同時拿掉 `is_custom` 例外。安全優先，而且工作量很小。
3. **用油預設值，要不要讓使用者調整？**
   - 建議：預設煎 5g、炒 10g、氣炸 0；profile 加一個「少油／一般」（少油＝減半）；用油不跟著縮放。
4. **過敏原詞彙加「花生」？**
   - 建議：一定要加。要不要照台灣法規再加「芒果」「亞硫酸鹽」「軟體動物（蚵仔等）」，請使用者決定，我建議至少加花生和軟體動物。

## 4. 標〔機〕但機器檢查不了的規則
