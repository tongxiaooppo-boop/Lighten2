## 二、完整回答（逐字）

### 0. 結論

方向可行，但 v0 **還不能開工**，有四個必須先處理的問題：

1. **預約與「記下」會把新估算洗成 700 kcal**：選擇器的估算草稿只帶 `{ size, name }`，`estimateComponent(size, name)` 每次都用 `ESTIMATE_SIZE_KCAL` 重算快照（`js/engine/meal-content.js` 第 536–542 行）；預約解析回草稿時也只取 size、name（第 932–933 行），所以 `planPseudoLog`（第 989–994 行）、`savedMealTotals`（第 1071–1073 行）、今天預約按「記下」（`js/ui/today-plans.js` 第 56 行）都會把「白飯＋4 菜 1 湯（中）」變成 700 kcal、其他營養素 null。草案 §5 完全沒提這條路徑。PRD 第 3 節的表其實已寫「estimate 的 snapshot 照存、不重算」，現在程式能過只是因為快照剛好等於常數。
2. **醬料資料不能直接拿衛福部的**：`P0700101 醬油` 的脂肪、纖維、飽和脂肪是 null，`P0900201 香油` 的蛋白質與鈉是 null，`N0100201 冰糖` 多欄 null；脂肪 null 會讓整道菜、整餐的脂肪變 null（章程 C4.5 null 傳染），違反草案「七欄都有數字」的目標。沙茶醬 `P1001701` 鈉 420.8 mg/100g 確實可疑（同表沙茶粉 2143、素沙茶醬 1990.5，且沙茶醬成分有扁魚、蝦米）。衛福部沒有一般食鹽（只有岩鹽 34468、低鈉鹽），也沒有白砂糖、水。要一張「調味料選樣表」處理（Q6）。
3. **跟現行 PRD 與決策直接衝突**：PRD 第 8 節第 278 行寫「用外食的直接估算 S／M／L 記錄就好，**不建菜色資料**（decisions #148）」；decisions #148 本身也寫「不建菜色資料」。草案要建一份菜色資料，需要新的決策取代 #148 那半句，否則違反 A1（先改 PRD 再改程式）。
4. **白飯 1 碗＝200g 跟 App 自己的資料不一致**：`food_tree.json` 的 `fx_cooked_rice` 是「1/4 碗＝40g」，等於 1 碗 160g；單品記錄「白飯 1 碗」跟估算「1 碗」會差 25%。

其餘都是可以直接照做的修正。

### 2. §5 八題

**Q1 要不要新增 `est` 欄位** → **要，而且草稿也要帶快照**。
- 形狀：`{ kind: "estimate", name, size, est: { type: "rice_one" | "rice_four_one", cat: "veg" | "mixed" | "main" | null }, snapshot }`；沒有 `est` 的就是現有的一般外食估算，舊紀錄不用遷移。
- 用途不是「之後重算」（紀錄快照不回溯，PRD 第 3 節），而是：①選擇器重新帶入（預約、編輯）時能還原成同一個選項；②明細顯示「白飯 1 碗＋菜肉 120g」這類說明；③日後統計估算類型（不評判）。
- 程式：`estimateComponent` 改成接受 `{ size, name, est, snapshot }`，有快照就照用；`savedMealDraft` 把快照與 `est` 一起帶回草稿；選擇器加入新估算時由 engine 的新函式算好快照再放進草稿。這同時修好結論 1。
- 驗證：`db.js` 紀錄與預約兩處加「`est` 不存在，或 type、cat 都是列舉值」；新估算的快照七欄必須都是數字（舊估算維持只驗 kcal）。

**Q2 驗證與備份**
- 不加熱量範圍檢查（S／M／L 對應的熱量會隨資料改，不應寫進 db 驗證）。
- 加 Q1 的 `est` 列舉檢查，以及「有 `est` 就七欄非 null」。
- 備份不升版（格式向下相容：舊備份沒有 `est`）；但要在 check-engine 加「含 `est` 估算的紀錄與預約匯出再匯入後快照不變」的來回斷言。

**Q3 選擇器估算卡**
- 卡片結構：先選類型「一般外食｜白飯＋1 樣｜白飯＋4 菜 1 湯」，再選（1 樣才有）類別，再選 S／M／L；按鈕旁的熱量由 engine 用目前資料算，**不再直接讀 `ESTIMATE_SIZE_KCAL`**（一般外食仍是那組常數）。
- 快照守則：新的 DOM（類型、類別按鈕）用 `data-` 屬性與事件委派（照現有 `data-estimate-size` 寫法），不新增需要 `getElementById` 的元素；名稱輸入框沿用現有 id。`diff-recs` 的 `ui.txt` 會因為估算卡 HTML 改變而變，這是刻意的，要逐條說明。
- 補記：**提供**。補記用的就是同一個選擇器，「昨天在家吃飯」正是最常補的情境；只有昨天卡片那一排 S／M／L（`recallEstimateLogEntry`）維持不變。預約模式也提供（家裡固定共食可以先排）。
- 已加入列表的文字改成讀元件快照的熱量。

**Q4 資料怎麼載入** → **進 `loadCatalog`，但只載「算好的小檔」**。
- 產生檔只放 engine 要用的東西：類別平均的每 100g 七欄（素菜、菜肉、主菜、湯）、白飯每 100g（從 `fx_cooked_rice` 抄過來，check-data 驗相等），加上每道菜的名稱、類別、每 100g（給說明頁與審查用），約數 KB。比照 `food_tree`：放進 `loadCatalog` 的 `Promise.all`，catalog 正規化成 `catalog.homeEstimate`。
- 不要懶載：檔案很小，懶載還要處理失敗重試與選擇器先畫再補，不划算。
- 建置時才讀 `tfda_lookup.json`（約 980KB）；執行期不讀。
- 算法放 `tools/lib/home-dish-values.js`，建置工具與 check-data 共用（比照 `food-tree-values`，C2）。

**Q5 check-data 規則**（照草案，加這幾條）
- 產生檔逐筆、逐欄（含類別平均與白飯）等於重算結果。
- `ref` 只能是：`ingredients.json` 的 id、`food_tree` 的 `fx_` id、`tfda_lookup` 的編號、或調味料選樣表（Q6）裡的 id；查不到就是錯誤。
- 每道菜與每個類別平均七欄都不是 null（缺值只能經由 Q6 的規則補 0）。
- `cooked_g` ≤ 食材總重＋水；另外加下限警告（`cooked_g` < 非水食材總重 × 0.5 時警告，抓「成品重打錯」）。
- 類別：**手動標**（來源檔多一個 `class` 欄位），check-data 用草案 §3 的規則算一次，不一致時給警告，不是錯誤（理由見 Q7）。
- 每類至少 3 道（湯目前只有 2 道，見 Q7）。
- 有 NTU 對照的，算出值跟 NTU 差超過 25% 要在 note 寫理由（比照 B5.4 的驗算精神）。
- note 不得有「AI」字樣（章程 B2.3 的精神）。

**Q6 醬料與調味的來源怎麼處理最乾淨** → **新增一張小的「調味料選樣表」`data/reference/home_dish_seasonings.json`**，每種調味料一筆：名稱、選定來源、理由。規則：
1. 優先選衛福部**欄位完整**的樣品，不用有 null 的：
   - 醬油：用 `P0700401 淡色醬油`，不用 `P0700101 醬油`。後者的脂肪、纖維、飽和脂肪是 null；前者全有，鈉 5277.5。
   - 香油：用 `M1500101 白芝麻油`，不用 `P0900201 香油`。後者蛋白質、鈉是 null；前者在油脂類，已依 B5.1 補 0。
   - 糖：用 `N0100301 紅砂糖`（欄位完整），不用 `N0100201 冰糖`（多欄 null）。衛福部沒有白砂糖，紅砂糖與白糖熱量差不到 1%，note 寫明。
   - 豆瓣醬 `P1004101`、烏醋 `P0600701`、蠔油 `P0800301` 照用。
2. 衛福部沒有的寫 `derived` 並給公式：
   - 食鹽：鈉 39,340 mg/100g，NaCl 化學計量，不用岩鹽的 34468。
   - 水：七欄 0。
3. 數值可疑的不用：沙茶醬 `P1001701` 的鈉不採用，改用市售包裝標示（`label`，寫品牌與網址或包裝照片出處），或在找到標示前把「沙茶牛肉炒空心菜」暫時移出類別平均。我**沒有查證**市售沙茶醬的實際鈉，只能確定衛福部這筆跟同表兩筆相近產品差約 5 倍。
4. 少數只有飽和脂肪是 null、脂肪 ≤0.5g 的（蠔油、烏醋）：比照 B5.1「蔬菜、水果脂肪 ≤0.5 → 飽和脂肪填 0」，把白名單擴到「調味料類、脂肪 ≤0.5」。這是改章程 B5.1，屬 C3；不想改章程的話，就換其他樣品或從配方拿掉。
5. 太白粉：衛福部查不到同名樣品（我用名稱查過）；每盤 3–8g，影響很小，建議配方直接不列，note 寫明。

**Q7 排除哪幾道、類別平均要不要加權**
