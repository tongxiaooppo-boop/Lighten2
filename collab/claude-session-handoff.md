## 這份交接要做的事

### 1. 四個需要使用者決定的開放問題（先問清楚再動手，不要自己猜）

Opus 兩輪審查都留下未回答的問題，累積到現在有 4 個：

1. **下午茶要不要主動推薦洋芋片/可頌/含糖飲料這類「治療型」品項？** 還是這些只在使用者自己選或預約時才出現，系統不主動推。（目前程式是會主動推的，例如預算約180kcal時模擬會推含糖豆漿。）
2. **`intake_high`（近期攝取偏高、系統暫不下修目標）這個狀態要不要跟使用者明講原因？** 選項是「明講」（較透明但可能感覺被評價）vs「只講資料不足，不點破原因」。這題其實是延續 9/27 第三輪 Opus 審核時留下的兩題之一，另一題「校正值要不要直接顯示」上次已經拍板「直接顯示」，這題還沒拍板。
3. **`連鎖健康餐盒`／`宅配健身餐`（convenience_items.json 裡的 conv_ch*／conv_dv*）該歸類成「超商」還是應該獨立一個來源選項？** Opus 指出這兩類其實不是超商能買到的（是連鎖店/外送宅配），現在歸在 convenience 分類下會被「今日建議來源=超商」的使用者篩選邏輯誤收，等於選了超商卻推薦宅配健身餐。
4. **今日建議彙總卡的標題文案。** 目前顯示「今日剩餘預算」（違反禁用字規則，「剩餘」在禁用清單裡）。Opus 建議改成「今日未記錄時段的建議熱量」，需要使用者確認語感可以接受，或提出別的說法。

### 3. 資料品質修正（審查報告第6節）

**一定要修（過敏原漏標，安全性問題）：**
| 檔案 | 品項 | 問題 |
|---|---|---|
| convenience_items.json | conv_dr01–03 豆漿 | 漏標「黃豆」 |
| convenience_items.json | conv_bx02（內含蛋白塊） | 漏標「蛋」 |
| convenience_items.json | conv_ch01（有水煮蛋） | 漏標「蛋」 |
| convenience_items.json | conv_pk01／pk02 蛋白飲 | 標`[]`，需查包裝實際蛋白來源 |
| convenience_items.json | conv_dv01（青醬） | 通常含起司/松子，漏標「乳製品」「堅果」 |
| taiwan_items.json | bf06 蘿蔔糕 | 台式做法常加蝦米，建議保守標「甲殼類」 |
| taiwan_items.json | fw06 麥當勞沙拉 | 醬料過敏原未確認 |

**建議修（資料矛盾/估算偏差）：**
- `bf05`（無糖豆漿小杯360ml，125kcal）跟這次新增的`dr06`（無糖豆漿大杯300ml，105kcal）數字矛盾（小杯反而比大杯熱量高）——建議刪掉bf05只留dr06，順便核對早餐店大杯實際容量（常見是450ml上下，不是300ml）。
- `tc03`可頌代表值400kcal偏高，衛福部食品成分表數據換算一般60-70g可頌約270-320kcal，建議改成300。
- `dr07`（含糖豆漿）數值其實是包裝產品版本，但名稱寫「早餐店常見版」，來源跟名稱對不上，建議改名或改註記。
- 台式品項普遍沒有碳水/脂肪數據（一律記0），畫面上如果有顯示這兩個數字會誤導，建議至少先不顯示或註明「無資料」。
- 台式多品項組合被記成`source_type:"recipe_template"`不太對，應該是`taiwan_item`或新的組合類型。
